- 추천·장소·알림·탈퇴용 빈 테이블이나 동작하지 않는 API를 미리 추가하지 않는다.
- 사진함 업로드·목록·중복 병합 API는 별도 담당자가 구현한다. 이 계획에서는 스키마와 번들 연결 경계를 제공한다.

## 2. 공통 구현 기준

| 역할 | 방식 |
| --- | --- |
| 내용·참여 변경, 발행·삭제 | REST |
| 편집권·활동 표시·실제 변경값 전달 | STOMP WebSocket |
| 최종 데이터·버전·편집권 검증 | PostgreSQL |
| 실시간 메시지 중계 | 단일 서버의 Spring 내장 브로커 |
| Redis | 기존 인증 세션 |

- 루트 단일 Gradle 모듈과 기존 Kotlin·Spring MVC·JPA·PostgreSQL·Redis를 유지한다.
- 새 의존성은 `spring-boot-starter-websocket`만 추가한다.
- 범용 동시성 프레임워크·분산 락·Redis Pub/Sub·outbox·이벤트 재생 저장소·이미지 정리 배치를 추가하지 않는다.
- 각 도메인에 필요한 `controller / service / domain / dto`만 만든다.
- 공용 이미지 영속성은 `image`, 사진함 기록은 `photo`, 번들 생애주기는 `bundle`에서 관리한다.
- `global`의 JWT·저장소 통신 등 기술 코드는 기능 Service·Controller·DTO에 역의존하지 않는다.
- 기존 응답을 공유하는 `BunchResponse`를 일괄 확장하지 않고 번들 전용 DTO를 사용한다.
- 변경 요청은 번치 → 번들 → 필요한 하위 행 순으로 잠근다. 여러 번들은 ID 순으로 처리한다.
- 사용자 입력·드래그 중에는 DB 트랜잭션을 열어두지 않는다. 새 번들 저장·발행 트랜잭션에 외부 파일 호출을 넣지 않는다.
- 본 작업에서는 서버 규칙을 지키는 두 요청의 기본 경합을 검증한다. 다중 서버·대규모 장애 복구는 후속 강화 범위다.

## 3. #23 이미지·Photo 기반

### 스키마

| 대상 | 데이터·제약 |
| --- | --- |
| `image_assets` | ID, Cloudinary public ID, URL, 생성 시각. public ID 유일성 |
| `members`·`bunches` | nullable `profile_image_asset_id` |
| `photos` | ID, 번치, 이미지 자산, 파일 해시, 처리 상태, 촬영 날짜·선택적 시각, 날짜 출처, 생성 시각 |
| `photo_uploaders` | Photo·회원·업로드 묶음 UUID·업로드 시각. Photo·회원 조합 유일성 |

- ImageAsset은 저장 파일이고 Photo는 번치 사진함의 기록이다.
- 같은 Photo의 업로더는 여러 명일 수 있다. `uploaded_by` 단일 컬럼으로 제한하지 않는다.
- 파일 해시는 업로드 입력 바이트의 SHA-256으로 관리한다. 중복 판별의 범위는 같은 번치다.
- 촬영 날짜·시각은 앱이 정리해 전달한 값을 보관한다. 시차 재변환·업로드 시각 대체를 하지 않는다.
- 서버 생성 시각은 `TIMESTAMP WITH TIME ZONE`으로 저장한다.
- 기존 기본 번치는 `last_used_at`으로 계산한다. `members.last_bunch_id`는 추가하지 않는다.

### 기존 프로필 이전

1. 기존 public ID·URL 쌍과 같은 public ID의 데이터 일관성을 검사한다.
2. 새 Flyway 마이그레이션으로 ImageAsset을 백필하고 프로필 FK를 연결한다.
3. 파일을 재업로드하지 않고 기존 API `imageUrl`을 유지한다.
4. 기본 이미지는 FK가 `null`인 상태로 유지한다.
5. 이전 검증 후 기존 직접 저장 컬럼을 제거하고 JPA 매핑을 전환한다.

프로필의 정사각 JPEG·크기·메타데이터 검증과 가입 시 이미지 실패 동작은 유지한다.
사진함의 일반 이미지 검증에 프로필 규칙을 적용하지 않는다.

### 이미지 삭제

- 개인·번치 프로필·Photo·번들 사진의 참조가 남아 있으면 파일을 삭제하지 않는다.
- 모든 참조가 사라진 파일만 DB 커밋 후 삭제를 시도한다.
- 외부 삭제 실패는 파일 식별자를 로그에 남긴다. 정리 배치·실패 큐·참조 수 카운터는 추가하지 않는다.
- 이미지 자산 FK로 사용 중인 자산의 DB 삭제를 보호한다.
- 새 파일 반영이 실패하면 기존 프로필을 유지하고 새 파일 정리를 시도한다.

### 완료 조건

- 개인·번치 기존 이미지 백필과 기본 이미지가 검증된다.
- 가입·본인 프로필·번치 이미지·초대 응답의 회귀가 없다.
- 공동 업로더·파일 참조·유일성과 실제 PostgreSQL Flyway/JPA 검증이 통과한다.
- 사진함 담당자가 사용할 데이터·조회·최종 삭제 연결 계약을 문서화한다.

## 4. #24 번들 기능 전체

### 스키마

| 테이블 | 데이터·제약 |
| --- | --- |
| `bundles` | 번치·생성자·상태·제목·공개 범위·날짜·전체 revision·필드 버전·생성/수정/발행 시각 |
| `bundle_photos` | 번들·원본 Photo·이미지 자산·순서·추가자/시각·캡션·캡션 버전/수정자 |
| `bundle_participants` | 번들·회원·참여 시각. 번들·회원 유일성 |
| `bundle_comments` | 번들·작성자·내용·버전·작성/수정 시각. 번들·작성자 유일성 |
| `bundle_edit_leases` | 대상 영역/사진·소유 회원/세션/화면·편집권 토큰·편집권 버전·만료 시각 |
| `bundle_requests` | 생성/사진 변경/발행 요청 키·입력 fingerprint·결과 번들 ID·적용 revision |

- 참여자는 발행 시 고정해 기여 기록으로 사용한다. 별도 Contributor 테이블은 만들지 않는다.
- 번들 사진은 ImageAsset을 직접 참조한다. 발행 후 원본 Photo 삭제 시 원본 FK만 비워지고 사진·캡션·순서는 유지된다.
- 요청 기록에는 삭제된 번들의 제목·코멘트·캡션을 보관하지 않는다.
- 번들이 삭제돼도 생성 요청의 결과 식별은 남겨 재시도로 초안이 복원되지 않게 한다.
- 추천 후보 FK·위치 컬럼·일반 알림 모델은 해당 후속 이슈에서 추가한다.

### 기능 구현 순서

이 순서는 한 이슈 안의 구현 순서이며 별도 기능 이슈로 나누지 않는다.

1. 생성·참여·초안 폐기와 공통 권한
2. 제목·공개 범위·날짜·코멘트·캡션·사진 구성 REST
3. 필드 버전·사진 이동·요청 중복 처리
4. 편집권·STOMP 인증/구독·실제 변경 이벤트
5. 발행·목록·상세·Stage
6. 발행 후 수정·삭제·Photo 최종 삭제 연결
7. 사진함 실제 연동과 회귀 검증

### REST 계약

기본 경로는 `/api/v1/bunches/{bunchId}/bundles`다.
기존 `success / data / error` 응답을 유지한다.

| 메서드·상대 경로 | 입력·동작 |
| --- | --- |
| `POST /` | 순서 있는 photoIds, 요청 키. 직접 생성 |
| `GET /` | DRAFT/PUBLISHED·page·size로 목록 조회 |
| `GET /summary` | 작성 중 수·발행 수·Stage |
| `GET /{id}` | 내용·버전·권한·발행 불가 사유·현재 편집권 |
| `PUT /{id}/title` | 제목·기대 버전·초안 편집권 |
| `PUT /{id}/visibility` | PUBLIC/PRIVATE·기대 버전 |
| `PUT /{id}/date` | 날짜/null·기대 버전·초안 편집권 |
| `PUT /{id}/comments/me` | 본인 코멘트·기대 버전 |
| `POST /{id}/participants` | 현재 번치 멤버 추가 |
| `DELETE /{id}/participants/{participantId}` | 해당 참여 연결 제외 |
| `POST /{id}/leave` | 본인 참여 종료. 생성자는 초안 삭제 |
| `POST /{id}/photos/changes` | 추가 Photo ID·제거할 번들 사진 ID의 차이 적용 |
| `POST /{id}/photos/{bundlePhotoId}/move` | 앞뒤 기준 사진으로 이동 |
| `PUT /{id}/photos/{bundlePhotoId}/caption` | 캡션·기대 버전·초안 사진 편집권 |
| `POST /{id}/publish` | 확인한 전체 revision·요청 키 |
| `DELETE /{id}` | 초안 폐기 또는 발행본 삭제 |

- 사진별 경로는 원본 Photo ID가 아닌 번들 사진 ID를 사용한다.
- 목록은 기본 20개·최대 50개다. 작성 중은 생성 시각, 발행본은 발행 시각 내림차순이며 ID로 동률을 정렬한다.
- 이 조회 API는 현재 번치 멤버용이다. 외부 Feed·팔로워 조회를 추가하지 않는다.
- 본 작업의 생성 경로는 직접 선택이다. 추천 출처 입력은 #26에서 추가한다.
- 날짜 수동 설정과 사진 날짜 기반 최대 3개 추천 칩을 포함한다. 장소 설정은 #27 범위다.
- 생성·사진 구성 변경·발행은 요청 키로 중복을 막는다. 같은 키·다른 입력은 409, 삭제된 결과 재시도는 404다.
- 텍스트 저장은 기대 버전으로 중복/오래된 변경을 막고 충돌 시 최신 값·버전을 반환한다.

### 저장·사진 이동

- 제목·공개 범위·날짜 버전, 사진별 캡션 버전, 작성자별 코멘트 버전을 구분한다.
- 전체 revision은 영속 내용이 실제로 바뀔 때만 올린다.
- 제목/코멘트/캡션 길이는 40/400/200 grapheme이며 본인 코멘트만 수정할 수 있다.
- 초기 공개 범위는 미선택이다. 생성은 번치 멤버 2명 이상·초안 최대 10개·사진 1~20장이다.
- 사진 선택 적용은 추가/해제 차이만 반영한다. 병합 결과가 0장·21장 이상이면 전체 변경을 거부한다.
- 사진 이동은 놓는 순간 최신 순서에 적용한다. 전역 revision 일치만으로 이동을 막지 않는다.
- 기준 사진 삭제·모순 또는 해당 사진의 타인 편집권이 있으면 이동을 거부한다.
- 갤러리 업로드 성공 후 번들 연결이 실패해도 사진함 원본을 지우지 않는다.

### 편집권·STOMP

- WebSocket 경로는 `/ws`이며 CONNECT 헤더에서 JWT·기존 인증 세션을 검증한다.
- 구독·명령마다 번치/번들 접근·참여 권한을 검사하고 기존 이탈자의 연결을 차단한다.
- 허용 Origin은 환경 설정으로 제한하고 인증 토큰을 URL·로그에 넣지 않는다.
- 편집 시작·heartbeat·편집 종료를 STOMP 명령으로 제공한다.
- 제목·날짜·사진별 편집권을 DB에서 관리한다. 코멘트에는 타인 잠금을 두지 않는다.
- 편집권 토큰은 소유 연결에만 전달한다. 다른 멤버에게는 대상·편집자·만료·편집권 버전만 전달한다.
- 5초 heartbeat, 마지막 유효 갱신 후 15초 만료, 1분 무입력 시 저장·종료를 적용한다.
- 드래그 시작에는 편집권을 얻지 않는다. 캡션 편집 시 해당 사진의 캡션·제거·직접 이동을 막는다.
- REST 저장은 소유자·토큰·만료·내용 버전을 같은 DB 트랜잭션에서 검사한다.
- 재획득은 새 토큰으로 식별하고 이전 요청은 거부한다.

내용 이벤트는 `bundleId / revision / requestId / type / 변경값`을 포함한다.

- 필드 변경: 저장 값과 필드 버전
- 사진 변경: 최대 20장 구성·순서·관련 캡션 버전
- 참여 변경: 참여 목록과 삭제한 코멘트 정보
- 코멘트 변경: 작성자·저장 내용·버전
- 상태 변경: 발행·삭제·접근권한 상실
- 편집권 변경: 내용 revision과 별개인 편집권 상태

커밋 후 실제 변경값을 전송한다. 중복·이전 revision은 재적용하지 않고 최초 접속·재연결·revision 누락 시 REST로 재조회한다.
heartbeat 응답에도 현재 revision을 제공한다. 프론트는 다른 사람의 이벤트를 적용하면서 본인의 미저장 입력을 유지한다.

### 발행·발행 후 수정·삭제

- 발행은 조건 검증·ImageAsset 참조 확보·참여자 고정·상태 변경을 한 트랜잭션으로 처리한다.
- 별도 파일 복사·외부 업로드·발행 작업 큐를 만들지 않고 발행 처리 중 상태를 장기 작업으로 남기지 않는다.
- 발행 시 생성자/참여 관리자 권한, 사진·제목·공개 범위·참여자·전원 코멘트·확인 revision을 검증한다.
- 발행 후 늦은 초안 저장은 거부한다.
- 발행본의 생성자/관리자는 공용 내용을 수정·삭제하고, 코멘트는 작성자만 수정한다. 코멘트를 비우거나 삭제할 수 없다.
- 발행본 수정에는 초안용 편집권을 요구하지 않는다.
- 기존 발행 사진은 Photo 삭제 후에도 유지하고 수정할 수 있다. 새로 넣는 사진만 현재 Photo를 검증한다.
- Stage는 현재 발행 수 0/4/8/12/16개로 계산하며 삭제 시 하락한다. Stage 자체는 저장하지 않는다.
- Photo 최종 삭제는 초안 사진·캡션을 정리하고 0장 초안을 삭제하되 발행본을 유지한다.

## 5. #25 번치 나가기·내보내기

### 스키마·API

- Membership 상태·역할을 변경 가능하게 하고 `last_activity_at`, `left_at`, `role_granted_by`를 기록한다.
- 현재 멤버·역할 목록, 나가기 미리보기·본인 나가기·관리자 내보내기를 제공한다.
- 대상은 Membership ID로 식별하여 재참여한 새 소속에 과거 요청이 적용되지 않게 한다.
- 일반 관리자 권한 부여/회수 API와 계정 탈퇴 API는 포함하지 않는다.

### 관리자·초대

- 다른 관리자가 있으면 나갈 수 있다.
- 마지막 관리자는 직접 후임을 선택하거나 자동 선정한다.
- 자동 순위는 현재 발행 기여 횟수 내림차순 → 실제 활동 최신순 → 가입일 오름차순 → Membership ID다.
- 활동이 없으면 활동 우선순위를 낮추고 가입일·ID로 결정한다.
- 실행 시 재계산한 자동 후임이 미리보기와 다르면 409로 재확인한다.
- 혼자인 관리자의 나가기는 차단하고 번치 삭제로 안내한다. 새 번치 삭제 API를 이 범위에 추가하지 않는다.
- 내보내기는 기존 초대 링크·코드를 폐기하고 새로 발급한다. 이전 성공 참여 요청으로 소속을 복원하지 않는다.
- 재참여는 새 Membership으로 처리한다.

### 데이터 정리·실패 처리

- 활동 시각은 업로드·초안 편집·코멘트 저장 성공 시 갱신한다. 접속·조회·heartbeat·화면 전환은 제외한다.
- 생성자가 이탈하면 그 생성자의 작성 중 초안을 삭제한다.
- 다른 초안에서는 이탈자의 참여·코멘트·편집권을 제거한다.
- 공동 업로더가 남으면 Photo를 유지하고 최종 업로더 제거 시 Photo와 초안 사진을 정리한다.
- 발행본의 이미지·캡션·기여 기록·코멘트 본문은 유지한다.
- 소속·후임·초대·Photo·초안 DB 변경은 한 트랜잭션이다. 하나라도 실패하면 전체 롤백한다.
- 외부 이미지 삭제만 커밋 후 수행하고 실패를 로그로 남긴다. DB 정리 재시도 작업은 만들지 않는다.
- 기존 STOMP 연결에도 권한 상실을 반영한다.
