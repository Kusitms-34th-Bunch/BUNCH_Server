# BUNCH 개발 규칙

## 1. 개발 순서와 기준

**요구사항·Spec 확인 → 이슈 → 작업 브랜치 → 테스트·구현 → 문서 갱신 → 검증 → PR·리뷰 → 머지**

- 제품 범위·우선순위·원문 우선순위는 [PRD](PRD.md), 기능 동작과 계약은
  [인증 Spec](specs/auth.md)과 [온보딩 Spec](specs/onboarding.md)을 따른다.
- 관련 Spec에 정상·실패 동작과 완료 조건을 정한 뒤 기능 구현에 착수한다.
  미정 항목과 충돌하는 동작을 추측해서 구현하지 않는다. 무관한 작업은 계속할 수 있다.
- 제품의 확정 요구사항, 제안, 미정과 현재 구현 상태를 분리해서 기록한다.
- 기능 이슈에는 기능 ID·Spec·완료 조건을 연결한다. 브랜치·커밋·PR·머지는
  [CONTRIBUTING](../CONTRIBUTING.md)을 따른다.
- 초기 공통 기반과 문서 정비는 `00` 예약 번호를 쓰는 부트스트랩 예외다.
  이 예외를 이후 기능 개발의 이슈·검증 생략 근거로 사용하지 않는다.

## 2. 구현·API·데이터 규칙

- Kotlin 1.9.25, Spring Boot 3.5.4, JDK 21과 루트 단일 Gradle 모듈을 유지한다.
- 기본 패키지는 `com.bunch`다. `global`에는 도메인과 무관한 공통 처리만 둔다.
  인증은 `auth`, 현재 개인 계정·소셜 식별자 영속성은 `member`가 담당한다.
  새 도메인은 실제 기능을 개발할 때 추가하며 빈 계층을 미리 만들지 않는다.
- 기능 코드는 도메인 이름 디렉터리를 먼저 두고, 그 아래를 `controller`, `service`,
  `domain`, `dto`로 분리한다. 각 계층은 필요한 코드가 생길 때 생성한다.
  `global`의 공통 설정·처리는 도메인 계층과 구분한다.

  ```text
  com/bunch/<도메인 이름>/
  ├── controller/  # HTTP 요청·응답 처리
  ├── service/     # 유스케이스 실행·트랜잭션 관리
  ├── domain/      # 엔티티·값 객체·도메인 규칙
  └── dto/         # 요청·응답 데이터 모델
  ```

- 기존 공통 `success / data / error` 응답과 예외 규칙을 유지한다.
  공개 API 변경 시 관련 Spec의 입력·출력·권한·오류·호환성 영향과 테스트를 갱신한다.
- 검증한 제공자 식별자로만 계정을 찾는다. 이메일 자동 병합을 하지 않는다.
- 가입 완료 여부, 대상 번치 소속·역할과 하위 데이터 소속은 서버에서 검증한다.
  앱의 버튼 비활성화만으로 권한·중복·정원 조건을 보장하지 않는다.
- 스키마 변경은 새 Flyway 마이그레이션으로 관리하고 적용된 파일은 수정하지 않는다.
  JPA `ddl-auto: validate`를 유지한다. 아직 없는 기능을 위한 가짜 초기 테이블은 만들지 않는다.
- 중복·동시 요청·트랜잭션 경계가 중요한 기능은 해당 Spec에서 보장 조건을 정하고
  실제 PostgreSQL·Redis로 검증한다.
- 운영에서 Swagger를 기본 비활성화하고 광범위한 credential CORS를 사용하지 않는다.
- 새 의존성은 명시적 요청 없이 추가하지 않는다. 실제 비밀값·원문 토큰·Authorization
  헤더는 로그·문서·커밋에 남기지 않는다. 운영 저장소에서 테스트하지 않는다.

## 3. 정리·리팩토링

- 변경 전 목적·범위·유지 동작·검증 방법을 담은 정리 계획을 쓴다.
- 유지 동작에 테스트가 없으면 회귀 테스트를 먼저 확보한다.
- 삭제·재사용·기존 경계 수정을 우선하고 한 번에 하나의 문제를 다룬다.
- 관련 없는 개선을 섞지 않고 작은 변경 단위로 검증한다.

## 4. 검증

[README](../README.md)에 따라 실제 PostgreSQL·Redis와 테스트 DB를 준비한다.

```bash
DB_URL=jdbc:postgresql://localhost:5432/bunch_test ./gradlew clean build
```

| 변경 범위 | 필요한 증거 |
| --- | --- |
| 공통 인프라 | 컴파일·build, 공통 응답·오류·로깅, 실제 DB·Redis 연결, 앱 기동 |
| 인증 | 정상·실패 API, 제공자별 claims·nonce, 토큰 재사용·갱신·로그아웃 |
| 영속성·동시성 | Flyway 적용·재실행, JPA validate, 유일성·동시 요청·원자성 |
| 계약·문서·템플릿 | 원문 기능 ID 대조, 정책 일치, 로컬 링크, YAML, staged diff |
| 앱 연동 | 실제 SDK·WebView·권한·링크 복귀 수동 검증. 자동 테스트와 별도로 기록 |

- 변경과 관련된 테스트를 실행하고 최종 코드 변경에는 전체 build를 수행한다.
- 현재 별도 lint·정적 분석 도구는 구성하지 않았다. 도입하면 명령과 CI도 갱신한다.
  Kotlin 컴파일이나 문서 링크 점검을 별도 정적 분석 통과라고 보고하지 않는다.
- 실제 SDK 수동 검증 전에는 전체 제공자 연동 완료라고 주장하지 않는다.
- 실행 결과는 PR과 완료 보고에 남긴다. 제품 계약에는 테스트 기준과 남은 검증만 두고
  실행 로그를 계속 누적하지 않는다. 결정 이유는 해당 Spec과 필요한 Lore trailer에 남긴다.

## 5. 필수 완료 조건

아래 조건은 모든 변경에 적용하며 충족하지 못하면 완료로 처리하지 않는다.

| 조건 | 이유 | 검증 방법 / 실패 기준 |
| --- | --- | --- |
| 관련 테스트·build 성공 | 회귀 방지 | 실제 결과 확인. 실패·결과 미확인 시 미완료 |
| API·데이터 계약 일치 | 클라이언트·DB 호환성 | Spec·테스트·새 마이그레이션 대조. 불일치 시 미완료 |
| 변경 범위·협업 규칙 준수 | 리뷰·변경 소유권 보장 | staged diff·커밋·브랜치 점검. 무관한 변경 혼입 시 미완료 |
| 비밀값·로컬 기록 제외 | 자격 증명·작업 정보 보호 | staged diff·추적 파일 검사. 실제 비밀값 포함 시 미완료 |
| 검증 한계 보고 | 완료 주장 정확성 | 명령·실제 결과·생략 사유·위험 기록. 근거 없는 통과 주장은 미완료 |

환경·앱 준비가 필요한 수동 검증은 미검증 사유와 후속 조건을 기록한다.
수동 검증이 남아 있으면 해당 연동까지 완료됐다고 표시하지 않는다.

## 6. 권장 사항

아래는 구현 판단을 돕는 선호 사항이며 별도 도구가 강제하는 완료 조건은 아니다.

- 도메인별 구조, 작은 diff, 명확한 이름을 선호한다.
- 새 추상화는 반복·경계 문제가 확인된 경우에만 도입한다.
- 테스트는 내부 구현의 복제보다 외부에서 관찰 가능한 동작을 검증한다.

## 7. 완료 보고

결과, 변경 파일·단순화 내용, 검증 명령과 실제 결과, 생략한 검증과 이유,
잔여 위험·후속 작업을 적는다. 정확한 토큰 사용량이 없으면 확인 불가로 표시한다.
