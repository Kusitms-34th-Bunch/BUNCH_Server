# BUNCH PRD

## 문서 기준·출처 우선순위

이 문서는 전체 제품 PRD와 로그인·온보딩 상세 명세를 통합합니다. 「확정」은 제품 정책의 상태이며 구현 완료가 아닙니다. 「제안·권장·예시」는 승인된 결정으로 승격하지 않고, 「미정·확인 필요·미해결」은 추가 합의가 필요한 항목입니다. 모든 기존 기능 ID와 우선순위를 유지합니다.

| --- | --- | --- |
| 1 | 승인된 문서 운영 기준 | 문서 소유 범위, 충돌 우선순위, 상태 구분, 일정·구현 상태 표시 |
| 2 | [번치 5장 시트](https://docs.google.com/spreadsheets/d/1ScziF7WoYLHRiC_UYJBkKsi0jL6KKQJD2TNDzW1QGfU/edit?gid=2104162394#gid=2104162394), 2026-10-29 사용자 승인 | 5.1~5.12의 47개 항목과 승인 보완 정책. 충돌하는 기존 역할·권한·Stage·소셜·알림 정책보다 우선 |
| 3 | `BUNCH_기능명세서_로그인온보딩.md` 전체(1.1~1.5, 2.1~2.7) | 로그인·개인 프로필·번치 생성·초대·진입 흐름의 충돌 시 우선 |
| 4 | 첨부 `Pasted text.txt` 전체(1~10절) | 전체 기능·우선순위·객체·관계·역할·상태·공통 DB 제약·제안·미정의 기준 |

원문 내부의 모순은 U 항목으로 추적하며 날짜가 더 늦다는 이유만으로 임의 해결하지 않습니다. 원문 10/10~10/16은 정책 변경 이력이며 연도·실제 개발 일정은 확인되지 않았습니다. 외부 정책·스토어 요건 표기는 제공 원문의 요구 배경을 보존한 것으로, 이번 작업에서 최신 외부 정책을 검증했다는 뜻은 아닙니다.

상세 문서는 [인증](specs/auth.md), [로그인·온보딩](specs/onboarding.md)으로 연결합니다.
번들의 동작·권한·제약과 사진함 연동은 [번들 Spec](specs/bundle.md)을 기준으로 합니다.
번치 홈·관리·소셜의 기능별 동작과 API·저장 계약은 [번치 Spec 색인](specs/bunch.md)을 따릅니다.
알림·푸시는 [알림 Spec](specs/notification.md)·[알림 API](specs/notification-api.md)·[알림 스키마](specs/notification-schema.md)가 소유합니다.
번들 고유 동작은 번들 Spec을 따르며 대체된 과거 정책보다 각 도메인의 확정 계약을 우선합니다.
2026-10-31 번치 5장 원문과 사용자 답변으로 외부 실제 Stage, 직접 나가기·내보내짐 후 재참여, 남은 발행 기록 표시 복구, 일반 멤버로 재참여를 확정했습니다. 기능 구현·자동 검증·앱 수동 검증·출시는 각각 구분합니다.
2026-10-17 사용자 합의로 확정한 미정 정책과 API는 [이슈 #5 계약](specs/login-onboarding-api.md)을 따릅니다. 해당 결정이 원문의 미정·제안보다 우선하며 구현 완료를 의미하지는 않습니다. 요청·응답·경로·오류 코드·토큰 구조 등 API 계약은 이 PRD에서 새로 정하지 않습니다. 기존 인증 기반은 dev에 커밋되어 있으며 제품 가입·온보딩 전체의 출시 완료를 뜻하지 않습니다.

## 1. 서비스 한 줄 정의

BUNCH는 가까운 사람들이 각자 찍은 사진을 하나의 **Bunch(그룹) 공동 사진함**에 모으고, 이를 경험 단위의 **Bundle(그룹 게시물)**로 함께 완성해 그룹의 기록과 프로필(**뭉치**)을 쌓아가는 그룹 아카이빙 서비스입니다.

**핵심 흐름**

```
사진 업로드 → 공동 사진함 저장
  → (A) 번들 만들기 화면에서 직접 선택  또는  (B) 시스템이 제안한 추천 번들 「적용하기」 후 조정
  → 공동 Bundle Draft (여러 멤버가 함께 편집)
  → 초안을 만든 사람 또는 참여 중인 관리자가 최종 발행 → Bundle Archive 축적 → 뭉치 모습 변화 → 피드 연결 (공개 번들)
```

**백엔드가 꼭 알아야 할 구분 4가지**

- **사진 업로드 ≠ Bundle 작성.** 업로드는 사진함 저장으로 끝납니다. Bundle을 만들지 않고 사진만 쌓아두는 것도 정상 사용입니다.
- **자동 그룹핑(번들 후보)은 보조 경로**입니다. 직접 선택(A)과 후보(B) 어느 쪽으로 만들어도 같은 Draft 구조로 합류합니다.
- **시스템은 절대 자동 발행하지 않습니다.** 발행은 항상 초안을 만든 사람 또는 그 초안에 참여 중인 관리자의 명시적 행동입니다.
- **기록의 주체는 Bunch**입니다. 개인은 Contributor(기여자)로 표시됩니다.

## 2. 플랫폼·개발 전제

- 웹 코드로 만들고 WebView로 감싸 **iOS 앱으로만 배포**합니다(10/12 변경). Android 앱과 모바일 웹(브라우저) 로그인·사용은 없습니다. 웹으로 남는 것은 로그인 없이 보는 **웹 초대장** 하나이고, 앱이 있으면 앱으로, 없으면 App Store로 보냅니다.
- 로그인: **카카오·Google·Apple 소셜 로그인** 3가지를 사용합니다(이메일/비밀번호 없음).
    - 같은 사람이 서로 다른 제공자로 가입하면 별도 계정으로 취급합니다(자동 병합 없음, 계정 연결 기능 없음, 확정).
    - Apple 로그인은 사용자가 이메일을 가릴 수 있고(중계 이메일), 이름은 최초 로그인 때 한 번만 전달됩니다. 계정 식별은 이메일이 아닌 제공자 고유 ID로 합니다.
- 앱스토어 출시 시 영향 (설계에 미리 고려)
    - 앱에서 가입할 수 있으면 **앱 안에서 계정 삭제** 기능이 필수입니다.
    - **로그인 방식 (10/12 확정):** 앱에서 카카오·Google·Apple **공식 SDK**로 로그인 창을 띄우고, 받은 **ID 토큰을 서버가 확인**합니다(OIDC 방식). 서버가 인증 결과의 유효성을 확인하고 제공자와 제공자 고유 ID로 User를 식별합니다. 구체적인 계약은 [인증 명세](specs/auth.md)를 따릅니다. 웹 브라우저로 이동했다 돌아오는 방식은 쓰지 않습니다. 카카오는 개발자 설정에서 OpenID Connect를 켭니다.
    - 초대 정보는 앱이 로그인·가입 과정에 보관하고, 가입 완료 후 참여에 사용합니다. 인증 단계에서는 참여하지 않습니다.
    - 상세 명세는 Apple 로그인 회원 탈퇴 시 Apple 연결 해제(토큰 취소)를 요구합니다. 구체적인 탈퇴·제공자 연동 방식은 탈퇴 명세에서 정의해야 하며 미정입니다.
- **Feed·팔로우·좋아요·댓글·신고·차단은 UT 이후 전시회 전까지 구현**합니다. 앱 출시를 하므로 신고·차단은 필수입니다(App Store 1.2). 초기 DB 설계에 포함해 주세요.
- **하단 탭 4개 (10/14):** 왼쪽부터 피드 · 사진함 · 번치 · MY. 사진함은 지금 보고 있는 Bunch의 사진함을 바로 여는 탭입니다(탭 안에 Bunch 전환 없음). 알림 종은 번치 탭에만 있습니다.
- 실시간 반영은 **Bundle Draft 화면에만** 필요합니다(다른 멤버의 사진 추가·순서 변경 등). 나머지 화면은 진입·새로고침 시 갱신으로 충분합니다.
- 사진 업로드 이후 처리(촬영 시각·위치 추출, 동네 이름 변환, 번들 후보 계산. 썸네일은 만들지 않음)는 **업로드 응답과 분리된 비동기 처리**를 전제로 합니다.

## 3. 핵심 데이터 객체와 관계

### 3-1. 확정된 객체

| 객체 | 설명 | 주요 관계 | 보관해야 할 정보 (컬럼이 아닌 "정보" 수준) |
| --- | --- | --- | --- |
| **User** | 개인 계정 | Membership을 통해 여러 Bunch에 소속 (N:M) | 소셜 제공자(카카오/Google/Apple) + 제공자 고유 ID, 닉네임(필수), 프로필 사진(선택), 출생연도·성별(선택, 10/12 변경), 약관 동의 이력(버전·일시), 가입 상태(가입 중/완료), 마지막으로 사용한 Bunch |
| **Bunch** | 그룹 계정이자 모든 기록의 주인 | Membership, Photo, 번들 후보, Bundle, 초대 링크를 가짐 | 이름(필수 1~12자), 프로필 사진(선택, 없으면 선택한 뭉치 유형의 기본 이미지), 한 줄 소개(필수 1~50자), 공개 범위(Public/Private, 미선택 시작·명시적 선택 필수), 분위기에 연결된 뭉치 유형(4종 중 1개, 생성 후 변경 불가). 뭉치 Stage는 현재 발행 Bundle 수로 계산하며 별도 저장하지 않음. 삭제는 영구 삭제 |
| **Membership** | User와 Bunch의 연결 + 역할 | User N:1, Bunch N:1 | 역할(메인 관리자 OWNER / 공동 관리자 CO_OWNER / 일반 멤버 MEMBER), 관리자 권한을 받은 시각·부여한 사람, 가입일, 최근 활동 시각, 상태(활성/나감/내보내짐) |
| **초대 링크** | Bunch 참여용 링크 | Bunch N:1, 생성한 멤버 | 추측 불가능한 링크 토큰, 초대 코드(링크가 끊길 때 보조 수단, 확정), 생성자, 만료 시각(7일), 폐기 여부. Bunch당 유효한 것 1개, 멤버를 내보내면 새로 발급 |
| **Photo** | 사진함에 쌓이는 가장 작은 기록 단위 | Bunch N:1, 올린 사람 목록을 통해 User N:M(각 업로드 기록은 User N:1), Draft·Bundle에서 참조됨 | 이미지 파일 1장(긴 변 2560px. 원본·썸네일은 따로 두지 않음, 확정), 업로더, 촬영 시각(없을 수 있음. 올린 사람이 날짜를 바꾸면 '사용자 지정'으로 표시해 EXIF 값과 구분, 10/12), 촬영 위치(정밀 좌표 대신 동네 단위: 동네 이름·동네 중심 좌표, 없을 수 있음), 업로드 시각, 파일 해시(중복 확인용), 처리 상태. **올린 사람은 여러 명일 수 있음(10/15):** 같은 사진을 다른 멤버가 또 올리면 새로 저장하지 않고 합치며 올린 사람 목록(사람·시각)에 추가. 한 명이 삭제하면 목록에서만 빠지고, 목록이 비면 Photo 삭제. 삭제하면 휴지통 없이 바로 삭제(복구 불가). 단 발행 Bundle이 쓰는 이미지 파일은 남김 |
| **사진함** | Bunch의 공동 사진 저장 공간 | 독립 객체가 아니라 "Bunch에 속한 Photo 목록" | - |
| **번들 후보 (Bundle Candidate)** | 같은 날(또는 같은 여행)에 찍은 사진을 시스템이 묶어 제안한 것 | Bunch N:1, Photo N:M | 포함 사진, 대표 날짜·장소, 상태(제안됨/변환됨/소멸), 사용자별 마지막 확인 시각(Home "새로운 후보" 표시용) |
| **Bundle** | Draft부터 발행까지 하나의 생애주기를 갖는 그룹 게시물 | Bunch N:1, Bundle 사진 1:N, 멤버별 코멘트 1:N, Contributor N:M | 상태(작성 중/발행 처리 중/발행됨. 폐기·삭제는 상태가 아닌 영구 삭제), 제목, 공개 범위(공개/비공개, 기본값 공개, 10/15), 생성자(참여 멤버 추가·제외·발행·폐기 권한 판단에 사용. 생성자 이탈 시 작성 중 초안은 삭제하며 인계하지 않음), 생성 경로(직접/후보), 발행 시각, 변경 버전 |
| **Bundle 참여 멤버** | Draft를 만들 때 고른 사진을 올린 현재 Bunch 멤버로 자동 결정(만든 사람 항상 포함, 별도 선택 단계 없음, 10/11 확정). 이후 참여 멤버는 추가, 생성자 또는 참여 중인 관리자는 제외(번들 Spec). 발행 시점의 참여 멤버가 이 Bundle의 주인 | Bundle N:1, User N:1 (Bundle–멤버 N:M) | 참여 멤버, 참여 멤버가 된 시각(24·72시간 리마인드 기준). 만든 사람은 자동 포함. **추가는 참여 멤버, 제외는 생성자 또는 참여 중인 관리자만 가능.** 생성자는 타인이 제외 불가, 현재 Bunch 멤버만 추가 가능, 참여하지 않은 관리자도 스스로 참여할 수 없음. 처음에 만든 사람 1명뿐이어도 Draft는 만들어지고 발행만 막힘. 발행에는 최소 2명이 필요하며 생성자 외 참여자는 스스로 나갈 수 있음. 추가된 멤버는 알림을 받고 코멘트를 써야 발행 가능. 제외된 멤버는 알림을 받고 코멘트는 삭제, 그 멤버가 추가한 사진은 남음. 참여 멤버가 Bunch를 나가면 자동으로 빠지고, 1명만 남으면 발행을 막고 만든 사람에게 "참여 멤버가 부족해요. 함께할 멤버를 추가해 주세요" 안내. 참여 멤버 전원이 멤버별 코멘트를 써야 발행 가능. 참여 멤버가 아닌 Bunch 멤버는 Draft를 볼 수만 있음 (확정) |
| **Bundle 사진 (Bundle과 Photo의 연결)** | Bundle에 들어간 사진 한 장. 같은 Photo라도 Bundle마다 따로 존재 | Bundle N:1, Photo N:1 (Bundle–Photo N:M을 잇는 연결) | 순서, Draft에 추가한 사람·시각, 캡션(최대 200자, 줄바꿈 허용, 10/15 변경, 내용·마지막 수정자·수정 시각·버전). 한 Bundle에 같은 Photo는 1번만. Draft에서 사진을 빼면 캡션과 함께 사라짐. 발행 후 사진함 원본이 삭제돼도 유지 |
| **멤버별 코멘트** | Bundle에 각 멤버가 남기는 짧은 글 | Bundle N:1, 작성자 N:1 (Bundle당 멤버 1개) | 작성자, 내용(최대 400자, 줄바꿈 허용, 10/15 변경), 작성·수정 시각. 각 멤버 고유 영역이라 작성자만 수정·삭제 가능 (관리자도 수정·삭제·숨김 불가). 발행 필수 조건이라 발행 후에는 수정만 가능하고 비우거나 삭제할 수 없음 |
| **뭉치 Stage** | Bunch 프로필 캐릭터의 단계 | Bunch 1:1 | 발행된 Bundle 수로 결정. Bundle을 삭제하면 그만큼 단계가 내려감(항상 현재 발행 Bundle 수로 다시 계산, 별도 저장 불필요). 기준값(Threshold)은 설정으로 관리하며 0/2/6/10개에서 1~4단계 |
| **알림** | 앱 내 알림 (Bell 아이콘) | 수신자(User) N:1, 관련 Bunch·Bundle 참조 | 종류, 수신자, 관련 대상, 읽음 여부, 생성 시각(30일 보관·최대 100개 표시), 발생 당시 문구·이동 대상, 푸시 전송 대기·결과. 푸시를 위해 User별 기기 푸시 토큰(여러 기기 가능)과 알림 수신 설정도 저장 |
| **팔로우** | Bunch가 다른 Bunch를 팔로우 (Bunch → Bunch) | 팔로우하는 Bunch N:1, 대상 Bunch N:1 | 팔로우하는 Bunch, 대상 Bunch, 상태(요청 중/승인됨. 공개 Bunch는 바로 승인됨), 요청·승인 시각, 실행한 멤버·승인한 멤버(내부 기록용, 화면 비노출). 같은 쌍 중복 불가, 자기 Bunch 팔로우 불가 |
| **좋아요** | Bunch가 Bundle에 누르는 반응 (Bunch 단위, 우리 Bunch의 Bundle에도 가능) | Bundle N:1, 누른 Bunch N:1 | Bundle, 누른 Bunch, 시각, 실행한 멤버(내부 기록용, 화면 비노출). Bunch당 Bundle 1회 |
| **댓글** | Bunch가 Bundle에 남기는 글 (Bunch 단위, 우리 Bunch의 Bundle에도 가능) | Bundle N:1, 작성 Bunch N:1 | 작성 Bunch, 내용(1~200자), 작성 시각, 상태(정상/작성 Bunch 삭제/대상 Bundle의 Bunch 관리자 삭제/운영 숨김), 실행한 멤버(내부 기록용, 화면 비노출) |
| **신고** | Bunch가 다른 Bunch의 콘텐츠·프로필을 신고 (Bunch 단위) | 신고한 Bunch N:1, 대상(Bundle·댓글·Bunch) | 신고한 Bunch, 대상 종류·대상, 사유, 상세 내용(기타 OTHER는 필수, 최대 200자), 처리 상태(접수/검토 중/조치/기각), 처리자·처리 시각, 실행한 멤버(내부 기록용). 같은 Bunch가 같은 대상을 첫 신고 시각부터 24시간 동안 최대 2번 신고할 수 있으며 멤버 전체의 접수를 합산한다. 허용된 재신고도 매번 새 신고로 접수하고 운영 검토도 건마다 진행한다 |
| **차단** | Bunch가 다른 Bunch를 차단 (Bunch 단위) | 차단한 Bunch N:1, 대상 Bunch N:1 | 차단한 Bunch, 대상 Bunch, 시각, 실행한 멤버(내부 기록용). 같은 쌍 중복 불가, 자기 Bunch 차단 불가 |
| **Feed** | 다른 Bunch의 공개 Bundle을 보는 화면 | 독립 객체가 아니라 "발행·공개 조건으로 조회한 Bundle 목록" | 별도 저장 없음. Bundle(발행 여부·공개 범위), Bunch(공개 범위), 팔로우(팔로잉 구간), 차단·신고·운영 숨김(제외 대상), 좋아요·댓글(개수)을 요청 때마다 조합해 만듦. 추천 알고리즘·Feed 캐시·읽음 위치는 MVP 범위 밖 |

### 3-3. 관계 요약

```
User ──(N:M, Membership: OWNER(메인 1명) | CO_OWNER | MEMBER)── Bunch
Bunch
 ├─ 초대 링크
 ├─ Photo (업로더 = User)  ← 사진함
 │    └─ 번들 후보 (Photo 묶음 제안, 시스템 생성)
 ├─ Bundle (작성 중 → 발행됨)
 │    ├─ Bundle 사진 (Photo 참조 + 순서 + 추가한 사람 + 캡션)
 │    ├─ 참여 멤버 (Draft 만들 때 사진 올린 멤버 자동 포함, 참여 멤버가 추가·생성자 또는 참여 중인 관리자가 제외, 발행 시점 멤버가 Bundle의 주인)
 │    └─ 멤버별 코멘트 (참여 멤버마다 1개, 작성자 소유)
 ├─ 뭉치 유형 (분위기 4종 중 1개, 생성 후 고정) + Stage (발행 Bundle 수에서 계산)
 └─ 팔로우 ──▶ 다른 Bunch (Bunch → Bunch)

Bunch ── 좋아요·댓글 ──▶ Bundle (다른 Bunch 것과 우리 Bunch 것 모두, Bunch 명의, 실행 멤버는 내부 기록만)
Bunch ── 신고 ──▶ 다른 Bunch의 Bundle·댓글·프로필
Bunch ── 차단 ──▶ 다른 Bunch
(좋아요·댓글·팔로우·신고·차단 모두 Bunch 명의. 실행한 멤버는 내부 기록만)
```

## 4-1. Feed·소셜 세부 규칙

Feed·팔로우·좋아요·댓글·신고·차단은 **UT 이후 전시회 전까지** 구현합니다. 구현 시점은 늦지만 관계·공개 범위 구조에 영향을 주므로 초기 DB 설계에 포함해 주세요. 표시한 "제안"은 Product Policy DB v1 기준 추천안입니다.

### Feed

- **구성 (확정): 탭 없이 하나의 Feed**로 보여줍니다. 인스타그램처럼 팔로우한 Bunch의 Bundle이 위에 먼저 나오고, 그걸 다 보면 그 아래로 공개 번치의 「공개」 Bundle이 이어집니다.
    - **① 팔로잉 구간:** 현재 선택한 Bunch가 팔로우한 Bunch들의 「공개」 Bundle(비공개 번치는 승인된 팔로우일 때만). 발행일 최신순 (제안).
    - **구분 안내:** 팔로잉 구간이 끝나면 "팔로우한 Bunch의 번들을 모두 봤어요" 같은 구분선을 보여주고 아래 구간으로 넘어갑니다 (제안).
    - **② 전체 공개 구간:** 공개 번치의 「공개」 Bundle 중 ①에 이미 나온 것을 뺀 나머지. 발행일 최신순 (제안).
    - 팔로우한 Bunch가 없거나 팔로잉 Bundle이 하나도 없으면 바로 ②부터 보여줍니다.
    - ①에 넣는 기간: 최근 14일 안에 발행된 팔로잉 Bundle만 위로 올립니다 (제안). 기간 제한이 없으면 오래 팔로우할수록 ②까지 내려가기 어려워지기 때문입니다. 14일보다 오래된 팔로잉 Bundle 중 공개 번치의 것은 ②에 섞여 나오고, 비공개 번치의 것은 그 Bunch 프로필에서 봅니다.
    - 팔로우가 Bunch 단위이므로, Bunch를 전환하면 ① 팔로잉 구간도 바뀝니다.
    - 백엔드 참고(제안): 두 구간을 하나의 무한 스크롤 목록처럼 연결합니다. 구간 전환과 페이지 조회의 구체 API 계약은 별도 합의합니다. 사용자별 "본 Bundle" 기록은 MVP에서 저장하지 않습니다.
- **노출 조건 (Bundle 공개 범위 공개/비공개 2단계, 10/15 확정):**
    - **공개 번치의 「공개」:** 누구의 Feed에나 나옵니다. 우리를 팔로우한 Bunch에게는 ① 팔로잉 구간에, 그 외에는 ② 전체 공개 구간에 나옵니다.
    - **비공개 번치의 「공개」:** 승인된 팔로워 번치의 ① 팔로잉 구간과 우리 번치 프로필에만 나오고, ② 전체 공개 구간에는 나오지 않습니다.
    - **「비공개」:** 우리 번치 멤버만 봅니다. Feed에 나오지 않습니다.
    - Bundle에는 「공개」/「비공개」만 저장하고, 실제로 누구에게 보이는지는 볼 때마다 번치 공개 범위로 계산합니다. 모든 판단은 서버에서 걸러야 합니다.
- **제외 대상:** 현재 선택한 Bunch의 Bundle, 현재 선택한 Bunch가 차단했거나 현재 Bunch를 차단한 Bunch의 콘텐츠, 현재 Bunch가 신고한 콘텐츠, 운영 숨김·삭제된 콘텐츠.
- **접근 (상세 명세 우선):** 가입 완료 User는 소속 Bunch가 **0개여도** 공개 번치의 「공개」 Bundle을 탐색할 수 있습니다. 이때 팔로잉 구간 없이 전체 공개 구간만 보여줍니다. 비회원·가입 중 User는 앱 Feed에 접근할 수 없습니다.
    - 소속 0개면 로그인·앱 실행 시 번치 시작 선택으로 안내하지만 닫기 또는 생성·참여 중단으로 공개 Feed에 진입할 수 있습니다. 마지막 Bunch에서 나감·내보내짐 이후에도 공개 Feed 열람 자격은 유지됩니다.
    - 좋아요·댓글·팔로우·신고·차단은 계속 현재 Bunch 명의이며 유효한 현재 Bunch와 활성 Membership이 필요합니다. 소속 0개 사용자에게 생성·참여를 유도하는 구체 UI는 미정입니다.
- **카드 정보:** 대표 사진, 제목, Bunch 이름·프로필 사진(10/12), 대표 날짜·장소명(동/구), 좋아요·댓글 수.
- **다른 Bunch 프로필 (확정):** Feed 카드의 Bunch 이름을 누르거나 링크로 들어갔을 때 보이는 그 Bunch의 프로필 화면입니다.
    - **공개 Bunch:** 이름, 뭉치, 소개, 공개 Bundle, 팔로워·팔로잉 수, 멤버 수, **멤버 명단**.
    - **비공개 Bunch:** 이름, 실제 단계의 뭉치, 소개, 팔로워·팔로잉 수, 멤버 수까지만 표시합니다. 번들 수(`publishedCount`)·본문·멤버 명단·팔로워/팔로잉 목록은 승인 전 비노출이며, 외부 응답의 `publishedCount`는 `null`입니다. 외부 프로필에는 번들 수 제목·내부 탭·가볼 곳 버튼을 두지 않습니다.
    - 비공개 Bunch의 **승인된 팔로워**에게는 공개 Bunch와 같은 범위(볼 수 있는 Bundle + 멤버 명단)를 보여줍니다.
    - **사진함·Draft는 어떤 경우에도 노출하지 않습니다.**
    - 멤버 명단에는 닉네임·프로필 사진·메인/공동 관리자 역할 배지를 보여주고 출생연도·성별·SNS 링크는 보여주지 않습니다. 역할 배지 근거는 [통합 PRD 정렬 커밋 `d898c21`](https://github.com/Kusitms-34th-Bunch/BUNCH_Server/commit/d898c21691201c1768f5f90e9e336d4cadd369e1)에 기록된 2026-10-29 제품 승인입니다. 명단의 멤버를 눌러도 개인 프로필로 이동하지 않습니다.
    - 차단 관계면 프로필 자체가 "볼 수 없는 Bunch예요"로 막힙니다.
- 검색은 MVP에서 제외.

### 팔로우 (Bunch → Bunch, 확정)

- 현재 선택한 Bunch 명의로 다른 Bunch를 팔로우합니다. 그 Bunch의 멤버라면 누구나 팔로우·취소할 수 있고, 화면에는 실행한 멤버 없이 Bunch로만 표시합니다. 실행한 멤버는 운영·악용 대응을 위해 내부에만 기록합니다.
- 현재 행동 번치 자신은 팔로우·차단·신고 불가(actorBunchId != targetBunchId). 본인이 함께 소속된 다른 번치에는 같은 외부 조회·팔로우·차단·신고 규칙을 적용합니다. 역할·공개 범위·차단 검사와 같은 쌍 중복 방지는 유지합니다.
- **공개 Bunch:** 바로 팔로우됩니다. 새 Bunch는 공개 범위를 미리 선택하지 않으며 생성자가 공개/비공개 중 하나를 명시적으로 선택합니다.
- **비공개 Bunch (인스타그램 비공개 계정처럼):**
    - 전체 공개 구간에 나오지 않고, 프로필에는 이름·뭉치·소개·팔로워/팔로잉 수·멤버 수만 보입니다.
    - 팔로우는 요청으로 보내고, 비공개 Bunch의 **멤버 누구나** 승인·거절할 수 있습니다. 요청이 오면 멤버 전원에게 알림을 보냅니다.
    - 승인된 팔로워 번치에게만 「공개」 Bundle이 보입니다.
    - 공개 → 비공개로 바꿔도 기존 팔로워는 유지되고, 비공개 → 공개로 바꾸면 대기 중인 요청은 모두 승인됩니다.
    - **공개 범위 변경:** 메인 관리자만 프로필의 다른 변경과 「저장하기」로 함께 반영합니다. 이전 별도 확인 모달은 폐기합니다. 공개 전환의 대기 요청 승인도 같은 트랜잭션에서 처리하며 승인·거절 경합은 먼저 확정된 결과를 유지합니다.
- Bunch Home의 팔로워·팔로잉 수는 Bunch 단위로 집계합니다.
- Bunch가 삭제되면 팔로우 관계도 함께 영구 삭제합니다.

### 좋아요 (Bunch 단위)

- 현재 선택한 Bunch 명의로 누릅니다. 그 Bunch의 멤버 누구나 누르거나 취소할 수 있고, 화면에는 Bunch로만 표시합니다.
- 한 Bunch는 한 Bundle에 좋아요를 1번만 누를 수 있습니다. 멤버 A가 누른 좋아요를 멤버 B가 취소할 수도 있습니다(Bunch 공동 상태).
- 우리 Bunch의 Bundle에도 좋아요를 누를 수 있습니다. 우리 Bundle은 Feed에 나오지 않으므로 Bunch Home Archive나 Bundle 상세에서 누릅니다.
- 화면에는 개수와 누른 Bunch 목록을 보여줄 수 있습니다.

### 댓글

- 현재 선택한 Bunch 명의로 1~200자를 작성합니다. 그 Bunch의 멤버 누구나 쓸 수 있고, 작성자는 멤버 이름 없이 Bunch 이름으로만 표시합니다.
- 답글·수정은 없습니다. 댓글을 남긴 Bunch의 멤버 누구나, 그리고 댓글이 달린 Bundle을 가진 Bunch의 관리자가 삭제할 수 있습니다.
- 우리 Bunch의 Bundle에도 댓글을 남길 수 있습니다. 이 댓글도 멤버 이름 없이 우리 Bunch 이름으로 표시되며, 참여 멤버가 쓰는 멤버별 코멘트와는 별개입니다.

### 신고 (앱 출시 필수)

- **주체:** Bunch입니다. 현재 선택한 Bunch 명의로 멤버 누구나 신고할 수 있고, 실행한 멤버는 내부에만 기록합니다.
- **대상:** 다른 Bunch의 Bundle·댓글·Bunch 프로필입니다. 이번 #75 구현은 번치 프로필 신고(5.10.7)만 다루며 댓글(6.2.10)·번들(6.2.14) 신고는 피드 구현 때 같은 정책을 적용합니다.
- **사유:** 스팸 / 음란·부적절 / 괴롭힘·욕설 / 개인정보 노출 / 기타 중 선택 + 상세 내용(기타 OTHER는 필수, 최대 200자).
- 같은 Bunch는 같은 대상을 첫 정상 접수 시각부터 24시간 동안 최대 2번 신고할 수 있습니다. 같은 번치의 다른 멤버가 신고한 것도 함께 셉니다. 허용된 재신고는 새 ID로 접수하고 사유·상세·상태를 독립적으로 보존하며 운영 검토도 건마다 진행합니다. 두 번째 신고·거부 시도로 24시간을 연장하지 않고, 정확히 24시간이 지나면 다음 정상 접수부터 새 구간을 시작합니다. 검토 완료 여부는 접수 횟수에 영향을 주지 않습니다.
- 번치 신고는 양방향 차단 여부를 한도보다 먼저 확인하며 차단된 대상은 접수하지 않습니다. 차단·해제로 기존 신고나 사용 횟수를 초기화하지 않습니다. 서버는 「신고하기」 요청 시 한도를 확인하고 3번째 이후 요청을 거부합니다. 앱은 시트를 닫고 「이미 신고가 접수되어 검토 중이에요.」를 표시합니다. API·오류 계약은 [번치 소셜 Spec](specs/bunch-social.md)을 따릅니다.
- 신고한 Bunch의 멤버 전원에게 해당 콘텐츠를 피드에서 즉시 숨기는 정책을 유지합니다. 접수된 신고는 건별 운영 검토 대상이며 운영자는 콘텐츠 숨김·삭제·이용 정지를 할 수 있어야 하고 모든 조치를 기록합니다. 신고만으로 자동 제재·차단하지 않습니다. 실제 피드 숨김 연결·댓글/번들 신고·운영 심사 API/화면 구현은 이번 범위 밖입니다. 상세 내용은 최대 200자이고 OTHER는 공백 외 1자 이상 필수입니다.
- App Store 규정상 앱 안에 공개 연락처(문의 채널)도 필요합니다. (CS = 카카오톡 오픈채팅방)

### 차단 (앱 출시 필수)

- **주체와 대상 모두 Bunch**입니다. Bunch는 하나의 그룹 계정이므로, 차단은 차단한 Bunch의 멤버 전원에게 적용됩니다. 개인 화면에서만 숨기는 방식은 쓰지 않습니다.
- **차단과 차단 해제 모두 관리자만** 할 수 있습니다(10/13 변경, 공동 관리자 포함). 현재 선택한 Bunch 명의로 하고, 실행한 관리자는 내부에만 기록합니다. 일반 멤버에게는 다른 Bunch 프로필의 「⋯」 메뉴에 「신고하기」만 보이고, 서버도 일반 멤버의 차단 요청을 거부합니다.
- 차단 목록은 Bunch 관리 메뉴에서 모든 멤버가 볼 수 있고, 해제 버튼은 관리자에게만 보입니다.
- **차단하면:** A Bunch가 B Bunch를 차단하면, A Bunch의 **모든 멤버** 화면에서 B Bunch의 콘텐츠가 **아예 보이지 않습니다.** 차단한 멤버 한 명만이 아니라 Bunch 단위로 적용됩니다.
- **구체적으로 안 보이게 되는 것** (A Bunch를 현재 Bunch로 쓰는 동안):
    - Feed 전체(팔로잉 구간·전체 공개 구간)에서 B의 Bundle
    - B의 Bunch 프로필과 B의 Bundle 상세. 링크·알림으로 들어와도 "볼 수 없는 Bunch예요"로 막음
    - 어떤 Bundle에서든 B가 남긴 댓글 (우리 Bundle에 이미 달린 것 포함)
    - 좋아요를 누른 Bunch 목록, 팔로워·팔로잉 목록에서의 B
    - B와 관련된 새 알림 (생성하지 않음)
- **함께 일어나는 것:**
    - A와 B 사이의 팔로우는 양쪽 모두 해제됩니다. 차단을 풀어도 팔로우는 자동으로 되돌아오지 않습니다.
    - B가 이미 남긴 댓글·좋아요는 삭제하지 않고 숨기기만 합니다. 차단을 풀면 다시 보입니다.
- **차단당한 B 쪽 (확정, 양방향):** B의 멤버도 B로 볼 때 A의 콘텐츠·프로필을 볼 수 없고, A의 Bundle에 좋아요·댓글·팔로우를 할 수 없습니다. 차단당했다는 사실은 알리지 않고 "볼 수 없는 Bunch예요"로만 보여줍니다.
- **영향 없는 것:** A Bunch 안의 사진함·Draft·발행 Bundle 등 내부 기록은 차단과 무관합니다.
- **현재 Bunch 기준 적용:** 차단은 "지금 어느 Bunch로 보고 있는지"에 따라 적용됩니다. A와 C에 모두 속한 멤버는 A로 볼 때 B가 안 보이고, C로 전환하면 C의 차단 목록을 따릅니다. 드물게 A와 B에 모두 속한 멤버도 B로 전환하면 B의 내부 기록은 그대로 봅니다.
- 서버는 Feed·프로필·Bundle 상세·댓글·좋아요·팔로우 요청마다 "현재 Bunch와 대상 Bunch 사이에 차단이 있는지"를 확인해 걸러야 합니다.
- 자기 Bunch는 차단할 수 없습니다.

### 추가 알림

- "OO Bunch가 우리 Bunch를 팔로우했어요" → 멤버 전원, "OO Bunch가 우리 Bundle에 댓글을 남겼어요·좋아해요" → 그 Bundle의 참여 멤버. 앱 안 알림과 푸시 모두 보내며, 좋아요·댓글은 달리자마자 바로 보냅니다. 시간대에 따른 발송 제한은 없습니다. 알림에도 실행한 멤버는 표시하지 않습니다.
- 같은 Bunch가 같은 Bundle에 좋아요를 취소했다 다시 누르면 푸시를 다시 보내지 않습니다 (알림 도배 방지).
- 우리 Bunch가 우리 Bundle에 남긴 좋아요·댓글은 알림을 보내지 않습니다. 좋아요·댓글 알림은 다른 Bunch가 남겼을 때만 갑니다.

## 5. 권한 (OWNER / CO_OWNER / MEMBER)

활성 번치마다 메인 관리자 `OWNER`는 정확히 1명입니다. 공동 관리자 `CO_OWNER`는 여러 명 가능하며 일반 멤버는 `MEMBER`입니다. 기존 「여러 Owner가 모두 같은 권한」 정책은 2026-10-29에 대체되었습니다. 생성자가 첫 메인 관리자이며 이후에는 현재 역할로 판단합니다.

| 행동 | 메인 관리자 OWNER | 공동 관리자 CO_OWNER | 일반 멤버 MEMBER |
| --- | --- | --- | --- |
| 사진 업로드·다른 멤버 사진 사용·초대/멤버 목록 | 가능 | 가능 | 가능 |
| 사진함 사진 삭제·날짜 변경 | 모든 사진 | 모든 사진 | 본인 업로드 사진만 |
| 초안 생성·조회 | 가능 | 가능 | 가능 |
| 초안 공용 편집·참여자 추가 | 참여 중일 때 | 참여 중일 때 | 참여 중일 때 |
| 초안의 타인 제외·발행·폐기 | 생성자 또는 참여 중일 때 | 생성자 또는 참여 중일 때 | 생성자만 |
| 발행 번들 공용 내용 수정·삭제 | 가능 | 불가 | 불가 |
| 본인 코멘트 작성·수정 | 본인만 | 본인만 | 본인만 |
| 번치 프로필 전체(사진·이름·소개·공개 범위) 일괄 저장 | 가능 | 불가 | 불가 |
| 공동 관리자 지정·해제 / 메인 관리자 인계 | 가능 | 불가 | 불가 |
| 번치 멤버 내보내기 | 공동 관리자·일반 멤버 대상 | 일반 멤버 대상만 | 불가 |
| 번치 삭제 | 가능 | 불가 | 불가 |
| 번치 나가기 | 후임 직접 지정 필수; 혼자면 삭제 안내 | 가능 | 가능 |
| 팔로우·좋아요·댓글·신고 / 팔로우 요청 승인·거절 | 가능 | 가능 | 가능 |
| 우리 번치 명의 댓글 삭제 | 가능 | 가능 | 가능 |
| 우리 번들에 다른 번치가 남긴 댓글 삭제 | 가능 | 가능 | 불가 |
| 다른 번치 차단·해제 / 차단 목록 조회 | 가능 | 가능 | 목록 조회만 |

메인 관리자를 내보내거나 직접 권한 해제할 수 없습니다. 인계 시 대상은 OWNER, 이전 메인은 MEMBER로 함께 변경합니다. 초안 생성자는 타인이 제외할 수 없으며 이탈하면 초안을 삭제합니다. 미참여 관리자는 편집·발행·폐기할 수 없습니다. 관리자도 타인 코멘트를 수정·삭제·숨길 수 없고 발행 후 본인 코멘트도 비우거나 삭제할 수 없습니다. 사진함 공동 업로더 규칙은 유지합니다. 권한·소속 변경은 번치 잠금 아래 현재 역할과 Membership ID를 다시 확인합니다.

## 6. 상태 흐름

각 객체가 가질 수 있는 상태값입니다. **Photo·Bunch·Bundle의 영구 삭제는 상태가 아니라 데이터 삭제**입니다. Membership의 이탈 상태, 댓글의 삭제·숨김 상태, Switcher의 「접근 불가」 안내는 별도 표시·관리 요구로 구분합니다.

| 객체 | 상태값 | 꼭 알아둘 것 |
| --- | --- | --- |
| **Photo** | 처리 중 / 처리 완료 | 업로드 실패한 사진은 서버에 남지 않음. 삭제는 휴지통 없이 바로 영구 삭제(복구 불가). 단 발행 Bundle이 쓰는 이미지 파일은 남김 |
| **번들 후보** | 제안됨 / 변환됨 / 소멸 | 새 사진이 합류하면 같은 후보를 갱신. 사진이 삭제·사용돼 조건 미달이 되면 소멸 |
| **Bundle** | 작성 중(Draft) / 발행 처리 중(일시적) / 발행됨 | Draft 폐기와 Bundle 삭제는 영구 삭제. 작성 중에는 사진함 원본과 연동(원본 삭제 시 Draft에서 빠짐), 발행 후에는 독립. 발행됨 → 작성 중 되돌리기는 없음 |
| **Bundle 참여 멤버** | (상태값 없음) | 참여 멤버가 추가·생성자 또는 참여 중인 관리자가 제외(번들 Spec). 제외되면 연결 삭제, 그 멤버 코멘트도 삭제. 참여 멤버가 된 시각 보관. Bunch를 나가면 자동으로 빠짐. 1명만 남으면 발행 불가 |
| **Membership** | 활성 / 나감 / 내보내짐 (+ 역할: OWNER / CO_OWNER / MEMBER) | 서비스 탈퇴는 나감과 같이 처리. 다시 초대받으면 새 활성 Membership 생성. 활성 메인 관리자는 정확히 1명 |
| **Bunch** | (상태값 없음) | 공개/비공개는 공개 범위 속성. 분위기·뭉치 유형은 생성 후 고정, Stage는 파생값. 삭제는 영구 삭제, 하위 데이터 전부 함께 삭제 |
| **초대 링크·코드** | 유효 / 만료 / 폐기 | 7일 뒤 만료. 관리자가 재설정하거나 멤버를 내보내면 폐기되고 새로 발급. Bunch당 유효한 것 1개 |
| **팔로우** | 요청 중 / 승인됨 | 공개 Bunch는 바로 승인됨. 거절·취소는 삭제. 차단하면 양쪽 팔로우 모두 삭제 |
| **댓글** | 정상 / 작성 Bunch 삭제 / 대상 Bunch 관리자 삭제 / 운영 숨김 | 차단된 Bunch의 댓글은 상태를 바꾸지 않고 조회에서만 걸러냄(차단 해제 시 다시 보임) |
| **신고** | 접수 / 검토 중 / 조치 / 기각 | 같은 Bunch·같은 대상은 첫 신고부터 24시간 최대 2건(멤버 전체 합산). 접수·운영 검토는 건별 독립 처리하며 검토 상태로 횟수를 초기화하지 않음 |

## 7. DB 설계 시 미리 반영해야 할 규칙

나중에 바꾸기 어려운 것들이라 초기 설계에 반영이 필요합니다.

1. **Membership 유일성:** 같은 User와 Bunch 사이의 활성 Membership은 하나만 존재합니다. 가입일과 최근 활동 시각을 남겨야 합니다(계정 탈퇴 시 메인 관리자 자동 승계 기준; 수동 나가기는 후임 직접 지정).
2. **메인 관리자는 정확히 1명:** 활성 OWNER 유일성을 DB에서 보장하고 인계·이탈·내보내기·계정 탈퇴를 번치 단위로 직렬화합니다. 수동 나가기는 후임 직접 선택 필수이며 계정 탈퇴만 자동 승계합니다. 소속·업로더·초안·코멘트·편집권 정리는 같은 트랜잭션으로 처리하고 실패하면 함께 롤백합니다. 과거 요청은 종료된 소속을 복원하거나 다른 Membership을 변경하지 않습니다.
3. **요청마다 권한 확인:** 모든 Bunch 단위 요청에 대상 Bunch를 명시하고, 서버가 매번 멤버 여부·역할을 확인합니다. 하위 데이터(사진·Draft·후보)가 그 Bunch 소속인지도 확인합니다. 이 멤버 권한 규칙과 별개로 공개 Feed·공개 프로필·초대 Preview는 각 절의 공개 조회 자격을 따릅니다.
4. **발행 기록은 이탈 후에도 유지:** 발행 이미지·멤버별 코멘트·기여 기록은 Membership 종료와 함께 삭제하지 않습니다. 사진함 업로더·초안 참여·코멘트·편집권은 같은 트랜잭션에서 정리하며 생성자 초안은 삭제합니다.
    - **서비스 탈퇴 시:** 발행 사진과 코멘트는 Bunch에 남기되, 작성자는 "탈퇴한 멤버"로 표시하고 코멘트 내용은 "탈퇴한 멤버가 쓴 코멘트예요"로 대체합니다(원래 내용은 삭제).
    - **Bunch 나가기·내보내짐:** 이탈 중에는 이름을 "나간 멤버"로 표시하고 발행 코멘트 내용은 유지합니다. 두 경우 모두 유효 초대·새 요청 키로 재참여할 수 있고 새 Membership의 MEMBER로 시작합니다. 남아 있는 발행본의 동일 계정 이름·프로필·코멘트 연결은 복구하되 삭제된 사진함·업로더·초안·초안 코멘트·편집권과 이전 관리자 권한은 복구하지 않습니다. 개인정보 즉시 삭제는 서비스 탈퇴에 적용합니다(U-01 대체, 2026-10-31 확정).
5. **사진 저장 방식 (확정):** 원본과 썸네일을 따로 두지 않고 긴 변 2560px 이미지 한 장만 보관합니다. 앱에서 줄여서 올리고 위치 EXIF는 지운 상태로 저장하며, 사진함 그리드·상세·Feed·발행 Bundle이 모두 같은 파일을 씁니다. 촬영 시각·위치는 줄이기 전에 뽑아야 합니다. 그리드 로딩이 무거우면 저장소·CDN의 내려줄 때 크기 줄이기 기능을 검토해 주세요.
6. **사진함 삭제와 이미지 파일 삭제 분리:** 사진함에서 지운 사진도 발행된 Bundle이 참조하는 동안 이미지 파일은 유지해야 합니다.
7. **Draft 데이터 분리:** 공동 영역(제목·사진 목록과 순서·사진별 캡션·공개 범위)과 개인 영역(멤버별 코멘트)을 나눠야 동시 수정 충돌이 줄어듭니다. 각 사진을 누가 추가했는지도 남깁니다.
    - **사진 캡션은 사진함 Photo가 아니라 "Bundle 안의 사진"에 붙습니다.** 같은 사진을 두 Bundle에 쓰면 캡션이 따로 있고, Draft에서 사진을 빼면 그 캡션도 함께 사라집니다. 발행 후 사진함 원본이 삭제돼도 캡션은 유지됩니다.
    - 두 멤버가 같은 사진의 캡션을 동시에 고치면 제목처럼 버전을 확인해 덮어쓰기를 막습니다(사진 단위).
8. **삭제 방식:** Bunch와 Bundle은 영구 삭제로 복구 기능이 없습니다. Bunch를 지우면 하위 데이터(사진·Bundle·후보·팔로우·좋아요·댓글·초대)도 함께 지워지며, 이미지 파일 정리는 뒤에서 따로 처리해도 됩니다. 사진함 Photo도 휴지통 없이 바로 삭제되며 복구할 수 없습니다. 단 발행 Bundle이 참조하는 이미지 파일은 남깁니다.
9. **Draft 생성자와 참여 시각 기록:** 생성자를 인계하지 않습니다. 생성자 이탈 시 작성 중 초안을 삭제하고 나머지 이탈자의 참여·코멘트·편집권을 정리합니다. 발행 기여 기록·코멘트는 유지하며 탈퇴 익명화는 별도 적용합니다. 참여 시각은 24·72시간 리마인드 기준입니다. 발행·이탈·참여 제외는 같은 번치/초안에서 순서대로 처리합니다. DRAFT-16의 이전 인계 요구는 대체되었습니다.
10. **중복 요청 방지:** Bunch 생성, 초대 참여, 사진 업로드, Draft 생성, 발행, 관리자 권한 부여·해제는 같은 요청이 두 번 와도 한 번만 반영되어야 합니다.
11. **촬영 정보는 없을 수 있음:** 촬영 시각·위치는 비어 있을 수 있고, 촬영 시각은 시간대 변환 없이 현지 시각 그대로 저장하는 것을 권장합니다. 업로드 시각은 항상 따로 저장합니다.
12. **위치 정보 보호:** 사용자에게 내려주는 이미지에는 위치 정보(EXIF)가 남으면 안 되고, 화면에는 장소명(동/구) 수준만 노출합니다. 서버에도 정밀 좌표는 저장하지 않고 동네 단위로만 저장합니다 (확정).
13. **멤버 전용 이미지 보호:** 이미지 URL이 유출돼도 권한 없는 사람이 볼 수 없도록 권한 확인 후 짧은 유효기간의 URL로 제공하는 방식을 권장합니다.
14. **기준값은 설정으로:** 번들 후보 기준(하루 경계 시각·여행 거리·최대 일수·최소 장수·비슷한 사진 간격), 뭉치 Stage 기준, 업로드 한도는 운영하며 바뀔 수 있으므로 코드 상수보다 설정값으로 관리합니다.
15. **활동 기록:** 생성·참여·발행·전환 시각을 처음부터 남겨두면 이후 지표(가입, Bunch 수, Bundle 수, 참여 인원, 재방문) 집계가 쉬워집니다.
16. **신고 구간과 동시성:** 영구적인 신고 쌍 UNIQUE 대신 첫 접수에 고정한 24시간 구간을 저장하고 번치·대상별 횟수 확인과 저장을 원자적으로 처리합니다. 기존 신고는 보존합니다. 번치 신고의 V18 백필·제약·배포 호환성은 [번치 소셜 Spec](specs/bunch-social.md)을 따릅니다.

## 9. 참고 수치

- **Bunch 생성은 1명, 최대 8명**, 공동 Draft 생성은 Bunch 멤버 2명 이상, 발행은 Bundle 참여 멤버 2명 이상. 원문 「최소 2명」을 생성 최소 인원으로 적용하지 않음. 1인당 활성 소속 Bunch 최대 10개
- 닉네임·Bunch 이름은 각각 전체에서 중복 불가 (10/13). 서버가 유일성 보장(유일 제약)
- 업로드 1회 50장, 1장 30MB, 1인당 번치마다 하루 100장(한국 시간 자정 초기화, 번치별로 따로 셈), 사진함 Bunch당 1,000장 (확정)
- Bundle(Draft) 사진 1~20장, Bunch당 작성 중 Draft 최대 10개 (2026-10-29 확정)
- 뭉치 4단계, 발행 Bundle 0/2/6/10개 기준 (2026-10-29 확정)
- 닉네임·Bunch 이름은 각각 공백 포함 **1~12자**, 한글·영문 대소문자·숫자·공백 허용, **특수문자·이모지·줄바꿈 불가**. 앞뒤 공백 제거, 공백만 불가, 대소문자·가운데 공백을 구분해 전체 유일성 보장. 닉네임·Bunch 이름 모두 앞뒤 공백 제거·NFC 정규화 후 Unicode 코드 포인트 수로 길이를 센다(조합되지 않은 자모도 각각 1자). 소개는 **필수 1~50자**, 특수문자·이모지·줄바꿈 허용, 공백·줄바꿈만 불가, 앞뒤 공백·빈 줄 제거. 닉네임·이름·소개는 글자 수 카운터 표시. Bundle 제목 1~40자(줄바꿈 불가), 멤버별 코멘트 최대 400자(줄바꿈 허용, 발행 시 공백만 제외 1자 이상), 캡션 최대 200자(줄바꿈 허용, 선택). 제목·코멘트·캡션은 카운터 없이 상한에서 입력을 막고 안내. 소개·제목·코멘트·캡션은 눈에 보이는 글자 기준(이모지 1개=1자)으로 서버도 같은 상한 검증. 닉네임·Bunch 이름은 위 코드 포인트 기준을 적용
- 초대 링크 7일 만료, 알림 30일 보관·목록 최대 100개 (확정)

## 11. 로그인·온보딩 상세 명세에서 보완한 제품 요구

상세 명세의 제품 동작을 요약한 것으로 신규 기능 ID를 만들거나 기존 우선순위를 바꾸지 않습니다.

### 11-1. 로그인·가입 재개 (상세 1.1~1.5)

- 앱 실행 시 `GET /api/v1/members/me/onboarding`으로 로그인·가입 상태를 판단합니다. 가입 중이면 약관 또는 프로필의 미완료 단계, 가입 완료면 도착지 규칙으로 이동합니다. 같은 계정의 여러 기기 동시 로그인을 허용합니다. 탈퇴·이용 정지 계정은 세션을 해제하고 Entry로 보냅니다.
- Entry는 로그인·가입 통합이며 카카오 → Google → Apple 순서입니다. 하나를 진행하는 동안 다른 로그인을 시작하지 못하게 하고 취소·실패하면 Entry에서 재시도합니다. 이때 초대 정보는 유지합니다. 카카오는 회원 식별자만 요청하고 소셜 닉네임·사진은 가져오지 않습니다. 제공자와 고유 ID로 계정을 구분하며 이메일·전화번호로 병합하지 않습니다.
- 가입 중 User는 가입 절차 기능만 이용할 수 있으며 번치 생성·참여·Feed는 불가합니다. 같은 소셜 계정 중복 생성을 막고, 탈퇴 후 재가입은 과거 기록과 연결하지 않는 새 계정입니다. 가입 중 30일 방치 계정의 자동 파기는 별도 정책 확정 후 적용하는 미정 사항입니다.
- 필수 약관 3개는 개별/전체 동의 가능, 모두 동의해야 진행합니다. 원문은 앱 안에서 최신 적용본을 열고 동의 버전·일시를 기록합니다. 저장 성공 후 사진 접근 → 카메라 → 알림 순서로 선택 권한을 요청하며 거부해도 가입은 계속합니다. 이미 결정한 권한은 중복 요청하지 않고 위치 권한은 받지 않습니다. 팝업 도중 앱 종료 시 다음 실행은 프로필부터 재개하고 남은 권한은 기능 사용 때 안내합니다. 약관에서 뒤로 가면 로그인 상태는 해제하되 가입 진행은 유지합니다.
- 닉네임 중복 확인은 입력을 0.5초 멈춘 후 수행합니다. 확인 중·중복·확인 실패 시 가입 완료를 막고 저장 때 최종 재검사합니다. 1~12자·허용 문자·NFC·전체 유일성 규칙을 적용합니다. 공백만 입력은 불가, 한글 조합은 완료 후 길이를 판단합니다. 프로필 입력은 완료 전 임시이며 앱 종료 시 미저장 값은 유지하지 않습니다.
- 선택 프로필 사진은 1:1 편집·위치 메타데이터 제거, JPEG·PNG·HEIC·WebP 허용이며 사진 저장 실패 시 기본 이미지로 가입 완료합니다. 출생연도·성별은 선택·비공개입니다. 약관 동의·프로필 저장 완료 시 가입 완료 시각과 상태를 기록합니다.
- 초대 없는 신규 가입 완료자는 번치 시작 선택으로 이동합니다. 초대가 있으면 가입 완료 후 자동 참여하고 실패해도 가입 완료는 유지하며 사유 안내 후 번치 시작 선택으로 이동합니다. 기기 초대 정보는 최대 24시간 유지하며 로그인 취소·실패에는 보존하고 참여 완료·로그아웃·24시간 경과·초대 확인 중단 시 삭제합니다. 복수 초대 중 최신 것만 유지하는 정책은 제안입니다.

### 11-2. 번치 시작·생성 (상세 2.1~2.3)

- 소속 0개이면 새 번치 만들기 / 초대받은 번치 참여하기를 고릅니다. 닫기(X) 또는 생성·참여 중단 시 확인 모달을 거쳐 공개 Feed로 이동할 수 있습니다. 다음 실행에도 소속 0개이면 번치 시작 선택을 다시 보여줍니다.
- 기본 정보 → 소개 → 분위기 3단계는 이동 시 입력을 유지하며 최종 생성 때 한 번에 반영합니다. 헤더 뒤로가기·스와이프는 중단 확인, 하단 이전은 단계 이동입니다. 생성 전 앱 종료·중단 시 임시 입력을 버립니다.
- 이름은 공백 포함 1~12자·허용 문자·전체 유일성 규칙, 공개 범위는 미선택 후 명시적 선택입니다. 이름 중복 확인은 입력 중단 0.5초 후 수행합니다. 닉네임과 달리 번치 이름 중복 확인의 네트워크 실패는 다음 단계 이동을 허용하고 생성 시 최종 검사합니다. 생성 시 충돌하면 기본 정보 단계로 돌아가 수정을 요청합니다.
- 소개는 필수 1~50자이며 특수문자·이모지·줄바꿈을 허용하고 줄바꿈을 저장·표시합니다. 공백·줄바꿈만 입력 불가, 앞뒤 공백·빈 줄 제거, 화면에 보이는 글자 기준입니다. TIP 3개 예시는 정보 표시만 하며 눌러도 자동 입력하지 않습니다.
- 분위기는 4종 중 1개 직접 선택 필수, 미선택 시작이며 생성 후 변경 기능은 없습니다. 유형별 단계 이미지가 필요하고 분위기 이름·설명·그래픽은 디자인 미정입니다. 이미지 로딩 실패가 분위기 선택을 막지 않도록 합니다.
- 가입 완료·활성 소속 10개 미만·이름·소개·공개 범위·유형 조건을 최종 확인합니다. Bunch와 유일한 첫 메인 관리자(OWNER) Membership을 함께 생성하고 실패 시 모두 되돌립니다. 중복 시도는 같은 번치를 반환하고 마지막 사용 번치를 갱신합니다. 뭉치 유형은 보관하고 Stage는 현재 발행 Bundle 0개 기준 1단계로 계산합니다.
- 생성 완료에서 축하 효과는 1회, 리소스 실패 시 정지 화면으로 대체합니다. 이미 생성됐으므로 생성 단계로 뒤로 가지 않습니다. 멤버 초대 또는 Home으로 이동할 수 있습니다. 사진은 생성 완료 후 즉시 변경하며 메인 관리자만 가능, 실패 시 기존 이미지를 유지합니다. 사진을 바꿔도 뭉치 유형·Stage는 바뀌지 않습니다.

### 11-3. 초대·참여 (상세 2.4~2.7)

- 초대 화면은 기존 유효 링크를 쓰고 없거나 만료·폐기됐으면 새로 발급합니다. Bunch당 유효 링크 1개·7일 만료·발급 멤버 기록을 유지합니다. 복사·iOS 공유가 가능하며 행동을 기록합니다. 로딩 실패 시 재시도 가능, 나중에 하기·닫기는 새 번치 Home으로 이동합니다. 코드의 존재 요구와 링크 중심 상세 화면의 공백은 U-04입니다.
- 링크 입력·붙여넣기 후 확인 단계에서는 참여하지 않습니다. 클립보드는 붙여넣기를 선택할 때만 읽습니다. 링크 유효성·만료·폐기·번치 존재·정원·소속 한도·기존 멤버 여부를 확인합니다. 이미 멤버면 중복 참여 대신 그 번치 Home으로 이동합니다.
- 초대 카드에는 번치 이름·소개·프로필 이미지·초대자 닉네임만 표시하고 사진·번들·멤버 수 등 내부 정보는 숨깁니다. 초대자가 나가거나 탈퇴하면 From을 숨깁니다. 소개가 빈 값일 때 숨기는 예외는 기존·비정상 데이터 표시 대응이며 생성·편집의 필수 소개 규칙을 바꾸지 않습니다.
- 참여 순간 조건을 재확인해 활성 Member Membership을 한 번만 만들고 마지막 사용 번치를 갱신하며 기존 멤버 전원에게 알립니다. 만료·폐기·삭제·정원·소속 한도 실패는 사유를 안내하고 입력을 유지합니다. 없는 링크와 만료 링크는 화면에서 구분하지 않습니다. 반복 입력 제한의 「계정당 10분에 10회」는 예시이며 확정 수치가 아닙니다.
- 초대 확인에서 중단하면 참여 없이 Feed로 이동하며 거절 알림을 보내지 않고 보관 초대 정보를 지웁니다. 참여 완료 화면에서 Feed로 돌아가도 완료된 참여는 유지합니다.
- 웹 초대장은 유일한 비로그인 웹 화면입니다. 설치된 iPhone은 Universal Link로 앱을 열고 미설치면 웹 초대 확인 → App Store로 안내합니다. 웹에서 로그인·참여하지 않고 정원·내부 데이터도 보여주지 않습니다. 설치 후 링크 다시 열기 또는 앱 내 붙여넣기로 이어갑니다. 설치 후 초대 자동 전달(Deferred Deep Link)은 구현 가능한 경우에만 진행하는 조건부 범위입니다.
- 앱 외부 초대 진입 시 비로그인·가입 중은 로그인·가입 완료 후 자동 참여, 로그인 완료자는 초대 확인 후 참여합니다. 다른 화면·번치 생성 중 새 초대를 열면 초대 흐름으로 진입하며 만들던 입력은 버립니다. 소속 10개 사용자의 링크 확인 시점 차이는 U-08입니다.
- 제안 유지: 초대 로딩 10초 초과 시 이전 화면 복귀, 외부 무효 링크의 복귀 화면, 복수 초대 중 최신 정보 유지, Android·PC 안내. 시스템 붙여넣기 UI 채택은 권장 검토, OG 디자인·Entry/일부 프로필 문구·분위기 리소스는 협의/디자인 미정입니다. 사진·카메라 권한 팝업 설명은 상세 1.3.4를 우선하고 알림 문구는 사용자 정의하지 않습니다.
