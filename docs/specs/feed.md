# 피드·소셜 6장 구현 계약

기능 ID: FEED-01~FEED-11 중 아래 원문 항목. 공통 #87(A), 최종 조립 #95(B).

기준은 [6장 시트](https://docs.google.com/spreadsheets/d/1ScziF7WoYLHRiC_UYJBkKsi0jL6KKQJD2TNDzW1QGfU/edit?gid=294136194#gid=294136194)의
6.1.1·6.1.4·6.1.7·6.2.1·6.2.4와 2026-11-07 승인 보완 정책이다.
발행본 내용/공개 범위 분리는 2026-11-10 재전달된 E19:K20·E23:K23(6.2.11·12·15, #124)를 따른다.
이 범위의 충돌은 기존 PRD·번들·번치 Spec보다 위 기준이 우선한다.
공통 서버 인터페이스와 DB 계약은 [feed-api](feed-api.md)를 따른다.

## 접근 판단

- ACTIVE 계정이면서 가입 완료인 사용자만 조회한다. 인증 세션은 기존 JWT 필터가 검증한다.
- 현재 번치는 클라이언트 입력을 받지 않고 기존 서버 선택 규칙인 ACTIVE 소속의
  `lastUsedAt DESC, id DESC`로 정한다. 요청 간 접근 판단이나 현재 번치를 캐시하지 않는다.
- 소속 0개도 공개 번치의 PUBLIC 발행 번들을 조회할 수 있다. 번치 명의 행동은
  `CURRENT_BUNCH_REQUIRED`로 거부한다. 가입 중·탈퇴 계정은 조회도 거부한다.
- 피드 후보에서는 사용자의 **모든 ACTIVE 소속 번치**를 제외한다. LEFT·REMOVED는 제외 근거가 아니다.
  상세에는 이 피드 전용 제외를 적용하지 않는다.
- 현재 번치의 상세는 PUBLIC·PRIVATE 발행 번들을 모두 허용한다. 현재가 아닌 소속 번치를
  외부 경로로 볼 때에는 기존 번치 프로필 계약대로 외부 규칙을 적용한다.
- OWNER의 [공개 범위 단독 변경](published-bundle-edit.md)으로 PRIVATE가 되면 외부 피드·번치
  프로필 목록/상세에서 즉시 제외한다. 내부 멤버 접근과 저장된 좋아요·댓글은 보존한다.
  PUBLIC 복구 후에는 기존 반응과 발행 시각을 유지하고 피드 위로 다시 올리거나 알림을 보내지 않는다.
- 외부 상세·피드 후보는 PUBLIC 발행 번들만 허용한다. 공개 번치는 누구나,
  비공개 번치는 현재 번치의 APPROVED 팔로우가 있어야 허용한다. PENDING은 허용하지 않는다.
- 현재 번치와 콘텐츠 소유 번치의 양방향 차단, 기존 번치 프로필 신고,
  번치·번들 운영 숨김, 현재 번치의 콘텐츠 숨김을 매 요청 DB에서 확인한다.
  내부 상세도 운영 숨김·현재 번치 신고 숨김을 우회하지 않는다.
- 좋아요·댓글 등의 쓰기는 같은 상세 접근 검사를 재사용하고 유효한 현재 ACTIVE 소속을 요구한다.
  역할·작성자·신고 횟수·대상별 멱등성은 해당 기능이 추가 검증한다.
- 기존 접근 불가 안내와 공개 범위 오류를 유지한다. 숨김·삭제·비발행·멤버 전용 외부 접근은
  존재 여부를 구분해 노출하지 않는다. 양방향 차단은 기존 번치 프로필 불가 응답을 사용한다.

## 피드와 후속 기능의 경계

팔로잉 구간은 최근 14일의 APPROVED 팔로우 대상 PUBLIC 번들, 공개 구간은 공개 번치의
PUBLIC 번들 중 앞 구간 중복을 제외한다. 각 페이지도 최신 접근 조건을 DB 조회에 적용한다.
A의 후보 집합 검사는 페이지를 받은 뒤 필터링하는 용도로 사용하지 않는다.
`GET /api/v1/feed`는 이 조건으로 두 구간을 한 페이지에 이어 채운다.
기본 20·최대 50번들이며 첫 anchor와 발행 시각/ID keyset을 유지한다.
팔로잉이 실제로 있었을 때만 `FOLLOWING_CAUGHT_UP` 항목을 경계에 넣는다.
공개 구간까지 끝나면 `endReached=true`이고 빈 페이지도 같은 종료 상태다.
현재 번치/소속/APPROVED 팔로우 문맥이 바뀌면 409 FEED_001로 새로고침을 요구한다.
차단·신고·운영 숨김·공개 범위는 모든 페이지의 DB 조회에서 즉시 재검사한다.

댓글은 개인 작성자와 작성 시 번치 배지를 표시하고 한 단계 답글을 허용한다.
작성자만 삭제하며 관리자도 남의 댓글을 삭제할 수 없다. 삭제 자리는 개수에 포함하고
차단·신고·운영 숨김은 개수에서 제외한다. 기존 `bundle_comments`는 참여자 코멘트다.
댓글·좋아요·신고·장소·광고는 아래 전용 Spec의 실제 저장소와 API를 사용한다.

## 카드·광고·소속 없음

피드 카드 응답에는 `photos[].picks`를 추가하지 않는다. 사진 순서는 번들 순서이고 첫 사진이
대표다. 사진별 `picks` 요약은 발행 번들 **상세**의 `photos[i].picks`에서만 제공하며,
발행 시점에 고정되어 원본 Photo 삭제나 순서 변경에도 유지된다. 제목·날짜·최대 3개 순서 있는 장소와
발행 시각, 번치 프로필·발행 참여자 전원·좋아요 수/현재 번치 상태·댓글 수를 반환한다.
참여자 표시는 발행 상세와 같은 배치 유틸을 사용한다. 나간/탈퇴한 참여자는 「작성자」와
기본 사진(null)이며 프로필 이동 불가다. 같은 계정이 번치에 재참여하면 복구되지만
WITHDRAWN 계정이나 새 계정은 복구되지 않는다.
사진별 제목 오버레이·상대 시각·회색 로딩 자리·토스트·애니메이션·스크롤 보존은 앱 표시 책임이다.

광고는 번들 6개마다 끼우며 페이지/구간을 넘어 센다. 광고는 번들 size에 포함하지 않는다.
매 API 요청마다 실제 활성·개인 미숨김 광고 후보를 새로 읽어 균등 랜덤 선택한다.
응답 내 풀 소진 전 중복과 직전 광고 반복을 피하며 대안이 없으면 자리를 생략한다.
빈 번들 응답에 광고만 반환하지 않는다. 개인 광고 숨김은 영구이고 번치 전환과 무관하다.

소속 0개도 PUBLIC 탐색이 가능하며 canInteract=false다. 번치 명의 쓰기는 기존 409로 거부한다.
헤더는 BUNCH 로고만 표시하고 알림/현재 번치 프로필은 숨긴다. 소속이 있으면 기존
홈·프로필/알림 API를 재사용한다. 새 피드 전용 헤더·알림 집계 API는 만들지 않는다.

## 운영·신고 비노출

V23의 `feed_content_hides`는 실제 조회에 적용되는 억제 기록이다.
운영 숨김은 DB에서만 관리하며 운영자 인증·HTTP API는 만들지 않는다.
신고 접수·심사·24시간 한도와 분리하여 같은 대상의 여러 신고가 하나의 비노출을 공유한다.
신고는 신고 번치에만 숨기며 다른 번치나 소속 0개 사용자에게 자동 제재하지 않는다.
기존 `bunch_profile_reports`는 별도 백필 없이 직접 조회한다.

## 검증 기준

전용 PostgreSQL·Redis에서 가입/계정 상태, 소속 0개, 서버 현재 번치, 전체 ACTIVE 소속 제외,
PUBLIC/PRIVATE·PENDING/APPROVED, 양방향 차단·프로필 신고, 운영/신고 숨김·해제·번치 전환,
실제 기존 상세/페이지 응답, 사진별 picks의 발행 동결·원본 삭제·번치 재참여·프로필 fallback,
동시 비노출 중복과 롤백, V23 제약·JPA validate를 검증한다.
실제 iOS/WebView/APNs 수동 검증은 별도다.

피드 통합은 두 구간을 함께 채우기·정확한 경계·빈 구간·동일 시각 ID 정렬·anchor 이후 발행 제외·
페이지마다 숨김/차단/신고/공개범위/삭제 적용·409 문맥 무효화·크기 변경·카드 사진/장소/참여자·
실제 좋아요/댓글 집계·삭제 자리·광고 간격/재선택/빈 응답·bounded 쿼리 수를 검증한다.
