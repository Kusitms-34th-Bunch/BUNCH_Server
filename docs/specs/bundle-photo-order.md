# 사진 ID 이동 — #107 / DRAFT-04

이 문서는 [번들 계약](bundle.md)의 사진 이동을 구체화한다. 사진 추가의 정원과
사진함 적용은 별도 계약이며 전체 목록 교체·CRDT·오프라인 재생은 추가하지 않는다.
2026-11-10 사용자 확인에 따라 같은 사진은 **서버가 나중에 처리한 새로운 이동**이 이긴다.

## 처리와 권한

기존 REST 이동의 대상/앞/뒤 ID는 모두 `bundle_photos.id`다. 원본 `photos.id`가 아니다.
호출자는 번치→번들 잠금을 잡고 현재 참여자·초안 상태를 검증한 뒤
`moveLocked(bundle, memberId, photoId, previousId, nextId, requestId)`를 호출한다.
잠금으로 직렬화된 처리 순서가 서버 도착 순의 기준이다. 같은 틈의 동률은 잠금 획득 후
DB 요청 행 ID 순서로 결정한다. 사용자 lease는 이동 전제가 아니다.

- 대상 자신을 기준으로 지정하거나 같은 앞/뒤 ID를 중복 지정하면 `BUNDLE_PHOTO_CONFLICT`다.
- 최신 목록에서 기준이 비인접이 되어도 수락한다. 뒤 기준 직전이 우선이고 뒤 기준이
  없으면 앞 기준 직후다. 같은 틈으로 이미 처리한 서로 다른 사진 뒤에 이어 붙인다.
- 앞 기준만 지정한 경우도 후속 이동은 그 틈에서 먼저 처리한 사진 뒤에 놓는다.
- 둘 다 null이면 빈 나머지 목록에서만 유효하다. 불명확한 전체 순서 초기화를 하지 않는다.
- 현재 번들의 실제 행이나 tombstone이 아닌 기준 ID는 `BUNDLE_PHOTO_CONFLICT`다.
  외부 번들 ID나 추측한 ID를 삭제 기준으로 받아들이지 않는다.
- 대상이 이미 삭제된 것으로 확인되면 변경 없이 끝낸다. 알 수 없는 대상은
  `RESOURCE_NOT_FOUND`다. 어떤 이동도 사진 행을 만들거나 삭제를 되돌리지 않는다.

## 최소 영속 정보

현재 노출 순서는 기존 `bundle_photos.position` 정수를 계속 쓴다. 변경 시 0부터 정규화한다.
`bundle_photo_order_marks`는 이동한 사진의 마지막 틈/처리 번호 또는 삭제된 사진의
이전 양옆 ID/슬롯만 보관한다. 전체 목록 사본·모든 이동 명령·재생 기록을 저장하지 않는다.
삭제 기준의 다음 생존 이웃, 이전 생존 이웃, 저장된 슬롯 순으로 자리를 보정한다.
여러 기준을 한꺼번에 삭제해도 이웃 사슬을 따라가고 순환은 방문 ID로 차단한다.
번들 삭제 시 marks도 DB cascade로 제거한다. 이 메타데이터를 사진 삭제와 함께 지우면 안 된다.
사진 원본·이미지·사용자 정보는 tombstone에 저장하지 않는다.

사진함 ‘적용’의 명시적 재선택은 기존 행을 유지한 채 새 선택 번호 순서로 뒤에 배치한다.
살아 있는 재선택 사진의 이전 drag gap mark만 제거하여 이후 동일 틈 이동이 옛 위치를
따라가지 않게 한다. 삭제 tombstone은 제거하지 않는다. 재선택·구성 변경·순서·요청 키는
같은 번들 잠금/트랜잭션으로 저장하며 기존 이동 요청 키의 재시도도 계속 보존한다.

모든 실제 사진 행 삭제 경로는 같은 잠금과 트랜잭션 안에서 삭제 **이전**에
`beforeRemoveLocked(bundle, rows)`를 호출한다. 사진함 차이 적용, 원본 최종 삭제 callback,
발행본 행 제거를 포함한다. 번들 자체 삭제는 cascade로 끝나므로 hook이 필요 없다.
마지막 사진 삭제·이미지 참조·핀·lease 등 기존 정책과 후처리는 호출자가 유지한다.

## 멱등성과 결과

기존 `bundle_requests`에 작업명 `PHOTO_MOVE`, 요청 키, SHA-256 fingerprint를 기록한다.
문자열 requestId는 작업명과 함께 UTF-8로 `UUID.nameUUIDFromBytes`에 넣어 안정적인 UUID로
변환한다. UUID 문자열뿐 아니라 기존 테스트·내부 호출의 일반 문자열도 지원한다.
키 범위는 기존과 같은 번치/사용자/작업이며 fingerprint에는 번들/대상/앞/뒤 ID를 넣는다.
같은 키와 다른 내용은 `IDEMPOTENCY_CONFLICT`다. 같은 요청 재전송은 최신 목록을 유지하고
`false`를 반환한다. 다른 요청이 그 사진을 다시 옮긴 뒤에도 옛 이동을 재적용하지 않는다.
보이는 순서가 안 바뀐 새 요청과 삭제된 대상의 요청도 멱등성에 기록한다.

서비스는 실제 순서 변경 여부만 반환하고 aggregate revision/시각/활동/이벤트를 변경하지 않는다.
호출자는 `true`일 때만 이를 한 번 갱신하고 현재 snapshot을 반환한다. 멱등성 행과 위치/marks는
같은 트랜잭션에서 커밋·롤백한다. 재연결은 서버 최신 snapshot을 읽으며 미전송 이동을 재생하지 않는다.

## 검증 기준

실제 PostgreSQL 트랜잭션에서 비인접 기준, 같은 틈의 앞뒤·앞만·뒤만 이동, 같은 사진의
마지막 이동, 오래된 요청 재전송, fingerprint 충돌, 삭제 기준 하나/여럿/양쪽, 삭제 대상,
외부 기준 거부, 롤백, 병렬 이동 후 사진 중복·유실 없음을 검증한다.
마이그레이션 적용·재적용과 JPA validate는 통합 테스트 환경 기동으로 확인한다.
실제 iOS 두 사용자의 드래그 보류·드롭·재접속 UX는 별도 수동 검증 대상이다.

## 마이그레이션 번호

최종 stack 적용 순서에 따라 미게시 파일은 V40을 사용한다.
제목 CRDT는 V41, 발행자는 V42다. 이전 로컬 lab 이력을
수정/repair하지 않으며 신규 DB에서 검증한다. 적용된 dev migration은 변경하지 않는다.
