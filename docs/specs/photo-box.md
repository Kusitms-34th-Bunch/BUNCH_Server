# 사진함 업로드 계약

이 문서는 이슈 #30의 사진함 업로드 저장 규칙을 고정한다. 앨범 선택(3.2.2)과 카메라 촬영(3.2.3)은
같은 규칙을 쓴다. HTTP 요청·응답 계약은 [사진함 업로드 클라이언트 계약](photo-box-api.md)에 둔다.
사진 목록·상세·삭제·날짜 변경은 이 범위에 포함하지 않는다.

## 기준 문서

기능명세서는 사진함 3.2.1~3.2.3·3.6.1, 번들 만들기 4.2.7·4.3.7을 따른다. 기획 문서와 충돌하면
기능명세서를 따른다. 영속성은 [사진함 기반 계약](photo-foundation.md), 이미지 검사와 외부 저장은
같은 문서의 "사진함 이미지 저장소"를 따른다. 값이 확정되지 않은 항목은 "확정 대기"로 표시하고 기본안으로 구현한다.

## 요청 단위

| 항목 | 규칙 |
| --- | --- |
| 단위 | 요청 1건에 사진 1장. 일부가 실패해도 성공한 사진은 저장된다(3.2.2 로직 4) |
| 대상 번치 | 요청 경로의 번치로 고정한다(3.2.1). 업로드 중 번치를 전환해도 원래 번치에 저장한다 |
| 업로더 | 가입 완료한 ACTIVE 번치 멤버만 가능하다. 소속은 저장 트랜잭션에서 다시 확인한다 |
| 업로드 묶음 | 요청마다 `uploadBatchId`(UUID)를 받아 `photo_uploaders`에 저장한다. 재시도해도 원래 값을 유지한다(3.2.2 로직 3 ⑤, 4.2.7) |
| 촬영 정보 | 촬영 날짜·시각은 앱이 보낸 현지 값을 그대로 저장한다. 없어도 업로드는 성공이다(3.2.2 로직 3 ④) |

## 처리 흐름

1. 촬영 정보를 검증한다. 날짜 없이 시각만 있으면 `COMMON_001`(400)로 거부한다.
2. 이미지 바이트의 SHA-256(소문자 hex)을 서버가 계산한다. 클라이언트가 보낸 해시는 쓰지 않는다.
3. **저장 전 확인(트랜잭션)**: 번치를 잠그고 소속을 확인한다. 같은 번치에 같은 해시의 Photo가 있으면
   외부 업로드 없이 합치기를 처리하고 끝낸다. 없으면 새 사진이 들어갈 자리가 있는지 확인한다.
4. **외부 업로드**: 트랜잭션 밖에서 이미지 저장소에 올린다. 실패하면 `PHOTO_007`(503)이며 DB에는 아무것도 남지 않는다.
5. **저장(트랜잭션)**: 3번과 같은 순서로 잠그고 모든 조건을 다시 확인한 뒤 `ImageAsset`, `Photo`(`READY`),
   `PhotoUploader`를 저장한다. 업로드하는 동안 다른 요청이 같은 사진을 먼저 저장했으면 합치기로 처리한다.
6. 올린 외부 파일이 쓰이지 않으면(합치기·실패) 삭제한다. 커밋 결과가 불확실한 실패에서는 같은 `publicId`의
   `ImageAsset` 행이 없을 때만 삭제한다. 삭제 실패는 로그만 남기고 응답에 영향을 주지 않는다.

잠금 순서는 (회원·업로드 묶음) → 번치 → 사진(ID 오름차순) → 업로더이며, 번치 이후는 번들 흐름과 같다.
하루 한도를 번치별로 세므로 번치 잠금만으로 같은 번치의 동시 업로드가 직렬화되어 회원 잠금은 쓰지 않는다.
한 묶음의 50장 한도는 번치와 무관하게 회원·묶음 기준으로 세므로, 서로 다른 번치에 같은 묶음으로 동시에 올려도
넘지 않도록 번치 잠금 앞에서 회원·묶음 단위의 트랜잭션 잠금(PostgreSQL 어드바이저리 락)을 먼저 잡는다.

## 한도와 집계

| 한도 | 값 | 기준 |
| --- | --- | --- |
| 묶음당 | 50장 | 같은 회원의 같은 `uploadBatchId` 업로드 행 수 |
| 1인·번치별 하루 | 100장 | 이 번치에서 회원의 `photo_uploaders.uploaded_at`이 오늘 `Asia/Seoul` 자정 이후인 행 수 |
| 번치당 | 1,000장 | 번치의 `photos` 행 수. **새 사진을 저장할 때만** 확인한다 |
| 1장 | 30MiB | #33 `PhotoImageStorage.inspect` |

- 한도는 사진 단위로 적용한다. 넘는 사진만 거부하고 나머지는 저장한다. 예: 990장인데 20장 → 10장 저장(3.2.2 예외).
- 한도를 넘으면 `PHOTO_001`(번치), `PHOTO_002`(하루), `PHOTO_003`(묶음) 409로 거부한다. 재시도해도 성공할 수 없다.
- 하루는 한국 시간 자정부터이며 매일 자정에 0장으로 초기화된다(기획 확정). 코드에서 `Asia/Seoul` 자정으로 계산하고 DB와
  서버의 시간대에 의존하지 않는다.
- 하루 한도는 **번치마다 따로** 센다(기획 확정). 「퇴근런클럽」에 100장을 올렸어도 「여행가조」에는 오늘 100장을 더 올릴 수 있다.
  갤러리에서 가져오기(4.3.7)도 같은 한도를 쓴다.
- 하루 집계는 오늘 올린 사진 중 **지금 남아 있는 장수**다(기획 확정). 사진을 삭제하면 `photo_uploaders` 행이
  사라지므로 그만큼 다시 올릴 수 있다. 예: 이 번치에 100장을 올리고 30장을 삭제하면 30장을 더 올릴 수 있다.
- 하루 집계에는 합쳐진 업로드도 포함한다. 이미 올린 사진(`ALREADY_UPLOADED`)은 새 행이 생기지 않으므로 세지 않는다.

## 같은 사진 합치기

같은 사진은 **파일이 완전히 같은 사진**이다(기획 확인). 같은 번치에서 `(bunch_id, file_hash)`가 같으면
같은 사진이다. 같은 장소에서 따로 찍은 사진은 합치지 않는다(3.2.2 로직 5). 서버는 앱이 줄이고 위치를 지운 뒤
보낸 파일의 바이트로 판단하므로, 같은 원본이 기기마다 같은 바이트로 나오는지는 앱 연동 뒤에 확인한다.

| 결과 | 조건 | 처리 |
| --- | --- | --- |
| `STORED` | 같은 번치에 같은 해시의 Photo가 없다 | 새 Photo와 업로더를 저장한다 |
| `MERGED` | 다른 멤버가 올린 같은 사진이 있다 | 업로더만 추가한다. 기존 Photo(날짜 포함)는 바꾸지 않는다 |
| `ALREADY_UPLOADED` | 내가 이미 올린 같은 사진이다 | 아무것도 바꾸지 않는다 |

세 경우 모두 `photoId`를 돌려준다(4.3.7). `MERGED`와 `ALREADY_UPLOADED`는 번치의 사진 수를 늘리지 않으므로
번치가 1,000장이어도 허용한다(4.3.7: 같은 사진은 "사진함에 새 사진이 생기지 않는다"). `MERGED`는 하루·묶음 한도에
포함하고, `ALREADY_UPLOADED`는 한도를 확인하지 않는다.
같은 요청의 재시도는 해시와 `(photo_id, member_id)` 유니크로 1장만 저장되므로 `Idempotency-Key`는 쓰지 않는다.

## 저장 값

| 항목 | 값 |
| --- | --- |
| 상태 | 새 Photo는 저장 즉시 `READY`(올린 직후 번들에 연결, 4.3.7) |
| 날짜 | 날짜가 있으면 `date_source=EXIF`, 날짜·시각이 모두 없으면 `UNKNOWN`. `USER`는 날짜 변경(3.4.1)에서만 쓴다 |
| 위치 | 받지도 저장하지도 않는다. 위치 메타데이터가 남은 이미지는 #33이 거부한다(3.2.2 로직 3) |

## 오류 구분

앱은 재시도 가능한 사진에만 「다시 시도」를 붙인다(3.2.2 상세동작 5). 서버는 상태 코드로 구분한다.

| 구분 | 상태 | 코드 |
| --- | --- | --- |
| 재시도 불가 | 400 | `COMMON_001` 형식·용량·해상도·위치 메타데이터·날짜 조합 |
| 재시도 불가 | 409 | `PHOTO_001`~`PHOTO_003` 한도 |
| 재시도 불가 | 403·404 | `AUTH_002` 번치 멤버가 아님, `RESOURCE_001` 번치 없음, `AUTH_015` 가입 미완료 |
| 재시도 가능 | 503 | `PHOTO_007` 이미지 저장소 장애 |

## 변경 신호

새 Photo를 저장하거나 업로더가 추가되면(`STORED`, `MERGED`) 트랜잭션 안에서
`PhotoChangedEvent(번치, 촬영 날짜, photoAdded)`를 발행한다. 구독하는 쪽은
`@TransactionalEventListener(AFTER_COMMIT)`로 받는다. 이미 올린 사진(`ALREADY_UPLOADED`)은 발행하지 않는다.

| 결과 | `photoAdded` | 이유 |
| --- | --- | --- |
| `STORED` | `true` | 새 사진이 들어왔다 |
| `MERGED` | `false` | 올린 멤버 수만 늘었다. 추천 조건(업로더 2명 이상)에는 영향을 주지만, "마지막 사진 추가 시각"과 30일 노출 기간은 새 사진이 추가될 때만 갱신한다(4.2.9) |

재계산 범위(촬영 날짜와 전날·다음 날)와 시점(마지막 변경 5분 뒤 한 번)은 구독하는 쪽(#26)이 정한다(4.2.9).
날짜 없는 사진(`capturedDate=null`)은 추천 계산에서 빠진다(4.2.7). 삭제(#39, #38)와 날짜 변경(#37)도 같은
이벤트로 알려야 하며, 이는 각 이슈에서 다룬다. 사진 올리기는 알림을 만들지 않는다.

## 번치를 나간 멤버

업로드 중 멤버가 번치를 나가면 저장 트랜잭션의 소속 확인이 `AUTH_002`로 실패해 남은 업로드가 멈춘다.
이미 올라간 사진의 정리는 #38(3.6.1)이 맡는다.

## 확정 대기

| 항목 | 기본안 | 확인 대상 |
| --- | --- | --- |
| 서버로 보낼 형식 | JPEG. 서버는 JPEG만 받고 리사이즈하지 않는다(리사이즈는 앱이 한다: 앱 확인) | 앱 |
| 같은 사진 판단 키 | 서버가 업로드된 파일의 SHA-256으로 판단한다. 앱이 가공(리사이즈·위치 제거)하면 같은 원본도 바이트가 달라질 수 있어 앱이 **원본 파일 해시**를 함께 보내는 안을 논의 중 | 앱, 팀(ERD) |
| Cloudinary 계정·파일 크기 한도 | 환경 구축 후 확인 | 계정 담당 |
| multipart 한도 배포 영향 | 30MB/31MB로 올렸다(사진 1장 30MiB 기준과 일치). 서버 전체 업로드에 적용되고 요청마다 최대 30MiB를 메모리로 읽으므로, 컨테이너 메모리와 터널의 요청 크기 한도를 확인한다 | 프로필·번치 이미지 담당, 배포 담당 |

## 테스트 기준

- 저장·합치기·본인 중복, 소속·가입 상태 거부, 날짜·시각 조합.
- 한도 경계(번치 1,000장·번치별 하루 100장·묶음 50장, 990+20 → 10장)와 하루 경계(`Asia/Seoul` 자정).
- 외부 업로드 실패, 업로드 중 소속 상실·같은 사진 선점 때 외부 파일 정리.
- 저장된 사진이 번들 연결(`lockReadyPhotosForConnection`)에서 받아들여짐.
- 실제 PostgreSQL 동시성: 같은 사진 동시 업로드, 같은 회원이 같은 번치에 동시에 올릴 때의 하루 한도, 번치 한도.
