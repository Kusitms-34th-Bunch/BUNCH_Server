# 추천 번들 조합 계약

이 문서는 이슈 #146의 추천 번들 조합 기반을 고정한다. 사진 한 장의 입력, 번들 결과, 코드, 설정값, 단서 매핑을 정의한다.
**계산 규칙은 정의하지 않는다.** 하루 준비(#148), 일반 번들(#149), 이벤트 번들(#150), 카드 사진(#151), 조립과 설명 로그(#152)가
이 타입을 쓰고, 입력 구성(#147)이 DB 값을 이 입력으로 바꾼다. 이름 붙이기·저장·노출·AI 호출은 이후 이슈다.

## 기준 문서

| 약칭 | 문서 | 쓰임 |
| --- | --- | --- |
| 조합명세 | 추천 번들 조합 백엔드 명세(노션 「추천번들조합_수정」, 2026-11-13) | 코드·특성·설정·결과 구조의 기준. 추천 번들과 AI 범위에서 기능명세서 4.2.2·4.2.7·4.2.8·4.2.9보다 우선한다(기획 정리) |
| 기능명세서 | 사진함 4.2.x, 3.2.2, 3.4.1 | 입력 데이터(업로더, 업로드 묶음, 촬영 시각)와 카드 6~10장 범위. 추천 번들 밖의 사진함 기능은 그대로다 |
| 앱 답변 | 업로드 필드 `capturedUtcOffset`, `sourceType` | 오프셋과 원본 유형 입력(#145) |
| 기존 계약 | [추천 번들 계약](recommended-bundle.md) | 지금 운영 중인 구현의 규칙. 새 계약으로 교체되기 전까지 그대로다 |

기존 코드(`PhotoClusterer`, `CardSelector`, `RecommendationService`, `RecommendationSettings`)는 바꾸지 않는다. 새 코드는
`com.bunch.recommendation.domain.combination`에 있고 기존 추천 흐름과 연결되지 않는다.

값은 확정(조합명세·기능명세서·앱 답변 근거 표시), 해석한 부분(명세가 정하지 않아 개발이 기본안으로 구현), 확정 대기로 나눠 적는다.

## 입력: 사진 한 장 (`RecoPhoto`)

함께 올린 사진은 한 장이고 올린 멤버는 모두 `uploads`에 든다(조합명세 3-1, 기능명세서 4.2.7 로직 2).

| 필드 | 뜻 | 근거 |
| --- | --- | --- |
| `capturedDate`, `capturedTime` | 촬영 현지 날짜·시각. 날짜를 바꾼 사진은 바뀐 날짜에 원래 시각이 붙어 있다. 업로드 시각으로 대신하지 않는다 | 4-1 F1, 기능명세서 3.4.1, 4.2.7 로직 4 |
| `utcOffset` | 촬영한 곳의 UTC 오프셋. 없으면 현지 시각을 기본 시간대로 읽는다 | 5-2, 앱 `capturedUtcOffset` |
| `uploads` | 올린 멤버와 업로드 묶음 ID(올린 사람마다) | 4-1 F2·F3, 기능명세서 4.2.7 로직 2·3 |
| `uploadedAt` | 사진이 처음 저장된 시각 | 8-5, 8-6 |
| `source` | 원본 유형 | 4-4, 앱 `sourceType` |
| `quality` | 품질. 사진을 올릴 때 서버가 계산해 `photo_reco_feature.quality`에 저장한 값(#168). 계산하지 못했으면 null | 4-1 F8, 4-4 |
| `aiStatus`, `analysis` | AI 분석 상태와 결과. 분석 전이면 `AiAnalysis.NONE` | 4-1 F4~F7, 4-3 |
| `embedding` | 이미지 비교용 숫자(임베딩). 없을 수 있다. 1차에서는 만들지 않는다 | 4-1 F10, 5-4 |
| `fingerprint` | 업로드 때 저장하는 64비트 이미지 지문(dHash, `photo_image_fingerprints`). 지문 도입 전 사진과 이미지를 못 읽은 사진은 없다 | 5-4, 기능명세서 4.2.8 로직 1 |
| `dateBatchId` | 여러 장의 날짜를 한 번에 조정한 사진들의 묶음 ID. 사용자가 날짜를 정한 사진에만 있다. 한 번에 올린 사진(`uploads`의 업로드 묶음 ID)과 함께 "같은 묶음"을 이룬다 | 기능명세서 4.2.7 로직 3, 4-1 F3, 7-9 |
| `timeState`(계산) | 날짜+시각 `FULL`, 날짜만 `DATE_ONLY`, 없음 `UNKNOWN` | 3-6 |

규칙: 시각만 있고 날짜가 없는 사진, 날짜 없이 날짜 묶음만 있는 사진, 올린 사람이 없는 사진은 만들 수 없다.

## 입력 만들기 (`RecoPhotoInputBuilder`, #147)

번치 하나의 사진을 DB에서 읽어 `RecoPhoto` 목록으로 바꾼다(조합명세 3-1, 5-1, 5-2). 계산하지 않고 값을 옮기기만 한다.

| 항목 | 내용 | 근거 |
| --- | --- | --- |
| 읽는 사진 | 번치의 `READY` 사진. 작성 중·게시된 번들에 쓰인 사진, 준비되지 않은 사진, 다른 번치 사진은 없다 | 3-1, 기능명세서 4.2.7 로직 1 |
| 날짜 없는 사진 | 시각을 모르는 사진(`UNKNOWN`)으로 **입력에 든다.** 하루 준비(#148)가 같은 중복 묶음에서 날짜를 빌리고(5-3), 빌린 뒤에도 모르면 그때 계산 제외한다 | 3-1, 5-3 |
| 함께 올린 사진 | 한 장으로 합치고 올린 멤버와 업로드 묶음을 모두 `uploads`에 담는다 | 3-1, 기능명세서 4.2.7 로직 2 |
| 순서 | 사진 번호 순이다. 같은 번치는 같은 입력이다 | 1장 원칙 5 |
| 오프셋 | 저장된 값을 그대로 쓰고 없으면 비워 둔다(읽는 쪽이 기본 시간대로 읽는다) | 5-2 |
| 품질 | 저장된 품질을 옮긴다. 값이 없으면 null이다(낮음이 아님, 3-1) | 3-1, 4-4 |
| 분석 상태 | 저장된 상태를 옮긴다. 분석을 요청한 적이 없으면(값 없음) 아래 해석을 따른다 | 4-3 |
| 분석 결과·임베딩 | 아직 값이 없어 비워 둔다(`AiAnalysis.NONE`, 임베딩 null) | 4-1, 4-3 |
| 지문·날짜 묶음 | 저장된 값을 담는다. 없으면 null | 4.2.8 로직 1, 4.2.7 로직 3 |

AI 공통 결과(`AiAnalysis`)는 모델과 상관없이 같다: 단서(코드, 확신도), 민감 단서(코드, 확신도), 활동(코드, 확신도), 피사체, 인물 수.
확신도는 AI가 낸 값 그대로 두고, 기준선은 계산하는 단계가 설정값(`clueMinConfidence`, `sensitiveMinConfidence`,
`activityMinConfidence`)으로 적용한다(4-3: "계산할 때 기준선을 적용한다"). 입력 만들기는 확신도를 걸러내지 않는다.

## 단서 매핑 (`EventClueMapping`)

이벤트마다 강한·보조·약한 보조 단서를 정한 표(3-3)이고, 코드가 아니라 데이터다. 출시 뒤에 오판이 많은 단서를 보조나 약한 보조로 내리는
조정이 잦기 때문이다. 기본값은 명세 표 그대로이고, 한 단서는 한 이벤트에서 셋 중 하나에만 들 수 있다. 꽃다발과 건배만 여러
이벤트(3개씩)에 걸친다. DB 테이블은 만들지 않는다.

조합명세 12장의 값을 하나씩 옮겼다. 규칙에는 숫자를 적지 않는다.

| 12장 | 필드 | 기본값 |
| --- | --- | --- |
| `DAY_START_HOUR`, 시간대 | `dayStartHour`, `afternoonStartHour`, `nightStartHour` | 5, 12, 18 |
| `CONT_SHORT` / `CONT_LONG` | `continuityShort` / `continuityLong` | 2시간 / 4시간 |
| `MIN_BOUNDARY_GAP` | `minBoundaryGap` | 20분 |
| `MIN_PHOTOS` / `MIN_UPLOADERS` | `minPhotos` / `minUploaders` | 6 / 2 |
| `PEOPLE_SPLIT_MIN_SIDE`, `SUB_BUNDLE_MAX` | `peopleSplitMinSide`, `subBundleMax` | 3, 40 |
| 카드 장 수 | `cardSizeSteps` | 6~15장은 6, 16~25장은 8, 26장 이상은 10 |
| `CLUE_MAX_RATIO` / `SUBJECT_MAX_RATIO` / `MEMBER_MAX_RATIO` | `clueMaxRatio` / `subjectMaxRatio` / `memberMaxRatio` | 0.5 / 0.5 / 0.6 |
| `TIME_BUCKETS`, `EVENT_SAME_PLACE_GAP` | `timeBuckets`, `eventSamePlaceGap` | 4, 2시간 |
| `CLUE_MIN_CONF` / `SENSITIVE_MIN_CONF` / `ACTIVITY_MIN_CONF` | `clueMinConfidence` / `sensitiveMinConfidence` / `activityMinConfidence` | 0.70 / 0.50 / 0.50 |
| `SAME_SCENE_MIN_SIM` | `sameSceneMinSimilarity` | 0.85 |
| 연사 | `burstMaxGap`, `burstMinSimilarity` | 3초, 0.90 |
| 거의 같은 구도 | `sameCompositionMaxGap`, `sameCompositionMinSimilarity` | 120초, 0.95 |
| 연사·같은 구도(지문) | `fingerprintBurstMinSimilarity`, `fingerprintSameCompositionMinSimilarity` | 0.90, 0.95 (개발 제안, 아래 해석한 부분) |
| 시계 보정 | `clockCorrectionMinPairs`, `clockCorrectionMinMedian` | 2쌍, 10분 |
| 품질 | `quality`(`ImageQualityCriteria`): 흔들림 60·200, 평균 밝기 35·225와 60~200, 양 끝 픽셀 비율 40%·10%(≤5, ≥250), 짧은 변 480·1080, 계산 크기 긴 변 1024px | 4-4 표 |
| 점수 가중치 | `representativenessWeight`, `qualityWeight`, `diversityWeight` | 0.4, 0.2, 0.4 |
| `AI_PENDING_TIMEOUT`, 기본 시간대 | `aiPendingTimeout`, `defaultZone` | 30분, `Asia/Seoul` |
| 재계산 디바운스, 목록 | `recalculationDebounce`, `listMax`, `sameActivityGeneralMax` | 5분, 20, 3 |
| `YEAR_END`·`HOLIDAY` 날짜창 | `yearEndWindows`, `holidayWindowDays` | 12/24~25와 12/31~1/1, 당일 앞뒤 1일 |
| 설정 버전(11장) | `configVersion` | `reco-cfg-1` |

`continuityOf(pace)`는 짧은 성격 2시간, 긴 성격 4시간, 하루 성격은 시간으로 나누지 않으므로 null이다. `dayPartOf(time)`은 시작 시각을
포함하고 끝 시각을 포함하지 않는다(04:59는 밤, 05:00은 오전, 12:00은 오후, 18:00은 밤). `cardSizeFor(장 수)`는 6장 미만이면 null이다.
디바운스, 목록 제한, AI 대기 시간처럼 이후 이슈에서 쓰는 값도 한곳에 모았다.

## 이미지 유사도 (`ImageSimilarity`)

중복 묶음(5-4)과 날짜 빌리기 후보(5-3)는 두 사진이 얼마나 닮았는지를 0~1로 묻고, 그 값을 설정의 기준과 견준다. 무엇으로 만든 값인지는
단계가 알지 못한다. 한쪽에 비교할 값이 없으면 닮았는지 알 수 없어 null이다(지문이 없는 사진은 자기 자신과도 견주지 못한다).

| 구현 | 값 | 상태 |
| --- | --- | --- |
| `FingerprintSimilarity` | 두 64비트 지문에서 같은 비트의 비율(`1 − 다른 비트 수 / 64`). 6비트 차이 0.906, 3비트 차이 0.953 | 1차 |
| 임베딩 | 코사인 유사도 | 후속(같은 인터페이스) |

## 하루 준비 (`DayPreparer`, #148)

입력 목록(번치 전체)을 받아 추천 하루별로 번들을 만들 준비를 한다(조합명세 5장). 저장하지 않고 판단만 돌려주며, 사진 자체는 바꾸지
않는다(빌린 값과 보정값은 결과에만 담긴다). 같은 사진이면 들어오는 순서와 상관없이 같은 결과가 나온다(1장 원칙 5, 8).

| 순서 | 하는 일 | 근거 |
| --- | --- | --- |
| 1 | 시각 정규화(`TimeNormalizer`): 현지 시각은 촬영 시각, 절대 시각은 현지 시각에서 오프셋을 뺀 값(없으면 `Asia/Seoul`). `day_key`는 날짜와 시각이 있으면 (현지 시각 − 5시간)의 날짜, 날짜만 있으면 그 날짜 | 5-2, X4 |
| 2 | 날짜·시각 빌리기(`DateBorrower`): 날짜를 모르는 사진은 날짜와 시각을, 시각 없는 사진은 시각을 닮은 사진에서 빌림. 빌린 뒤에도 날짜를 모르면 계산 제외(`excludedPhotoIds`) | 5-3, X2, 기획 원문 X2·X3 |
| 3 | 기기 시계 보정(`ClockCorrector`): 같은 하루에서 멤버의 사진과 다른 멤버의 닮은 사진의 시각 차이가 2쌍 이상이고 중앙값이 10분 이상이면 그 멤버의 그날 사진 시각을 중앙값만큼 옮김 | 5-5, X5 |
| 4 | 하루로 나눔. 보정으로 하루가 바뀐 사진이 있으면 오가는 하루를 `movedDays`에 담음 | 5-5 |
| 5 | 중복 묶음(`DuplicateGrouper`): 하루 안에서 연사(3초, 유사도 0.90)와 거의 같은 구도(120초, 0.95)를 이행적으로 묶음. 지문이 없는 사진과 시각이 없는 사진은 혼자 | 5-4, C1 |
| 6 | 하루 차단: 계산 대상 중 `PENDING`이 1장이라도 있으면 보류(`Held`), 아니면 확신도 0.50 이상의 민감 단서가 1장이라도 있으면 차단(`Blocked`), 아니면 준비됨(`Ready`) | 5-6, X6, X7, X12, E25 |

결과는 하루별 `DayPreparation`(`Ready`: 사진과 중복 묶음, `Held`: 대기 중인 사진, `Blocked`: 민감 단서)과 계산 제외 사진, 다시 계산할 하루
(`movedDays`)다. 쓸 수 있는 사진(`usable`)과 장 수 계산은 번들 이슈(#149, #150)가 한다.

## 이벤트 번들 (`EventFinder`, #150)

준비된 하루(`DayPreparation.Ready`)에서 이벤트를 찾아 이벤트 번들을 만든다(조합명세 6장). 저장하지 않고 결과(`EventResult`)만 돌려준다.
일반 번들(#149)은 확정된 이벤트의 시간 범위로 하루를 자르고, 범위 안의 나머지 사진과 번들이 되지 못한 이벤트의 단서 사진을 쓴다(7-2).

| 순서 | 하는 일 | 근거 |
| --- | --- | --- |
| 1 | 단서 사진(`EventClues`): 확신도 ≥ `clueMinConfidence`(0.70)인 단서를 가진 사진 중 원본 유형이 카메라이고 시각이 있는 사진. 품질과 문서 여부는 보지 않음. 기준선은 이 단계가 적용 | 3-1, 4-3, 5-1 |
| 2 | 이벤트 성립(`EventEstablisher`): 이벤트 종류마다 단서 사진을 이어짐 기준(짧은 2시간, 긴 4시간, 하루는 전체)으로 덩어리로 나누고, 덩어리 안에서 ① 강한 단서 + 확인 신호(다른 중복 묶음에도 같은 단서, 같은 이벤트의 다른 단서, 사람이 주인공), ② 보조 2종(약한 보조는 보조 1종 이상 뒤에 한 종까지), ③ 연말·명절의 보조 1종 + 날짜로 성립 | 6-1, 3-3, 3-5 |
| 3 | 같은 자리 정리(`EventPlaceMerger`): core가 겹치거나 공백이 `eventSamePlaceGap`(2시간) 미만인 이벤트는 연쇄까지 하나만 남김(단서 사진의 중복 묶음 수, STRONG 우선, 이른 core). 합쳐진 이벤트와 이유를 남김 | 6-2 |
| 4 | 시간 범위(`EventRangeBuilder`): core에서 앞뒤로 이어짐 기준 미만 공백만큼 넓히되 다른 이벤트의 core 앞에서 멈춤. 겹치면 core가 가까운 이벤트, 같으면 앞 이벤트. 하루 성격 이벤트는 하루에서 다른 이벤트 범위를 뺌 | 6-3 |
| 5 | 관련 사진(`EventPhotoCollector`): 범위 안의 단서 사진, 사람이 주인공인 사진. 범위 안의 나머지는 `leftoverPhotoIds` | 6-4, 7-2 |
| 6 | 번들 성립(`BundleEligibility`): 관련 사진 중 쓸 수 있는 사진의 중복 묶음 수 ≥ 6, 업로더 ≥ 2명. 못 채우면 없었던 것처럼 이벤트를 빼고(단서 사진은 `failed`에 담음) 남은 이벤트의 범위를 다시 계산, 바뀌지 않을 때까지 반복 | 6-4, 6-5, 3-1 |

쓸 수 있는 사진(카메라, 품질 낮음 아님, 문서 아님)과 장 수·업로더 수 계산(`BundleEligibility`)은 일반 번들(#149)도 같이 쓴다. 결과의 확정 이벤트는
`rule_trace`의 이벤트 항목(`trace()`)에 필요한 값(성립 근거, 강한 단서 사진, 확인 신호, 보조·약한 보조 종류, 합쳐진 이벤트, 범위, 관련 사진 구성)을 담는다.

## 일반 번들 (`GeneralBundleFinder`, #149)

준비된 하루와 이벤트 결과(`EventResult`)에서 일반 번들을 만든다(조합명세 7장). 저장하지 않고 결과(`GeneralResult`: 번들 목록과 번들이 되지 못한 조각의
사진 번호)만 돌려준다. 이벤트를 놓치거나 번들이 안 된 사진도 사진함에 남고 일반 번들로 갈 수 있어 사진이 추천에서 사라지지 않게 받는 단계다(7-10).

| 순서 | 하는 일 | 근거 |
| --- | --- | --- |
| 1 | 덩어리(`GeneralChunker`): 이벤트가 가져가지 않은 시각 있는 사진을 확정 이벤트의 범위로 자른 틈마다 하나, 각 이벤트의 `leftover`는 그 범위 안에서만 하나씩. 번들이 못 된 이벤트(`failed`)의 범위는 자르지 않음 | 7-1, 7-2 |
| 2 | 구간(`GeneralSegmenter`): 공백이 `minBoundaryGap`(20분) 이상인 곳을 경계로 나눔. 공백은 시각 있는 사진 전부(쓸 수 없는 사진 포함)로 재고, 구간의 대표 활동과 시간대, 업로더를 정함 | 7-3, 5-1 |
| 3 | 2·3순위(`GeneralPeopleTimeSplitter`): 공백이 큰 경계부터(같으면 이른 것) 한 경계에 처음 해당하는 규칙 하나만 적용. 사람 바뀜(앞뒤 구간 업로더가 안 겹치고 양쪽 전체가 3장 이상), 시간대 바뀜(시간대가 다르고 두 활동이 모두 알려져 있고, 공백이 더 긴 성격의 이어짐 기준 이상이고, 양쪽이 성립. 하루 성격은 시간으로 나누지 않음) | 7-4 |
| 4 | 5순위(`GeneralActivitySections`): 같은 활동의 이웃 구간을 합치고, `UNKNOWN` 구간은 공백이 짧은 쪽(같으면 앞) 활동 구간에 붙임(받는 쪽 이름은 그대로). 조각 전체가 `UNKNOWN`이면 하나 | 7-5 |
| 5 | 6순위(`GeneralSectionBalancer`): 성립 못 하는 활동 구간 중 장 수가 가장 적은 것을 공백이 짧은 쪽과 합치고 활동은 장 수가 많은 쪽을 따름(같으면 앞). 남은 경계는 양쪽이 모두 성립 | 7-6 |
| 6 | 7순위(`GeneralBigSplitter`): 40장 초과면 양쪽이 모두 성립하는 경계 중 공백이 가장 큰 곳(같으면 양쪽 장 수 차이가 작은 곳, 이른 곳)에서 나눔. 나눌 곳이 없으면 그대로. 나뉘면 `sub_index`를 1부터 | 7-7 |
| 7 | 추천 조건: 성립(장 수 ≥ 6, 업로더 ≥ 2)하고 쓸 수 있는 사진 활동 다수결이 `UNKNOWN`이 아님. 아니면 저장하지 않음 | 7-8 |

활동은 쓸 수 있는 사진만 세고 사진 한 장이 한 표다. 확신도가 `activityMinConfidence`(0.50) 미만이거나 분석 결과가 없는 사진은 `UNKNOWN`이다(13-5 X7).
다수결은 `UNKNOWN`이 절반 이상이면 `UNKNOWN`, 아니면 알려진 활동 중 많은 쪽이고, 같으면 확신도 합이 큰 쪽, 그다음 3-4 표의 앞쪽이다(7-3).
`rule_trace`의 `general`에는 적용한 규칙이 문자열로 남는다(처음은 조각의 출처 `outside_event_range` 또는 `event_leftover:종류`, 이어서 `rule2_people_change`,
`rule3_slot_change`, `rule6_join_section`, `rule7_split_big`을 `at 시각 gap 길이` 형식으로). 활동 구간은 번들이 잘려 나온 조각의 활동 구간 전체이다.

시각 없는 사진(날짜만 있음)을 번들에 붙이는 단계(7-9)는 이 단계의 결과 뒤에 이벤트·일반 번들이 모두 확정된 뒤에 하므로 포함하지 않는다. 결과에도
그런 사진은 없다.

시간·사람으로 묶었으므로, 연동 전에 대체 추천이 필요한지는 기획이 정한다(확정 대기).

## 정렬 기준 (`PhotoOrder`)

같은 입력이면 항상 같은 결과가 나오도록(조합명세 1장 원칙 5) 모든 단계가 사진을 같은 순서로 놓는다. **시각이 이른 쪽, 같으면 `photo_id`가
작은 쪽**(원칙 8)이고, 시각이 없는 사진은 시각이 있는 사진 뒤에 `photo_id` 순으로 놓는다(8-6). 시각은 호출하는 쪽이 넘긴다. 빌린 시각이나
보정한 시각(5-3, 5-5)을 쓰는 단계가 있기 때문이다.

## 해석한 부분 (제안)

| 항목 | 기본안 |
| --- | --- |
| 시각 상태 | 값으로 두지 않고 날짜·시각에서 계산한다. 값끼리 어긋난 입력을 만들 수 없게 하려는 것이다 |
| 사진 업로드 시각 | 사진이 처음 저장된 시각(`photos.created_at`)이다. 올린 사람별 시각이 아니다. 8-6의 "업로드 순"은 `photo_id` 오름차순으로 읽는다 |
| 원본 유형 `UNKNOWN` | 앱이 판단하지 못한 사진이다. 조합명세 3-6에는 없고 앱 답변에만 있는 값이며, 카메라가 아닌 사진으로 본다. #145는 `UNKNOWN`을 저장하지 않는다 |
| 원본 유형이 없는 사진 | 앱이 원본 유형을 보내기 전에 올라간 사진(값 없음)은 조합명세 4-4의 카메라 정의(제조사·모델 또는 촬영 시각이 있음)를 적용해, **촬영 날짜와 시각이 있으면 카메라, 없으면 저장 이미지**로 읽는다. 입력을 만들 때 한 곳(`RecoPhotoInputBuilder`)에서만 정한다. 현재 서버의 기존 사진은 테스트 데이터뿐이다 |
| 분석하지 않은 사진의 분석 상태 | 분석을 요청한 적이 없는 사진(저장된 상태가 없음)은 `PENDING`이 아니라 `FAILED`(4-3: 단서 없음, 활동 미상)와 같은 상태로 입력한다. `PENDING`이면 하루 전체가 영구히 보류되기 때문이다(5-6). 저장된 상태가 있으면 그대로 읽는다 |
| 품질 저장 | 조합명세 4-5의 `quality` 컬럼대로 등급(`GOOD`/`NORMAL`/`LOW`)을 업로드 때 계산해 저장한다. 기준값을 나중에 바꾸면 이미 저장된 등급은 옛 기준 그대로이므로, 필요하면 후속 이슈에서 다시 계산한다. 기존 사진의 품질은 채우지 않는다 |
| 해상도의 "원본" | 조합명세 4-4 표의 "원본 짧은 변"을 **서버가 받은 사진(앱이 줄인 JPEG)의 짧은 변**으로 읽는다. 흔들림·노출은 긴 변 1024px로 줄여 재고, 해상도만 줄이기 전 크기를 쓰라는 뜻으로 읽었다(4-2, 기능명세서 3.2.2). 앱이 줄이기 전 원본 크기를 뜻하면 앱에 선택 필드를 요청한다. 극단적인 파노라마(약 3:1)만 판정이 달라질 수 있다 |
| 같은 묶음 | 업로드 묶음 ID나 날짜 묶음 ID가 하나라도 같은 사진이 같은 묶음이다. 연쇄(A와 B, B와 C가 같은 묶음일 때 A와 C)는 잇지 않는다. 판단은 시각 없는 사진을 붙이는 단계(7-9)가 하고, 입력은 두 값을 담기만 한다 |
| 값 없는 품질 | 3-1이 "품질이 낮음이 아님"이라고 했으므로 낮음이 아닌 것으로 본다 |
| 모르는 활동 | 활동이 null이면 `UNKNOWN`과 같다 |
| 확인 신호 이름 | 6-1의 세 신호를 `SAME_CLUE_IN_OTHER_PHOTO`(①), `OTHER_CLUE_KINDS`(②), `PERSON`(③)으로 이름 붙였다 |
| 규칙 추적 구조 | 조합명세 11장은 JSON 예시만 있어 그 필드를 타입으로 옮겼다. 규칙·카드 선택 근거·합친 이유는 문자열이고, 활동 구간은 활동과 시간 범위로 두었다 |
| 시간대 경계 | 경계가 모두 정시라서 시(hour)로 가른다 |
| 설정 검증 | 가중치 합이 1이고, 시간대가 순서대로 시작하고, 카드 장 수 단계가 커지는 등의 검증은 개발이 더했다 |
| 관련 사진 | `EventResult`의 관련 사진은 장 수에 세는 사진이고, 단서 사진은 품질이 낮은 것까지 포함한다(6-4) |
| 1차 이미지 유사도 | 조합명세 4-2는 임베딩이지만 1차에서는 만들지 않고, 이미 저장하는 지문(dHash)으로 5-4·5-3을 판정한다. 기능명세서 4.2.8 로직 1의 "경량 이미지 비교"와 같은 방식이다. 지문 기준은 임베딩 기준과 따로 두고(`fingerprint…MinSimilarity`) 첫 값은 표와 같은 0.90, 0.95다(6비트, 3비트 차이까지). 지문은 밝기 변화만 보므로 각도가 다른 같은 장소는 못 찾고, 값은 실제 사진으로 조정한다(14장 V6). 지문으로 대신하는 방향은 기획이 확인했다(2026-11-18). 기준값 0.90, 0.95는 개발 제안이다 |
| 지문으로 하지 못하는 것 | 6-4 ③ 이벤트 「같은 장면」(0.85)과 8-4 카드 점수의 대표성은 지문으로 판정할 수 없어 1차에서 쓰지 않는다. 이벤트 관련 사진이 줄 수 있다 |
| 시계 보정의 쌍 | 5-5는 "같은 중복 묶음"의 쌍을 쓰라고 하지만 5-4의 중복 묶음은 시각 차이가 3초·120초 이내여야 해서, 시계가 10분 이상 어긋난 사진은 같은 묶음이 될 수 없다. 기획 원문 X5는 "다른 멤버의 같은 장면 사진과 시각 차이로 보정"이라고 하므로 쌍은 시각 조건 없이 같은 하루, 다른 멤버, 유사도 ≥ 거의 같은 구도 기준(0.95)으로 찾고 사진마다 가장 닮은 사진 하나만 쓴다. 보정 뒤에 중복 묶음을 만든다. 멤버의 사진은 그 멤버 혼자 올린 사진만 센다(여러 멤버가 올린 사진은 누구의 시계인지 모른다). 쌍의 중앙값은 짝수 개면 가운데 둘의 평균이다 |
| 시계 보정 대상 | 두 멤버가 서로 어긋나 있으면 누구의 시계가 틀렸는지 데이터로 알 수 없다. 가장 크게 어긋난 멤버부터 하나씩 보정하고(다시 비교), 같으면 그날 사진이 더 적은 멤버, 그래도 같으면 멤버 번호가 큰 멤버를 보정한다(먼저 온 멤버를 기준으로 봄). 쌍은 같은 하루 안에서만 만들어서, 하루 경계를 사이에 둔 두 사진은 짝이 되지 못한다 |
| 날짜를 빌릴 후보 | 날짜를 모르는 사진과 시각 없는 사진은 비교할 시각이 없으므로, 날짜와 시각이 있는 사진 중 유사도 ≥ 0.95인 사진에서 빌린다. 후보가 여럿이면 유사도가 높은 쪽, 같으면 같은 업로드 묶음, 그다음 시각이 이른 쪽, 사진 번호가 낮은 쪽이다. 빌린 사진에서 다시 빌리지 않는다(날짜가 이어 전해지지 않음) |
| 중복 묶음의 범위 | 중복 묶음은 하루 안에서만 만든다(번들은 하루를 넘지 않는다). 하루 경계 양쪽의 닮은 사진은 다른 묶음이다 |
| 하루 차단의 순서 | 분석 대기(보류)가 민감 단서(차단)보다 먼저다. 분석이 끝나야 민감 단서를 다 알 수 있기 때문이다(5-6 의사코드 순서) |
| 관련 사진의 「같은 장면」 | 6-4 ③(단서 사진과 유사도 0.85 이상)은 지문으로 판정할 수 없어 1차에서 쓰지 않는다(기획 확인, 2026-11-18). 그래서 이벤트 번들은 단서 사진과 사람이 주인공인 사진만 모으고 `relatedBy.sameScene`은 0이다. 식탁이나 방을 찍은 음식·장식 사진만 있는 파티는 관련 사진이 모자라 일반 번들로 갈 수 있다. 임베딩을 도입하면 추가한다 |
| 하루 이벤트의 범위 | 하루 성격 이벤트의 범위는 시각 구간이 아니라 그날의 사진 집합이므로, 그날 시각이 있는 사진 중 다른 이벤트가 가져가지 않은 것으로 하고 `range`는 그 첫 사진부터 마지막 사진까지로 표현한다. 같은 날 하루 이벤트가 둘이면 사진은 core가 가까운 이벤트에 간다(6-3의 겹침 규칙을 준용, 명세에 없음) |
| 시각 없는 사진 | 시각이 없는 사진(날짜만 있음)은 이벤트의 범위·관련 사진 계산에 끼지 않는다(7-9에서 붙임). 시각을 빌린 사진은 시각이 있는 것으로 본다 |
| 명절 날짜창 | 설·추석은 기존 `SpecialDayCalendar`의 설·추석 날짜 전체로 한다. 명세는 "당일과 앞뒤 하루"인데 표는 대체공휴일까지 담아 2027년 설은 하루 더 들어간다. 연결(캘린더 주입)은 조립 이슈(#152)가 한다 |
| 연말·명절 날짜창 | 연말은 설정에 두고, 명절 날짜는 이벤트 번들(#150)에서 기존 `SpecialDayCalendar` 재사용을 먼저 검토한다 |
| 활동 다수결의 한 표 | 7-3은 "쓸 수 있는 사진 활동 다수결"이라고만 한다. 사진 한 장이 한 표이고 중복 묶음으로 세지 않는다(장 수·업로더는 3-1대로 중복 묶음) |
| 구간의 업로더 | 7-4의 구간 업로더는 3-1처럼 그 구간의 쓸 수 있는 사진이 속한 중복 묶음의 업로더 합이다. 쓸 수 있는 사진이 없는 구간은 업로더가 비어 사람 바뀜 판단에서 빠진다 |
| 번들의 활동 | 번들의 `activity`와 `rule_trace`의 대표 활동은 활동 구간의 이름(7-5: `UNKNOWN`을 붙여도 받는 쪽 이름은 그대로)이다. 추천 조건(7-8)의 "조각 전체 대표 활동"은 번들 사진의 다수결로 따로 판단한다. 둘은 거의 같고, 다르면 추천 조건이 이긴다 |
| `UNKNOWN` 구간이 이어질 때 | 7-5 ②는 "공백이 더 짧은 쪽 이웃 활동 구간"이라고 한다. `UNKNOWN` 구간 사이에 다른 `UNKNOWN` 구간이 있으면 가장 가까운 알려진 구간까지의 시간으로 비교한다. 그 사이의 구간들도 같은 쪽으로 가서 활동 구간은 항상 이어진다 |
| 번들의 시작·종료 시각 | 번들 안 첫 사진과 마지막 사진의 시각이다. 자정을 넘기면 앱이 기능명세서 4.2.2의 「10월 19일~20일」 표시를 만들 수 있다. 이벤트 번들의 `range`와 같은 방식(조합명세는 일반 번들의 시각을 정하지 않음) |
| 시각 없는 하루의 번들 | 그날 시각 있는 사진이 하나도 없으면 기능명세서 4.2.7대로 하루 전체를 한 조각으로 본다(조합명세에 없음). 시작·종료 시각이 없어 하루 시작(05:00, 기본 시간대)으로 둔다 |
| 이벤트 범위 안 조각의 출처 | `rule_trace`의 `general.rules`는 조각의 출처(`outside_event_range`, `event_leftover:종류`)로 시작한다. 조합명세는 규칙 문자열의 형식만 예로 보인다 |

## 테스트 기준

- 설정 기본값이 12장 표와 한 값씩 같다. 시간대·카드 장 수 경계(04:59, 05:00, 12:00, 18:00, 5·6·15·16·25·26장)를 확인한다.
- 단서 매핑이 3-3 표와 같고, 모든 단서 코드가 한 이벤트 이상에서 쓰이고, 여러 이벤트에 걸친 단서는 꽃다발과 건배뿐이다.
- 이벤트와 활동의 성격이 3-5와 같고, 두 성격을 합치는 규칙, 활동 선언 순서가 3-4와 같다.
- 입력과 번들 타입의 불변식(시각만 있는 사진, 이벤트·일반 번들의 종류 조합, 카드 위치, 커버)을 확인한다.
- 정렬은 시각, `photo_id`, 시각 없는 사진, 입력 순서와 무관함을 확인한다.
- 품질은 선명·흔들린·어두운·과노출·작은 이미지를 4-4 표대로 판정하고, 경계값(60·200, 35·225, 60~200, 40%·10%, 480·1080)을 확인한다. 이미지를 읽지 못하면 품질이 없다. 업로드는 새 사진에만 품질을 저장하고 실패해도 성공하며, 있는 값은 바꾸지 않는다.
- 하루 준비는 하루가 05시에 끝나고(04:59와 05:00), 날짜·시각 모름이 닮은 사진의 값을 빌리고, 시계가 30분 느린 멤버가 2쌍 이상일 때 보정되고(1쌍과 10분 미만은 안 함), 보정 뒤에 같은 장면 사진이 한 묶음이 되고, 분석 대기는 보류, 확신도 0.50 이상의 민감 단서는 차단(0.49는 준비됨)임을 확인한다. 연사 3초·0.90, 거의 같은 구도 120초·0.95는 시간과 유사도 경계값으로 확인한다. 들어오는 순서를 바꿔도 결과가 같다.
- 이벤트 번들은 13-1의 E1부터 E30까지를 확인한다. 단서 한 장으로 단정하지 않고(확인 신호), 같은 이벤트의 이어진 덩어리 안에서만 단서를 세고(E24), 이어짐 기준(2시간 미만, 4시간 미만)과 날짜창(12/24~25, 12/31~1/1)의 경계를 확인한다. 같은 자리 이벤트는 하나만 남고(E9) 이유가 남으며, 번들이 되지 못한 이벤트는 단서 사진과 함께 `failed`에 들고 남은 이벤트의 범위가 다시 계산된다(E14, E15-1). 관련 사진은 단서 사진과 사람이 주인공인 사진이고, 품질이 낮은 단서 사진은 번들에 들지만 장 수에는 세지 않는다(E16).
- 입력 만들기는 함께 올린 사진을 한 장으로 합치고, 날짜만 있는 사진과 날짜 없는 사진을 포함하고, 작성 중·게시된 번들의 사진·준비되지 않은 사진·다른 번치 사진을 빼고, 오프셋·원본 유형(값 없는 경우 포함)·지문·날짜 묶음을 옮기고, 사진 번호 순으로 내놓음을 확인한다.
- 지문 유사도는 같은 지문 1.0, 모두 다른 비트 0.0, 순서와 무관함, 값 없는 쪽이 있으면 null임을 확인한다. 연사 기준은 6비트 차이까지, 같은 구도 기준은 3비트 차이까지 통과함을 경계값으로 확인한다.
- 일반 번들은 13-2의 G1부터 G14까지와 13-3의 R1·R2·R4·R4-1, 기능명세서 4.2.7의 예시(낮과 저녁 4시간 공백, 한쪽이 1장, 꾸준히 찍음, 자정을 넘긴 사진, 6장이어도 멤버 1명)를 확인한다. 이벤트 범위로 자르고(범위 안의 나머지는 따로, 번들이 못 된 이벤트의 범위는 안 자름), 공백 19분과 20분, 시간대 바뀜의 2시간 미만·이상(짧은 활동)과 4시간 미만·이상(긴 활동), 하루 성격은 시간으로 나누지 않음, 사람 바뀜(양쪽 3장, 멤버 겹침), 활동 다수결(확신도 0.49·0.50, 절반이 미상), `UNKNOWN` 구간 붙이기, 성립 못 하는 구간 합치기, 40장과 42장의 서브 번들을 경계값으로 확인한다. 모든 사진은 번들 하나 또는 번들이 못 된 조각 하나에만 있고(7-10), 입력 순서를 바꿔도 결과와 규칙 추적이 같다.
