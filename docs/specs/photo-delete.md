# 사진 삭제 계약

이 문서는 이슈 #39의 사진함 사진 삭제 API 계약을 고정한다. 기준은
기능명세서 3.3.5(사진 삭제), 3.5.2(사진 상세 ⋯), 3.6.1(번치 이탈 시 정리)이다.
영속성·삭제 경계는 [사진함 기반 영속성 계약](photo-foundation.md)을 따른다.

## 요청

`POST /api/v1/bunches/{bunchId}/photos/delete`

```json
{ "photoIds": [5021, 5018, 5002] }
```

- 인증이 필요하다. 해당 번치의 가입 완료 활성 멤버만 호출할 수 있다.
- `photoIds`는 1~50개이고, 중복이나 1 미만의 값이 없어야 한다.
- 상세 화면(3.5.2)의 삭제도 사진 1장을 담아 같은 API를 쓴다.

## 삭제 권한과 결과

사진마다 아래처럼 처리한다.

| 호출자 | 사진 | 결과 |
| --- | --- | --- |
| 올린 멤버 | 혼자 올린 사진 | 사진이 사라진다 |
| 올린 멤버 | 함께 올린 사진 (다른 업로더가 남음) | 호출자의 올린 사람 기록(프로필 배지)만 빠지고 사진은 남는다 |
| 올린 멤버 | 함께 올린 사진 (호출자가 마지막 업로더) | 사진이 사라진다 |
| 관리자(`OWNER`) | 올린 사람이 아닌 사진 (함께 올린 사진 포함) | 사진 전체가 사라진다 |
| 관리자(`OWNER`) | 자신이 올린 함께 올린 사진 | 올린 멤버와 같다: 배지만 빠진다 |
| 일반 멤버 | 다른 멤버만 올린 사진 | 403, 요청 전체가 거절된다 |

- 사진이 사라질 때 작성 중인 번들에서는 그 사진과 캡션이 빠지고, 사진이 0장이 된 번들은
  삭제된다. 이미 발행된 번들에는 이미지·순서·캡션이 남는다. 이 처리는 최종 삭제 콜백
  (#24)이 같은 트랜잭션에서 한다.
- 배지만 빠지는 경우에는 번들에 영향이 없다.
- 이미지 파일은 DB 커밋 뒤에만 정리한다.

## 전부 성공 또는 전부 실패

- 한 번의 요청은 하나의 트랜잭션이다. 하나라도 권한이 없으면 아무것도 지우지 않는다.
- 번치 → 사진 ID 오름차순 → 업로더 ID 오름차순으로 잠근다.
- 요청한 사진이 다른 번치의 것이거나 `READY`가 아니면 요청 전체를 400으로 거절한다.
- **이미 없는 사진 ID는 건너뛴다.** 응답을 잃어 다시 보내거나 다른 멤버가 먼저 지운 경우에도
  오류 없이 남은 사진만 처리한다.

## 응답

```json
{ "success": true, "data": { "deletedCount": 3, "uploaderRemovedCount": 2 } }
```

| 필드 | 설명 |
| --- | --- |
| `deletedCount` | 사진함에서 실제로 사라진 장수. 앱 토스트 「사진함에서 사진 N장이 삭제되었어요.」의 N이며 0이면 토스트를 띄우지 않는다 |
| `uploaderRemovedCount` | 함께 올린 사진이라 호출자의 배지만 빠지고 사진함에 남은 장수 |

## 오류

| 상태 | 경우 |
| --- | --- |
| 400 | 빈 목록, 51개 이상, 중복·1 미만 ID, 형식이 잘못된 본문, 다른 번치 또는 `READY`가 아닌 사진 포함 |
| 401 | 인증 없음 |
| 403 | 가입 미완료, 번치의 활성 멤버가 아님, 일반 멤버가 다른 멤버만 올린 사진을 포함 |
| 404 | 번치 없음 |

## 하루 업로드 한도와의 관계

하루 한도(번치마다 100장)는 사진함에 남아 있는 오늘 올린 사진을 센다(기획 확인). 따라서 삭제하면
그만큼 다시 올릴 수 있다. 이 API는 한도를 따로 갱신하지 않는다.

## 확정 대기

| 항목 | 기본안 | 확인 대상 |
| --- | --- | --- |
| 요청 형태(`POST .../photos/delete`)와 최대 50장 | 위 계약 | 앱 |
| 이미 없는 사진 ID는 건너뜀 | 위 계약 | 앱 |
| 공동 관리자 | 코드에 역할이 없어 관리자는 `OWNER`만 | 기획 |
