# 비동기 작업 처리 계약

업로드 응답과 분리해 실행하고, 실패하면 다시 시도하는 서버 작업의 공통 기반을 정의한다.
사진 처리 상태 전이와 이후 사진·후보·파일 정리 작업이 이 기반을 사용한다.
작업 종류별 처리 내용은 각 기능 Spec이 정한다. 이 문서는 작업의 저장·실행·재시도 규칙만 다룬다.

## 기준 문서

- [사진함 기반 계약](photo-foundation.md): `Photo.processingStatus`(`PENDING`, `READY`, `FAILED`)
- [번들 Spec](bundle.md): 추천 번들 재계산(§7.2)
- 기능명세서 `사진함_번들 만들기`: 3.1.4(처리 중인 사진은 회색 자리표시), 4.2.9(변경 5분 뒤 한 번 재계산)

## 모델

작업은 `async_jobs` 테이블의 한 행이다. 서버 메모리에만 두지 않으므로 재시작 후에도 남는다.

| 필드 | 의미 |
| --- | --- |
| `job_type` | 작업 종류. 종류마다 처리기 하나가 대응한다 |
| `target_key` | 작업 대상 식별 문자열(예: 사진 ID, 파일 public ID). 길이 255 이하 |
| `status` | `PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED` |
| `attempts` | 실행을 시작한 횟수. 점유할 때마다 1 증가한다 |
| `next_attempt_at` | 이 시각 이후에 실행할 수 있다 |
| `lease_until` | `RUNNING`일 때만 값이 있다. 이 시각이 지나면 중단된 것으로 본다 |
| `last_error_code` | 마지막 실패의 종류. 오류 원문·응답·인증 정보는 저장하지 않는다 |

- 같은 `job_type`과 `target_key`의 작업은 `PENDING` 또는 `RUNNING`인 동안 하나만 존재한다.
  이미 있으면 새로 등록하지 않는다. `SUCCEEDED`·`FAILED`가 된 뒤에는 같은 키로 다시 등록할 수 있다.
- 작업 등록은 소유 데이터를 바꾸는 트랜잭션 안에서만 한다(`MANDATORY`).
  소유 데이터가 롤백되면 작업도 함께 사라지고, 커밋되면 작업이 남는다.

## 상태 전이

```text
PENDING ─ 점유 ─▶ RUNNING ─ 성공 ─▶ SUCCEEDED
   ▲                 │
   │  실패(시도 횟수 < 최대)
   └─────────────────┤
                     └─ 실패(시도 횟수 ≥ 최대) 또는 알 수 없는 종류 ─▶ FAILED
```

- `RUNNING`인 작업의 `lease_until`이 지나면 다른 실행기가 다시 점유할 수 있다.
  이미 시도 횟수가 최대에 도달했다면 실행하지 않고 `FAILED`(`LEASE_EXPIRED`)로 끝낸다.
- 성공·실패 기록은 점유한 시도와 같은 `attempts`일 때만 반영한다. 점유가 만료돼 다른 실행기가 가져간 뒤에
  늦게 끝난 이전 시도가 결과를 덮어쓰지 못한다.

## 실행기

- 설정한 주기마다 실행 가능한 작업을 가져온다. 대상은 `PENDING`이고 `next_attempt_at`이 지난 작업과,
  `RUNNING`이고 `lease_until`이 지난 작업이다.
- 가져오는 조회는 `FOR UPDATE SKIP LOCKED`를 사용한다. 여러 서버나 여러 실행기가 동시에 돌아도 같은 작업을
  두 번 가져가지 않는다.
- 점유(`RUNNING`, 시도 횟수 증가, `lease_until` 설정)는 짧은 트랜잭션으로 커밋한다.
  처리기는 이 트랜잭션 밖에서 실행하므로 외부 호출 중 DB 잠금을 잡지 않는다.
- 처리기는 같은 작업이 두 번 실행돼도 안전해야 한다(멱등). 점유 만료나 응답 유실로 중복 실행될 수 있다.
- `RUNNING` 중에 같은 종류·대상으로 등록하면 새 작업이 만들어지지 않는다. 그래서 처리기는 등록 시점의 값이 아니라
  실행 시점의 최신 데이터를 읽어 처리해야 한다.
- 처리기가 예외를 던지면 실패로 기록한다. `last_error_code`에는 업무 오류 코드 또는 예외 클래스 이름만 남긴다.
- 처리기가 없는 종류는 재시도하지 않고 즉시 `FAILED`(`UNKNOWN_JOB_TYPE`)로 둔다.
- 로그에는 작업 ID와 종류만 남긴다. 대상 키가 비밀값을 담지 않도록 호출하는 쪽이 책임진다.

## 재시도 정책

실패 시 다음 시도 시각은 `기본 간격 × 2^(시도 횟수 − 1)`이며 1시간을 넘지 않는다.

| 설정 | 기본값 |
| --- | --- |
| `async-job.retry.max-attempts` | 5 |
| `async-job.retry.base-seconds` | 10 |
| `async-job.worker.lease-seconds` | 300 |
| `async-job.worker.poll-interval-ms` | 2000 |
| `async-job.worker.batch-size` | 10 |
| `async-job.worker.enabled` | `true` (테스트 프로필은 `false`) |

기본값은 처음 기준이며 운영하면서 조정한다. 위 값은 팀 확인이 필요한 항목이다(미정).

## 사진 처리 상태 전이

`Photo.processingStatus`는 `PENDING`에서만 `READY` 또는 `FAILED`로 바뀐다.

- `READY`와 `FAILED`는 종료 상태다. 다시 바꾸지 않는다.
- 이미 종료 상태이거나 사진이 삭제됐으면 변경하지 않고 "변경 없음"으로 응답한다. 반복 호출은 안전하다.
- `FAILED` 사진은 사진함 목록과 후보 계산에서 제외한다(각 조회 이슈에서 적용).

## 이 문서의 범위가 아닌 것

- 구체 처리기: 사진 `READY` 처리, 이미지 지문, 후보 재계산, 파일 삭제 재시도는 각 기능 이슈가 처리기를 추가한다.
- 실행 지연 갱신(마지막 변경 후 5분 뒤 한 번 실행)이 필요한 작업은 해당 이슈가 등록 방식을 확장한다.
- 작업 관리 화면, 수동 재실행 API, 메트릭 대시보드는 제공하지 않는다.
- 새 외부 의존성(메시지 큐, Redis 큐, 스케줄러 라이브러리)은 사용하지 않는다.

## 테스트 기준

실제 PostgreSQL에서 다음을 검증한다.

- 등록 → 실행 → 성공, 같은 키의 활성 작업 중복 등록 방지, 완료 후 재등록
- 실패 시 재시도 시각 계산, 최대 횟수 후 `FAILED`, 오류 원문 미저장
- 알 수 없는 종류의 즉시 실패
- 여러 실행기가 동시에 돌아도 작업별 한 번만 실행
- 점유 만료 작업의 재점유와 최대 횟수 도달 시 `FAILED`, 늦은 이전 시도의 결과 무시
- 트랜잭션 없는 등록 거부, 롤백 시 작업 미생성
- 사진 상태 전이 규칙과 반복·삭제된 사진 처리
