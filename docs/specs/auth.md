# 로그인·가입·초대 맥락 Spec

## 범위와 상태

기준 자료는 「BUNCH 상세 기능명세서 — 로그인·온보딩」(원본 파일명
`BUNCH_기능명세서_로그인온보딩.md`) 전체 중 1장이다. 원문 번호와 기능 ID는
[원문 추적표](#auth-traceability)에 보존한다. 2장의 번치 생성·초대 참여는
[온보딩 Spec](onboarding.md)이 담당한다.

- **요구사항**: 원문에서 제안으로 표시하지 않은 목표 동작이다. 구현 완료를 뜻하지 않는다.
- **제안**: 원문에 제안·협의·조건부 구현으로 명시된 사항이다. 확정 정책으로 사용하지 않는다.
- **미결정**: 원문 내부 충돌, 세부 정책 누락, 아직 합의하지 않은 API·스키마다.
- **현재 로컬 구현**: 작업 공간에서 확인한 미커밋 인증 코드다. 커밋된 릴리스나 운영 계약으로 간주하지 않는다.

현재 코드는 소셜 토큰 검증·회원 조회/생성·자체 토큰 발급/재발급·로그아웃까지다.
가입 단계, 약관, 개인 프로필, 번치·Membership, 초대 처리는 구현되어 있지 않다.
기존 인증 구현은 로컬 대기 상태로 유지하며 이 문서는 기능 코드를 변경하지 않는다.

[온보딩 공개 웹](onboarding.md#onboarding-public-web)에서 별도로 정의한다.

<a id="auth-launch"></a>
## 앱 실행과 도착지 — 1.1.1, 1.2.7~1.2.8

앱 실행 시 BUNCH 로고 스플래시를 표시한다. 링크로 열린 경우
[기기 초대 정보](#auth-invite-storage)를 먼저 보관한 다음 세션을 판단한다.
도착 화면이 정해질 때까지 스플래시를 유지하여 빈 화면을 보이지 않는다.

목표로 하는 서버 세션 확인 결과에는 가입 상태, 약관 동의 여부, 마지막 사용 번치의
유효 여부, 소속 번치 여부가 필요하다. **이 조회 API와 응답 필드는 아직 없다.**
현재 로그인 API의 토큰 응답만으로 이 결과를 알 수 있다고 가정하지 않는다.

| 조건 | 목표 도착지 |
| --- | --- |
| 로그인 정보 없음 또는 유지 불가 | Entry |
| 신규 계정 또는 가입 중·약관 미동의 | 약관 동의 |
| 가입 중·약관 동의 완료 | 프로필 설정 |
| 가입 완료·유효한 기기 초대 정보 있음 | [로그인 상태별 초대 처리](onboarding.md#onboarding-link-routing) |
| 가입 완료·초대 없음·마지막 번치 유효 | 그 번치 홈(번치 탭) |
| 마지막 번치 탈퇴·내보내짐·삭제, 다른 소속 번치 있음 | 소속 번치 중 가장 최근 사용한 번치 홈 |
| 가입 완료·소속 번치 0개 | [번치 시작 선택](onboarding.md#onboarding-start) |

분기는 사용자가 고르지 않고 서버의 가입 상태를 따른다. 가입 중 사용자는 번치 생성·참여
등 가입 후 기능에 접근할 수 없으며 미완료 단계로 보낸다. 백엔드도 이를 제한해야 한다.

마지막 사용 번치는 사용자별로 유지하고 번치 전환·생성·참여 완료 시 갱신한다.
마지막 번치가 무효여도 별도 안내 모달은 띄우지 않는다. 사유는 번치 전환 목록의
「삭제됨」/「내보내짐」 배지로 확인한다(BUNCH-04의 연계 요구).

인터넷 연결 없음, 세션 확인 응답 10초 이상 지연, 도착한 번치 홈 데이터 로딩 실패에는
「일시적인 오류가 발생했어요. 다시 시도해 주세요」를 표시한다. 탈퇴·이용 정지 계정의
세션은 해제하고 Entry로 보낸다. 장애 후 재시도 UI와 정지/탈퇴 판정 계약은 미결정이다.
같은 계정의 여러 기기 동시 로그인은 목표 요구사항이며 현재 토큰 정책과 충돌한다.

<a id="auth-entry"></a>
## Entry와 소셜 인증 — 1.2.1~1.2.6

### 공통 화면과 실패

신규·기존 회원은 같은 Entry를 쓴다. 이메일·비밀번호 입력, 별도 회원가입 버튼,
Entry에서의 약관 동의는 없다. 화면 진입만으로 인증을 자동 실행하지 않는다.
버튼 순서는 카카오(노란색) → Google(흰색) → Apple(검은색)이다.
Entry 로고·소개·일러스트는 디자인 확정 대기이며 버튼은 원문의
`Login Button - Brand`, `Login Button - Status`(Default/Pressed/Disabled)를 따른다.

한 버튼을 누르면 해당 버튼만 로딩하고 나머지 둘은 비활성화한다. 연타는 첫 탭만
처리한다. 소셜 창 취소, 소셜 오류, 네트워크·시간 초과, 서버 검증 실패 모두 Entry로
돌아와 「로그인에 실패했어요. 다시 시도해 주세요」를 표시하고 세 버튼을 Default로
복구한다. 별도 오류 화면으로 보내지 않으며 기기 초대 정보는 유지한다.
소셜 인증 완료 전 실패에는 신규 계정을 만들지 않는다. 비정상 반복 로그인 제한의
구체적인 횟수·기간·응답은 별도 협의 대상이다.

### 제공자별 목표 동작

| 제공자 | 네이티브 인증 및 정보 수집 | 예외·범위 |
| --- | --- | --- |
| Kakao / AUTH-01 | 공식 SDK, 카카오톡 로그인 우선·불가능하면 카카오 계정 로그인. 외부 웹 브라우저 왕복 방식은 쓰지 않는다. 회원 식별자만 요청하며 닉네임·사진·이메일은 요청하지 않는다. 결과를 서버 계정 확인으로 전달한다. | MVP 우선 구현 수단이며 Kakao만으로 가입→번치 생성까지 동작해야 한다. BUNCH 연결 해제 후 재로그인은 다시 인증하고 동일 소셜 식별자면 기존 BUNCH 계정 사용 |
| Google / AUTH-02 | 공식 로그인 기능 실행 후 서버 계정 확인 | 취소·오류는 공통 실패 처리, 초대 정보 유지 |
| Apple / AUTH-06 | iOS 기본 Apple 로그인 창. 고유 ID로 식별하고 이메일·이름을 필수값/식별값으로 쓰지 않는다. 이메일은 중계 주소일 수 있고 이름은 최초에만 제공될 수 있다. | 원문은 출시 전 Apple 로그인 제공을 요구한다. 탈퇴 시 Apple 연결 해제/토큰 취소는 탈퇴 명세에서 정의 |

Apple 탈퇴·토큰 취소는 **이번 스프린트 구현 범위 밖**이지만 **PRD에서 유지할 제품
요구사항**이다. 초기 기술 범위에서 제외되었다는 표기를 제품 전체 제외로 해석하지
않는다. 자동 계정 연결·병합은 원문에서 제공하지 않는 기능이다.

<a id="auth-account"></a>
### 계정 확인과 생성

선택한 버튼의 로딩을 유지한 채 별도 화면 없이 서버가 소셜 인증 결과를 검증한다.
소셜 종류와 고유 ID로 기존 계정을 찾고, 없으면 목표상 '가입 중' 계정을 만든다.
이메일·전화번호는 식별값이 아니며 소셜 닉네임·사진은 가져오지 않는다.

- `(provider, subject)` 유일성과 동시 요청 처리가 필요하다. 같은 사람의 다른 소셜
  로그인은 별도 계정이고 이메일이 같아도 자동 연결하지 않는다.
- 유효하지 않거나 만료·재사용된 인증 정보는 거부한다. 검증 성공 전 회원을 생성하지 않는다.
- 초대 정보는 인증 시 참여 처리하지 않는다. 인증 이후의 참여는 온보딩 책임이다.
  현재 로컬 로그인 요청에는 초대 필드가 없고, 향후 서버 전달 여부도 미결정이다.
- 탈퇴 후 같은 소셜로 돌아오면 이전 기록과 연결하지 않고 새 가입한다는 목표다.
  현재 로컬 구현에는 탈퇴 상태·식별자 해제 처리가 없다.
- 가입 중 30일 초과 계정 자동 파기는 정책 확정 후 적용한다. 현재 확정된 정리 작업이 아니다.

<a id="auth-terms"></a>
## 약관과 접근 권한 — 1.3.1~1.3.5

### 체크·원문·저장

약관 화면에는 뒤로가기, 「필수 항목 모두 체크하기」, 필수 3개, 권한 안내,
동의 완료 버튼을 둔다. 필수 항목은 서비스 이용 약관, 개인정보 수집·이용 동의,
만 14세 이상 확인이다. 연령 확인에는 원문이 없으며 마케팅 수신 동의는 받지 않는다.

전체 체크를 누르면 모두 선택하고 이미 전부 선택되면 모두 해제한다. 개별 체크는
전체 상태와 동기화한다. 전체 체크의 미선택 상태는 Disabled **모양**이어도 선택할 수
있어야 한다. 누르는 동안 Pressed, 전체 선택 시 Default 강조를 쓴다. `Terms Label`,
`Label - 01`은 원문 디자인 참조다. 세 항목을 모두 체크해야 완료 버튼이 활성화된다.

각 약관의 `>`는 앱 내부 상세 페이지로 이동한다. 항목 체크와 원문 열기를 구분하고,
원문을 보지 않아도 체크할 수 있다. 원문을 닫아도 체크를 유지한다. 현재 적용 중인
최신 버전을 보여주고, 완료 버튼 선택 시 항목별 버전·동의 일시·이력을 저장한다.
원문 로딩 실패에는 원문 화면 안에서 공통 일시 오류 토스트를 표시한다.
체크 자체는 저장 완료가 아니며 완료 전까지 화면에서 유지한다.

저장 중 연타는 무시한다. 저장 실패 시 체크를 유지하고 버튼을 복구하며 공통 일시 오류
토스트를 표시한다. **동의 저장 성공 후에만** 권한 요청을 시작한다.
약관 동의가 완료된 가입 중 사용자는 일반 재진입에서 약관을 건너뛰고 프로필로 간다.

### 권한 안내와 요청

사진 접근(앨범에서 불러오기), 카메라(촬영 업로드), 알림(활동·소식)은 모두 선택 권한이다.
권한 정보는 눌리지 않는 안내 영역이다. 위치 권한은 요청하지 않으며 촬영 위치는
사진 파일 EXIF에서만 읽는다는 목표다. 개인 프로필 사진의 저장 시에는 아래 규칙대로
불필요한 위치 메타데이터를 제거한다.

네이티브가 동의 저장 후 **사진 → 카메라 → 알림** 순으로 OS 권한을 요청한다.
허용·거부와 관계없이 다음 권한으로 진행하고 끝나면 프로필 화면으로 간다.
이미 허용/거부한 권한은 다시 요청하지 않는다. 사진 설명은 사진함·게시물·프로필에
쓸 사진 불러오기, 카메라 설명은 사진함·게시물용 촬영 목적을 알린다. 알림 시스템
팝업 문구는 커스텀하지 않는다.

알림 허용 기기는 서비스 알림을 받을 수 있어야 하며 같은 계정도 기기별 수신을
지원한다. 기기 등록·푸시 토큰 API/스키마는 아직 없다. 거부한 권한이 필요한 기능을
사용하면 안내하고 필요 시 설정 변경을 제공한다(사진·카메라·알림 세부 명세에서 구체화).
팝업 중 앱이 종료되면 동의는 이미 저장된 상태이므로 다음 실행은 프로필부터 시작하고,
남은 권한은 해당 기능 사용 때 요청한다.

약관 화면 뒤로가기는 로그인 상태를 해제하고 Entry로 이동하되 가입 중 계정과 진행
상태는 유지한다. 초대 삭제와의 충돌은 [미결정 사항](#auth-open-questions)에 기록한다.

<a id="auth-profile"></a>
## 프로필과 가입 완료 — 1.4.1~1.4.7

### 화면과 임시 상태

닉네임은 필수, 사진·출생연도·성별은 선택이다. 기본 원형 이미지와 카메라 버튼,
닉네임 `n/12`와 지우기 X, 출생연도 목록, 성별 선택, 「BUNCH 시작하기」를 표시한다.
원문의 `Profile Image`, `Cam Button - S`, `Labled_Text_Field`, `Year_Option`,
`Option` 상태를 따르며 placeholder·바텀시트/편집 문구는 디자인 확정 대기다.
성별 아래 「출생연도와 성별은 다른 사용자에게 공개되지 않아요.」를 표시한다.

입력은 가입 완료 전까지 화면 임시 상태다. 앱 종료 후 저장하지 않은 값은 유지하지
않고 초기화한다. 프로필 뒤로가기는 약관 화면으로 이동하고 기존 동의를 유지한다는
원문 요구가 있으나, 동의 완료자는 약관을 건너뛴다는 규칙과의 처리 우선순위는 미결정이다.

### 개인 프로필 사진

이미지/카메라 버튼은 「앨범에서 사진 선택 / 기본 이미지 적용 / 취소」를 제공하며
현재 기본 이미지이면 초기화 항목을 숨긴다. **카메라 아이콘 자체가 촬영 기능을
의미하지 않는다.** 사진은 1장만 선택하고 1:1 정사각형 영역·원형 가이드에서 확대·이동
편집 후 미리보기에 반영한다. 기본 이미지 적용도 가능하다.

사진은 가입 완료 때 최종 저장하며 1:1 비율과 JPEG·PNG·HEIC·WebP를 허용한다.
촬영 위치 등 불필요한 메타데이터는 제외한다. 미등록이면 기본 이미지이며 멤버 목록,
업로드 표시·번들 코멘트 등에 사용한다.

- 사진 접근 거부: 「권한 설정이 필요해요」 안내와 「취소 / 설정 열기」 제공.
- 선택한 사진만 허용: 허용된 사진 안에서 선택.
- 지원하지 않는 형식·손상 사진: 「이 사진은 사용할 수 없어요」, 기본 이미지 유지.
- 최종 사진 저장만 실패: 기본 이미지로 **가입은 완료**한다.

전송 방식(multipart·사전 업로드 등), 객체 저장소·URL/식별자, 변환 책임, 최대 용량·해상도,
압축 기준·임시 파일 정리·저장 실패 판정은 미결정이다. 허용 형식을 로컬 구현 지원
목록이나 확정 업로드 스키마로 해석하지 않는다.

### 닉네임 규칙과 중복 확인

화면에 보이는 글자 기준 1~12자이며 공백도 센다. 한글·영문 대소문자·숫자·공백을
허용하고 특수문자·이모지·줄바꿈은 금지한다. 저장 시 앞뒤 공백 제거·한글 NFC 정규화 후
서버가 길이와 문자를 최종 검증한다. 공백만 입력하면 0자로 보고 완료 버튼을 끈다.

일반 입력은 12자를 넘지 못하게 하되 한글 조합을 끊지 않고 조합 완료 후 판단한다.
붙여넣기에서 금지 문자는 제거한다. 붙여넣기 등으로 12자를 초과한 상태는
「입력 가능한 글자수를 초과했어요」와 함께 완료를 차단한다. 지우기 X는 입력 중에
표시하고 탭하면 비운다. 입력란은 Disabled/Default/Focused/Editing/Filled/Error 상태를 쓴다.

입력 정지 **0.5초 후** 앞뒤 공백을 제거한 값으로 서버 중복 확인을 한다.
전체 사용자에서 유일하되 대소문자는 구분하고 내부 공백도 비교에 포함한다
(`Bunch` ≠ `bunch`, `번치 클럽` ≠ `번치클럽`). NFC 정규화와 동일성 검증은 저장
규칙과 일치해야 한다. 확인 중·중복이면 가입 완료를 비활성화하고 결과 문구를 표시한다.
다시 입력하면 이전 결과를 지운다. 중복 조회 실패도 공통 일시 오류 토스트와 함께 완료를
차단하며 재입력/재시도로 재확인한다. 최종 저장에서 중복이 발생하면 가입을 완료하지
않고 「이미 사용 중인 이름이에요」를 표시하여 버튼을 비활성화한다.

### 선택 인구통계 정보

출생연도는 분석 목적으로 선택 수집한다. 목록 최상단은 「선택 안 함」이며 그 아래
`현재 연도 − 14`부터 1950년까지 내림차순이다. 고르면 목록을 닫고 표시하고 선택 안 함은
빈 값으로 돌린다. 서버도 선택 범위를 검증한다. 출생연도에서 나이를 다시 판정하지
않으며 만 14세 이상 여부는 약관의 연령 확인을 따른다.

성별은 여성/남성 중 하나만 고르고 같은 항목 재탭 시 해제한다. 둘 다 미선택 가능하다.
둘을 다른 사용자에게 공개하지 않는다. 분석용 선택 정보 수집의 별도 동의·보유기간 등은
[미결정 사항](#auth-open-questions)이며 필수 약관 동의가 자동으로 이를 해결하지 않는다.

### 가입 완료 처리

닉네임 규칙·중복 확인을 통과하면 버튼을 활성화한다. 사진·출생연도·성별 미입력은
가입을 막지 않는다. 탭 후 로딩하면서 프로필을 저장하고 서버는 닉네임을 최종 검증한다.
사진 저장 실패는 기본 이미지로 대체하지만, 프로필 저장 자체 실패는 가입을 완료하지
않고 오류 토스트·입력 유지·버튼 복구로 처리한다. 원문 오류 문구의 닫는 따옴표 누락은
의미를 바꾸지 않고 일시 오류 안내로 해석하며 최종 문구는 정리가 필요하다.

성공 시 가입 완료 시각과 '가입 완료' 상태를 기록하고 전체 서비스 사용을 허용한다.
초대가 없으면 번치 시작 선택으로, 있으면
[온보딩의 인증 후 자동 참여](onboarding.md#onboarding-link-routing)로 이동한다.
자동 참여 실패로 가입 완료를 취소하지 않는다. 성공/실패 후 화면은 온보딩 계약을 따른다.

## 기기 초대 정보 보관 — 1.5.1 / AUTH-05

이 절은 **기기 보관 생명주기의 단일 기준**이다. 링크 발급·서버 유효성·참여 조건·화면
분기는 [온보딩 초대 처리](onboarding.md#onboarding-link-routing)가 담당한다.
기기 보관 최대 24시간과 서버 초대 링크 유효기간 7일은 서로 다른 제한이다.
보관되어 있어도 서버 유효성이 보장되지 않는다.

| 시점 | 기기 보관 요구 |
| --- | --- |
| 링크로 앱 진입 | 세션 판단 전에 보관, 최대 24시간 유지 |
| 소셜 로그인 취소/실패, 약관·프로필 진행 | 유효한 초대 정보를 유지 |
| 신규 가입 완료/기존 회원 로그인 성공 | 보관된 초대로 온보딩 참여 처리, 신규는 시작 선택·만들기를 건너뜀 |
| 참여 처리 완료 | 보관 정보 삭제 |
| 보관 후 24시간 경과 | 초기화하여 초대 없음으로 처리; 시작 선택의 링크 입력 경로로 재참여 가능 |
| 로그아웃 | 보관 정보 삭제(약관 뒤로가기와 충돌하는 경우는 미결정) |
| 초대 확인 화면에서 명시적으로 참여 중단 | [온보딩 중단 규칙](onboarding.md#onboarding-join-cancel)에 따라 삭제 |
| 설치 과정에서 정보 소실 | 가입 후 시작 선택; 원래 링크 재클릭 또는 앱에 붙여넣기로 복구 |

인증 완료 전 여러 링크를 열었을 때 **가장 최근 링크만 유지**하는 것은 원문의 **제안**이다.
확정 우선순위·교체 UI·저장 매체/필드·24시간 계산 기준·실패 후 재시도용 보관 여부는
아직 정하지 않았다. 인증 직후 자동 참여 및 이미 멤버인 경우 등의 삭제 시점도
참여 결과와 함께 계약을 구체화해야 한다.

<a id="auth-local-api"></a>
## 현재 로컬 인증 구현과 API

아래는 `src/main/kotlin/com/bunch/auth/AuthController.kt`,
`src/main/kotlin/com/bunch/auth/AuthService.kt`,
`src/main/kotlin/com/bunch/member/Member.kt` 파일을 읽어 확인한 **미커밋 로컬
구현**이다. 제품 목표의 가입 상태·약관·초대 API가 구현되었다는 뜻이 아니다.

| API | 현재 요청/인증 | 현재 성공 결과 |
| --- | --- | --- |
| `POST /api/v1/auth/apple/login` | JSON `idToken`, 원본 `nonce` 필수 | 자체 access/refresh token |
| `POST /api/v1/auth/google/login` | JSON `idToken` 필수 | 자체 access/refresh token |
| `POST /api/v1/auth/kakao/login` | JSON `idToken`, `nonce` 필수 | 자체 access/refresh token |
| `POST /api/v1/auth/reissue` | JSON `refreshToken` 필수 | 자체 access/refresh token 교체 |
| `POST /api/v1/auth/logout` | Bearer access token | `success: true`, `data: null`, `error: null` |

로그인·재발급은 공개 요청이고 로그아웃은 인증이 필요하다. 쿠키 입력과 `Set-Cookie`는
사용하지 않는다. 로그인/재발급 성공 응답은 다음과 같다(예시 값은 실제 토큰이 아니다).

```json
{
  "success": true,
  "data": {
    "accessToken": "<accessToken>",
    "refreshToken": "<refreshToken>"
  },
  "error": null
}
```

실패도 `success / data / error` envelope이며 `error`에는 `code`, `message`, `detail`이 있다.
현재 주요 오류는 입력/JSON 400, 잘못된 JWT 형식 `AUTH_008` 400, 소셜 검증
`AUTH_009`·nonce 불일치 `AUTH_010`·ID 토큰 재사용 `AUTH_011` 401,
미인증 `AUTH_001` 401, 제공자 검증 기반 사용 불가 `AUTH_014` 503,
이미 로그아웃 `AUTH_007` 400이다. 화면의 한국어 안내와 현재 서버 message key를
동일한 확정 문구로 취급하지 않는다.

### 현재 ID 토큰·회원 처리

- 제공자별 RS256 서명·JWKS, issuer, 허용 audience, 만료·발급 시각·subject 및
  존재 시 nbf를 검증한다. 현재 시간 허용 오차는 60초이며 JWT 인코딩도 검사한다.
- Apple은 앱이 로그인에 넣은 SHA-256 nonce와 서버에 전달한 원본 nonce를 비교한다.
  Kakao는 로그인 요청 nonce와 claim을 그대로 비교한다. 둘은 필수이고 Google은
  서버 Client ID를 audience로 검증하며 현재 nonce를 요구하지 않는다.
- 검증 후 ID 토큰 digest를 Redis에 원자 등록하여 재사용·동시 재사용을 거부한다.
  기록은 만료 시각 + 60초까지 유지하고 임의 TTL 상한을 두지 않는다. 원문 ID 토큰은
  저장하지 않는다. 토큰·비밀값·인증 헤더는 로그나 문서에 기록하지 않는다.
- 회원/소셜 식별자는 별도 테이블이며 `(provider, provider_subject)` 유일성을 둔다.
  PostgreSQL 트랜잭션과 식별자별 잠금으로 동시 최초 로그인 중복 생성을 방지한다.
- 검증된 이메일만 선택 저장하며 이메일은 유일 키가 아니다. 비밀번호는 저장하지 않는다.
  Kakao에서 이메일을 요청하지 않는 목표와, 이미 전달된 검증 이메일을 저장할 수 있는
  현재 구현은 구분한다. 향후 이메일 최소 수집 정책은 확인이 필요하다.
- 현재 회원은 ID·이메일·역할을 가지며 가입 상태·약관·프로필·정지/탈퇴 상태가 없다.
  생성 즉시 `ROLE_USER` 토큰을 발급하고 현재 보안 필터는 JWT를 검증할 뿐 가입 완료나
  계정 정지 여부를 조회하지 않는다. 목표 접근 제한을 이미 충족한다고 볼 수 없다.

### 현재 자체 토큰 정책과 다중 기기 충돌

`src/main/kotlin/com/bunch/auth/security/TokenProvider.kt`와
`src/main/kotlin/com/bunch/auth/redis/RefreshTokenRedisRepository.kt`의
현재 정책은 다음과 같다. **제품의 최종 토큰 정책으로 확정한 값이 아니다.**

| 항목 | 현재 로컬 구현 | 목표/미결정 영향 |
| --- | --- | --- |
| 수명 | access 7일, refresh 14일 | 제품 최종 수명은 별도 합의 필요 |
| 식별 | 토큰 종류 분리, 발급별 고유 jti | 기기/세션 모델 미정 |
| refresh 보관 | 회원당 1개, 로그인 시 기존 값 대체 | 두 번째 기기 로그인은 첫 기기의 refresh를 무효화하므로 여러 기기 세션 유지 목표와 충돌 |
| 재발급 | 기존 값 비교+새 값 저장을 원자 처리, 이전/동시 재사용 거부 | 기기별 재발급 정책 미정 |
| 로그아웃 | 회원 refresh 삭제, access는 만료 전까지 유효 | 기기별/전체 로그아웃 구분 및 access 즉시 차단 여부 미정; 현재 기능은 기기별 로그아웃이 아님 |

| 다중 기기 인증·알림 | 기기별 세션·알림 수신 | 기기 식별·토큰 모델·등록 API 미정 |
| 초대 전달 | [기기 보관](#auth-invite-storage)에서 [온보딩 참여](onboarding.md#onboarding-join)로 연결 | 로그인 요청에 초대를 추가할지 등 미정; 현 API에는 없음 |

여기의 데이터는 요구 의미이며 DB 컬럼명·DTO·경로·HTTP 오류 계약을 새로 확정하지 않는다.

## 검증 상태와 후속 확인

이번 문서 작업에서는 원문 전체·현재 소스·테스트 정의를 읽고 추적표와 상대 링크를
대조한다. 기존 자동 테스트의 과거 통과 표시를 현재 완료 체크로 옮기지 않는다.
아래는 구현·재검증에 필요한 조건이며 **현재 통과 결과가 아니다.**

- [ ] 세 제공자 로그인·재로그인, nonce·서명/claims·재사용 거부, 이메일 누락/상이 제공자·동시 가입 자동 테스트 재실행
- [ ] 실제 PostgreSQL·Redis에서 `DB_URL=jdbc:postgresql://localhost:5432/bunch_test ./gradlew clean build` 실행
- [ ] 실제 iOS SDK와 WebView 브리지·권한 거부/제한·앱 종료 재개 수동 검증
- [ ] 세션/가입 상태 제한·약관 버전/저장·프로필 규칙과 경합·사진 실패 후 가입·0개 번치 도착지 검증
- [ ] 초대 24시간 보관·취소/실패·로그아웃·인증 후 자동 참여·여러 기기 정책 검증

체크리스트는 목표·후속 확인 항목이며 과거 실행 이력이 아니다. 빌드·DB/Redis 테스트 등
전체 작업의 실제 실행 결과는 PR 또는 완료 보고에서 확인한다. 실제 SDK 검증은 자동
테스트와 구분하며, 문서 추적 검사는 구현 검증을 대체하지 않는다.
