# 날짜 미확인 사진 목록·사진 상세 조회 계약

이 문서는 이슈 #36의 두 API 계약을 고정한다. 「촬영 날짜를 확인할 사진」 영역에 쓰는 미확인 목록과 사진 한 장을
크게 보는 상세다. 사진함 목록은 [사진함 목록 조회 계약](photo-list.md), 삭제는 [사진 삭제 계약](photo-delete.md),
날짜 변경(#37)은 [사진 촬영 날짜 변경 계약](photo-date.md), 번치 이탈 정리(#38)는 이 범위에 포함하지 않는다.

## 기준 문서

기능명세서(1101 기준)는 사진함 3.1.1~3.1.5, 3.3.1, 3.5.1, 3.5.2, 번들 만들기 4.1.1을 따른다.
영속성은 [사진함 기반 계약](photo-foundation.md), 사진 저장 규칙은 [사진함 업로드 계약](photo-box.md)을 따른다.
**와이어프레임과 기능명세서가 다르면 기능명세서를 따른다.** 다른 곳은 아래 "와이어프레임과 다른 점"에 적었다.

이 문서는 값을 세 가지로 나눠 적는다.

| 구분 | 뜻 |
| --- | --- |
| 확정 | 기능명세서가 정한 것. 근거 조항을 적는다 |
| 제안 | 명세서가 정하지 않아 개발이 기본안으로 구현한 것. "확정 대기"에 모은다 |
| 미정 | 명세서와 충돌할 수 있어 구현하지 않은 것 |

## 날짜 미확인 목록

```text
GET /api/v1/bunches/{bunchId}/photos/undated
```

| 항목 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `bunchId` (경로) | Long | O | 조회할 번치 |
| `memberId` | Long | 선택 | 이 멤버가 올린 사진만 조회한다. 없으면 전체 |
| `cursor` | String | 선택 | 이전 응답의 `nextCursor`. 없으면 첫 페이지 |
| `size` | Int | 선택 | 한 번에 가져올 장수. 기본 60, 1~100 |

- 인증이 필요하다. 가입을 완료한 그 번치의 ACTIVE 멤버만 조회할 수 있다(3.1.1).
- 사진함 목록과 같은 `memberId`·`cursor`·`size` 규칙을 쓴다. `cursor`는 앱이 해석하지 않고 그대로 되돌려 보낸다.

### 응답

```json
{
  "success": true,
  "data": {
    "totalCount": 12,
    "photos": [
      {
        "photoId": 5021,
        "thumbnailUrl": "https://res.cloudinary.com/demo/image/upload/c_fill,w_300,h_300/photos/a.jpg",
        "uploaderIds": [12, 15],
        "usedInDraftBundle": false
      }
    ],
    "nextCursor": "dXw1MDIx"
  },
  "error": null
}
```

| 항목 | 설명 |
| --- | --- |
| `totalCount` | **멤버 필터를 적용한** 날짜 미확인 사진 수. 「촬영 날짜를 확인할 사진 N장」의 N이다(3.1.2 로직 3, 3.1.5 상세 1). `size`와 무관하다 |
| `photos[].photoId` | 사진 ID |
| `photos[].thumbnailUrl` | 정사각형 썸네일 URL(300px). 별도 배지는 붙이지 않는다(3.1.4) |
| `photos[].uploaderIds` | 올린 멤버 ID 목록. 함께 올린 사진은 여러 명이며 올린 순서다. 닉네임·프로필은 `GET /api/v1/bunches/{bunchId}/members`(#43)를 쓴다 |
| `photos[].usedInDraftBundle` | 작성 중인(초안) 번들에 들어 있는 사진이면 `true`. 발행된 번들에만 쓰였거나 안 쓰였으면 `false`. 선택 모드에서 삭제할 때 확인 창의 문구를 고르는 데 쓴다(3.1.5 상세 4, 3.3.5) |
| `nextCursor` | 다음 페이지 시작 위치. 마지막 페이지면 `null` |

날짜가 없는 사진만 나오므로 사진함 목록과 달리 `capturedDate`·`capturedTime`이 없다.

### 규칙

| 규칙 | 내용 | 구분 | 근거 |
| --- | --- | --- | --- |
| 대상 | 촬영 날짜가 없는 사진. 사용자가 날짜를 조정한 사진은 날짜가 생겨 제외된다 | 확정 | 3.1.5 로직 1, 2 |
| 정렬 | **업로드 최신순**: 나중에 올라온 사진이 앞(`photoId` 내림차순). 함께 올린 사진은 처음 올린 시점 기준 | 확정, 함께 올린 사진의 기준은 제안 | 3.1.5 상세 2 |
| 멤버 필터 | `memberId`를 따른다. 함께 올린 사진은 올린 멤버 모두의 필터에서 보인다. `uploaderIds`에는 필터와 무관하게 모든 올린 멤버가 들어간다 | 확정 | 3.1.2 로직 2, 3 |
| 처리 상태 | `READY` 사진만 내려준다. 새 사진은 저장 즉시 `READY`라서 처리 중인 사진은 생기지 않는다 | 미정 (아래 확정 대기) | 3.1.4 로직 2 |
| 번들에 쓰인 사진 | 제외하지 않는다 | 확정 | 4.1.1 로직 1, 4 |
| 이어서 불러오기 | 사진함 목록과 같은 방식. 서버는 `size + 1`장을 읽어 다음 사진이 있으면 `nextCursor`를 만든다 | 제안 | 3.1.3 로직 4 |
| 두 화면에서 쓴다 | 사진함과 번들 만들기가 같은 영역과 N을 쓴다 | 확정 | 4.1.1 로직 1 |

앱은 영역을 처음에 접힌 상태로 둔다(3.1.5 상세 2). 접힌 동안은 「N장」만 필요하므로 `size=1`로 불러 `totalCount`를 쓰고,
펼칠 때 사진을 불러올 수 있다. 멤버 칩을 바꾸면 N도 다시 받는다. 날짜 미확인 사진이 0장이면 영역을 숨긴다(3.1.5 예외).

### 이어서 불러오기

- 정렬 키 `photoId`(내림차순) 기준의 커서 방식이다. 페이지 사이에 사진이 올라오거나 지워져도 이미 받은 사진이
  중복되거나 빠지지 않는다.
- 커서는 위치를 담은 불투명한 문자열이다. 사진함 목록의 커서와 서로 바꿔 쓸 수 없고, 해석할 수 없는 값은 400이다.
- 다른 멤버가 올리거나 지운 사진은 실시간으로 반영하지 않는다. 앱이 진입·복귀·새로고침 때 다시 부른다(3.1.1 로직 2).

## 사진 상세

```text
GET /api/v1/bunches/{bunchId}/photos/{photoId}
```

| 항목 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `bunchId` (경로) | Long | O | 사진이 속한 번치 |
| `photoId` (경로) | Long | O | 볼 사진 |

- 인증이 필요하다. 가입을 완료한 그 번치의 ACTIVE 멤버만 조회할 수 있다.
- 선택 모드에서는 사진을 눌러도 상세로 가지 않는다(3.3.1 상세 4). 앱의 동작이다.

### 응답

```json
{
  "success": true,
  "data": {
    "photoId": 5021,
    "imageUrl": "https://res.cloudinary.com/demo/image/upload/photos/a.jpg",
    "capturedDate": "2026-10-19",
    "uploaders": [
      {
        "memberId": 12,
        "nickname": "멤버 A",
        "imageUrl": "https://res.cloudinary.com/demo/image/upload/profile/k.jpg"
      },
      {
        "memberId": 15,
        "nickname": "멤버 B",
        "imageUrl": null
      }
    ],
    "usedInDraftBundle": true
  },
  "error": null
}
```

| 항목 | 설명 |
| --- | --- |
| `photoId` | 사진 ID |
| `imageUrl` | 사진함에 보관된 원본 이미지(긴 변 2560px). 앱이 화면 너비에 맞춰 보여준다(3.5.1 상세 2, 3.3.3 로직 2) |
| `capturedDate` | 촬영 날짜. 사용자가 조정한 사진은 조정한 날짜. 날짜를 알 수 없으면 `null`이며 앱이 「날짜 미확인」만 보여준다(3.5.1 예외) |
| `uploaders[]` | 올린 멤버, 올린 순서. 함께 올린 사진이면 여러 명이고 앱이 올린 사람 수만큼 배지를 세로로 나열한다(3.5.1 상세 4) |
| `uploaders[].memberId` | 멤버 ID |
| `uploaders[].nickname` | 멤버의 **현재** 닉네임. 프로필 배지는 현재 프로필을 따른다(3.5.1 로직 2) |
| `uploaders[].imageUrl` | 멤버의 **현재** 프로필 이미지 또는 `null`. `null`이면 앱이 기본 프로필 이미지를 쓴다(3.5.1 상세 3) |
| `usedInDraftBundle` | 작성 중인(초안) 번들에 들어 있는 사진이면 `true`. 발행된 번들에만 쓰였거나 안 쓰였으면 `false`. 앱이 「삭제」 확인 창의 문구를 고르는 데 쓴다(3.5.2, 3.3.5). 사진이 사라지면 서버가 초안에서도 빼므로 삭제 전에 따로 확인하는 API는 없다 |

### 규칙

| 규칙 | 내용 | 구분 | 근거 |
| --- | --- | --- | --- |
| 출력 | 사진, 촬영 날짜, 올린 멤버 프로필 배지 | 확정 | 3.5.1 출력 |
| 내려주지 않는 값 | 장소, 촬영 시각, 업로드 날짜, 위치 정보, 이전·다음 사진 ID, 메뉴 권한 | 확정 | 3.5.1 상세 1, 상세 6, 로직 1, 예외 |
| 이전·다음 이동 | 앱이 사진함 순서로 처리한다 | 확정 | 3.5.1 상세 6 |
| 메뉴 표시 | 「날짜 바꾸기」·「삭제」는 사진을 올린 멤버와 관리자에게만 보인다. 앱이 `uploaders`와 번치 멤버 목록의 `role`로 판단한다 | 확정(권한), 판단 주체는 제안 | 3.5.2 로직 2 |
| 없는 사진 | 번치에 없거나 지워진 사진, 다른 번치의 사진, 처리가 끝나지 않은 사진은 404. 앱이 「삭제된 사진이에요」 토스트 뒤 사진함으로 돌아간다 | 확정 | 3.1.3 예외, 3.5.1 예외 |

## 와이어프레임과 다른 점

아래는 와이어프레임이 기능명세서와 달라서 **기능명세서를 따른** 곳이다.

| 와이어프레임 | 기능명세서 | 서버 |
| --- | --- | --- |
| 「9월 12일 화요일 · 한남동」 같은 장소 | 장소 줄은 없다. 촬영 위치는 저장하지 않는다(3.5.1 상세 1, 로직 1) | 장소를 내려주지 않는다 |
| 날짜 없는 사진의 「알 수 없음 · 10월 11일 업로드」 | 날짜 자리에 「날짜 미확인」만 보여준다(3.5.1 예외). 「일 업로드」 같은 문구는 명세서에 없다 | 업로드 날짜를 내려주지 않는다 |
| 헤더 제목 「사진」, 배지가 사진 아래쪽 | 헤더에 촬영 날짜, 배지는 사진 오른쪽 위(3.5.1 상세 1, 3) | 앱·디자인 사항이라 서버와 무관하다 |

## 오류

| 상태 | 코드 | 상황 |
| --- | --- | --- |
| 400 | `COMMON_001` | (미확인 목록) 해석할 수 없는 `cursor`, `size`가 1~100이 아님, 숫자가 아닌 값, 번치 멤버가 아닌 `memberId`. (상세) `photoId`가 숫자가 아님 |
| 401 | `AUTH_001` | 토큰 없음·만료·세션 없음 |
| 403 | `AUTH_015` | 가입이 끝나지 않음 |
| 403 | `AUTH_002` | 번치 멤버가 아님(나간 멤버 포함) |
| 404 | `RESOURCE_001` | 번치 없음. (상세) 사진 없음·다른 번치의 사진·`READY`가 아닌 사진 |

확인 순서는 가입 완료(403) → 번치 존재(404) → 번치 소속(403) → 입력(400) → 사진(404)이다.

## 인덱스

별도 인덱스를 만들지 않는다. 번치당 사진은 최대 1,000장(3.2.1)이라 번치로 거른 뒤 날짜 없는 사진을 고르고 정렬해도
부담이 없다. 한도가 크게 늘거나 느려지면 그때 새 마이그레이션으로 추가한다.

## 확정 대기

| 항목 | 기본안 | 확인 대상 |
| --- | --- | --- |
| 미확인 목록을 `cursor`·`size`로 나누는 방식. 3.1.5는 나누는지 정하지 않았다 | 사진함 목록과 같은 방식 | 앱 |
| 영역 제목의 N을 어떻게 받는지 | 미확인 목록의 `totalCount`(접힌 동안은 `size=1` 호출) | 앱 |
| "업로드 최신순"의 기준(함께 올린 사진) | 처음 올린 시점(`photoId` 순) | 기획 |
| 「날짜 바꾸기」·「삭제」 메뉴를 앱이 판단하는지 | `uploaders`와 번치 멤버 목록의 `role`로 앱이 판단. 공동 관리자도 허용(명세서 5.6.2)이지만 코드에는 아직 역할이 없어 `OWNER`만 | 앱, 번치·멤버 담당 |
| **처리 중인 사진을 회색 자리표시로 보여주기**(3.1.4 로직 2) | 지금은 새 사진이 바로 `READY`라 처리 중인 사진이 없어 `READY`만 내려준다. 처리 단계가 생기면 두 API에 `processingStatus`를 더한다 | 기획 |

## 테스트 기준

- 미확인 목록 대상: 날짜가 없는 `READY` 사진만 나온다. 날짜가 있는 사진, 날짜를 조정한(`USER`) 사진, `READY`가 아닌 사진,
  다른 번치의 사진은 나오지 않는다.
- 정렬: 업로드 최신순(`photoId` 내림차순).
- 이어서 불러오기: 페이지 크기 1~10으로 끝까지 따라가면 모든 사진을 한 번씩만 만난다. 마지막 페이지의 `nextCursor`는 `null`이다.
  사진함 목록의 커서는 이 목록에서 거절된다.
- 멤버 필터: 함께 올린 사진이 올린 멤버 모두에게 보이고, `uploaderIds`는 필터와 무관하게 모든 올린 멤버를 담는다.
  번치 멤버가 아닌 `memberId`는 400이다.
- `totalCount`: 필터를 적용한 미확인 수이고 `size`와 무관하다. `uploaderIds` 순서, 썸네일 주소, 빈 목록도 확인한다.
- 상세 응답: `photoId`, `imageUrl`, `capturedDate`, `uploaders[]`, `usedInDraftBundle`만 있고 장소·촬영 시각·업로드 날짜·위치는 없다.
  `usedInDraftBundle`은 초안에 든 사진만 `true`이고 발행된 번들에만 쓰인 사진은 `false`다. 미확인 목록 항목도 같다.
  날짜가 없으면 `capturedDate`가 `null`이다.
- 상세 올린 멤버: 올린 순서, 현재 닉네임, 프로필 이미지가 없으면 `null`, 프로필 이미지를 바꾸면 바뀐 값이 나온다.
- 상세 404: 없는 사진, 다른 번치의 사진, `READY`가 아닌 사진.
- 권한·입력: 비멤버·나간 멤버·가입 미완료·없는 번치·토큰 없음, 잘못된 `cursor`·`size`·`photoId`.
