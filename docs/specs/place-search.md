# 번들 장소 검색 결과 입력 계약

#126, DRAFT-17·FEED-10. **검색은 프론트가 처리하고 서버는 선택한 결과값만 받는다.**
2026-11-10 사용자 답변과 2026-11-11 재전달에서 이 경계를 확정했다.
서버 검색 API·공급자 클라이언트·검색용 자격증명·캐시는 추가하지 않는다.
공급자 선택과 호출 방식은 프론트 책임이며 서버가 카카오로 고정하지 않는다.

검색·취소·빈 결과·검색 실패만으로 서버 저장값을 바꾸지 않는다.
네트워크·API 오류 토스트는 「일시적인 오류가 발생했어요. 다시 시도해 주세요」이며 검색어를 유지한다.
검색은 키워드만 사용한다. 위치 권한·현재 위치·좌표·EXIF·내 주변 검색은 추가하지 않는다.
장소와 지역을 따로 제한하지 않으며, 주소 없는 지역도 아래 null 계약으로 저장할 수 있다.

## 입력·응답

[번들 장소](bundle-locations.md)의 기존 `BundleLocationInput`과 저장 경로를 재사용한다.

```json
{"provider":"example-provider","externalId":"region-01","name":"여의도","address":null,"position":0}
```

- provider는 공급자 구분 문자열이며 기존 trim·소문자 ASCII 1~32자 규칙을 따른다.
  예제의 값은 실제 공급자 선택이 아니다.
- externalId는 공급자의 문자열 ID를 보존하고 trim한다. 임의 ID를 생성하거나
  숫자로 변환해 선행 0·대소문자를 바꾸지 않는다.
- name은 실제 검색 결과의 장소명/지역명이며 trim 후 1~200 grapheme이다.
- **address는 필드가 필수이고 값은 null 또는 유효한 주소 문자열**이다.
  null은 주소 없음이며 장소명이나 임의 주소로 채우지 않는다.
  문자열은 trim 후 비어 있지 않은 1~500 grapheme, NUL 금지다.
  빈 문자열·공백을 주소 부재로 사용하거나 자동으로 null로 바꾸지 않는다.
- 누락된 address는 COMMON_002/400, 빈 문자열·공백·NUL·길이 초과는 COMMON_001/400이다.
  실패 시 기존 목록·버전·revision·출처 삭제 이벤트를 변경하지 않는다.
- 서버 발급 장소 행 id와 외부 externalId는 다르다. 콕 요청은 저장 응답의 행 id를 사용한다.
- 초안 snapshot·장소 조회·발행본·핀 스냅샷·광고 place의 address도 동일하게 문자열 또는
  **명시적 JSON null**이다. 빈 문자열이나 장소명으로 대체하지 않는다.
- `PlaceDetails.of`는 구조 검증만 수행한다. 공급자 검색 진위·ID 유효성·주소 실재를
  재조회하거나 보증하지 않는다. 서버 검색 endpoint는 이 계약에 필요하지 않다.

클라이언트의 기존 [PlaceResult](https://github.com/Kusitms-34th-Bunch/BUNCH_Client/blob/38b9b1221a1851a56d46c8798d820b20bb8e2990/apps/web/src/features/bundle/lib/types.ts#L79)는
id/name/address 문자열 형태다. 실제 연결 시 provider와 externalId를 구분하고 address를
nullable로 맞춰야 한다. 기존 클라이언트 문서의 BFF/백엔드 호출 후보보다 최신 사용자 결정이 우선한다.

## 주소 복사·영속성·호환성

8.1.7은 앱에서 저장된 주소 전체를 복사하고, address가 null이면 name을 복사한다.
클립보드 실패 안내도 앱 책임이다. 콕은 기존처럼 저장된 번들 장소/광고 행에서만 값을 복사한다.
핀 요청 본문으로 이름·주소를 바꾸지 않는다. 원본 삭제 후에도 null 주소와 이름을 포함한 핀
스냅샷 보존 정책을 유지한다.

V36은 bundle_locations.address, pinned_places.address,
feed_advertisements.place_address의 NOT NULL만 제거한다. 기존 CHECK는 null에서 통과하고
빈 주소는 계속 거부한다. 기존 주소·ID·키·출처를 갱신하지 않으며 과거 Flyway 파일을 수정하지 않는다.
V35 이후 주소 계약(V36), 콕 목록(V37), 픽(V38~39),
공동 편집(V40~42)을 순서대로 적용한다.

기존 유효 문자열 입력은 그대로 호환된다. 클라이언트는 nullable 응답을 처리한 뒤
주소 없는 결과를 보내야 한다. 기존 앱이 address를 항상 문자열로 가정하면 표시·복사가 실패할 수 있다.
프론트의 검색 결과 정규화·키 관리·공급자 실패 처리는 이 서버 저장 검증으로 대신 확인할 수 없다.

## 연계·검증

- #107 소유인 위치 추가·삭제·교체·이동 동시 처리와 lease 제거는 중복 구현하지 않는다.
  이 브랜치에서는 기존 저장 요청의 version/lease를 유지하며 통합 시 그 최신 요청에도 같은 주소 계약을 적용한다.
- #125의 목록·필터·개수는 중복 구현하지 않는다. 핀 공통 DTO의 nullable 주소를 목록에서도 유지하고,
  주소 복사 fallback은 앱에서 적용한다.
- 자동 검증은 명시적 null HTTP 저장·snapshot, 누락/빈 주소 거부의 원자성, 실제 번들/광고에서
  콕 생성·조회·원본 삭제 후 스냅샷 보존, 이전 DB 업그레이드·재실행·빈 주소 DB 거부를 확인한다.
- 실제 공급자 검색·빈 결과·실패·페이지·지역 선택, iOS/WebView 표시·클립보드 복사는
  프론트 환경에서 별도로 검증한다. 서버 자동 테스트만으로 앱 검색 연동 완료를 주장하지 않는다.
