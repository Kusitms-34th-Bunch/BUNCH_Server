# 추천 번들 계약

이 문서는 이슈 #67(추천 번들 사진 묶기와 저장 구조)의 계산 규칙을 고정한다. 선정·제목·재계산·만료·조회는 이후 이슈(#68~#73)가
이 문서를 확장한다. **와이어프레임과 기능명세서가 다르면 기능명세서를 따른다.**

## 기준 문서

기능명세서 사진함 4.2.7(함께 찍은 사진 묶기)을 따르고, 풀어 쓴 설명은 추천 번들 백엔드 가이드 4장을 참고한다.
가이드와 명세서가 다르면 명세서가 기준이다. 사진 저장은 [사진함 기반 계약](photo-foundation.md), 날짜 변경은
[사진 촬영 날짜 변경 계약](photo-date.md)을 따른다.

값은 확정(명세서 근거 표시), 제안(명세서가 정하지 않아 개발이 기본안으로 구현), 확정 대기로 나눠 적는다.

## 이름

| 말 | 뜻 |
| --- | --- |
| 추천 번들 | 사용자에게 보이는 이름. 번들 만들기 화면의 추천 번들 시트 카드 한 장 |
| 후보 | 코드와 DB가 쓰는 이름(`bundle_candidates`). 추천 번들 하나가 후보 하나다 |
| 사진 묶음 | 서버가 "같은 자리에서 함께 찍었다"고 보고 하나로 묶은 사진들(코드의 `PhotoCluster`). 화면에는 보이지 않는다 |
| 업로드 묶음 ID | 한 번에 올린 사진들이 가진 같은 ID(`photo_uploaders.upload_batch_id`) |

코드 패키지는 `com.bunch.recommendation`이다. Notion API 태그는 `Recommendation`이다.

## 사진 묶기 계산 (4.2.7)

데이터베이스와 시계에 의존하지 않는 순수 계산이다. 호출하는 쪽이 계산에 넣을 사진만 골라 넘긴다.

### 입력

| 값 | 설명 |
| --- | --- |
| 사진 ID | |
| 촬영 날짜 | 사용자가 날짜를 조정한 사진은 조정한 날짜(3.1.3 로직 1, 3.4.1). 시간대 없는 현지 값 그대로 쓴다 |
| 촬영 시각 | 없을 수 있다. **업로드 시각으로 대신하지 않는다**(4.2.7 로직 4) |
| 올린 멤버들 | 함께 올린 사진은 여러 명이다. 사진은 1장으로 세고 올린 멤버는 모두 센다(4.2.7 로직 2) |
| 업로드 묶음 ID들 | 목록으로 받는다. 날짜를 한 번에 조정한 묶음 ID(#66)는 저장되기 전까지 넣지 않으며, 목록이라 나중에 더해도 계산이 바뀌지 않는다 |

### 계산에 넣지 않는 사진 (호출하는 쪽이 제외, 4.2.7 로직 1·상세 1)

- 촬영 날짜를 모르는 사진(「촬영 날짜를 확인할 사진」, 3.1.5). 날짜를 맞추면 그때부터 들어간다.
- 작성 중인 번들(초안)에 들어간 사진, 이미 발행된 번들에 쓰인 사진.

### 출력

사진 묶음 목록이다. 묶음마다 사진 ID들(카드 순서 규칙대로 정렬), 시작 날짜, 끝 날짜(자정을 넘겨 이은 묶음만), 올린 멤버
집합, 정리 전 1차 조건 통과 여부를 가진다. 조건을 못 채운 묶음도 돌려준다. 이후 재계산이 분리·병합을 판단하려면 필요하다.

### 규칙

| 단계 | 규칙 | 근거 |
| --- | --- | --- |
| 1. 날짜별로 묶기 | 사진함 날짜 섹션과 같은 날짜 기준으로 같은 날 사진을 모은다 | 4.2.7 상세 1 |
| 2. 하루 나누기 | 촬영 시각이 있는 사진을 시간순으로 놓고, **사진 사이가 4시간 이상 비었거나, 공백이 짧아도 앞쪽 사진 전체와 뒤쪽 사진 전체의 올린 멤버가 한 명도 겹치지 않으면** 그 사이에서 나눈다. 나눈 양쪽에 각각 3장 이상 있을 때만 나눈다. 나눌 수 있는 곳이 여러 군데면 가장 긴 공백부터 본다. 나눈 조각마다 같은 방식으로 다시 본다. 시각 있는 사진이 하나도 없거나 나눌 곳이 없으면 하루를 한 묶음으로 본다 | 4.2.7 상세 2·예외 |
| 3. 자정 잇기 | 날짜별로 나눈 묶음에서, 전날의 **마지막 묶음**과 다음 날의 **첫 묶음**이 아래 조건을 모두 채우면 두 묶음을 **통째로** 하나로 잇는다: 전날 묶음의 마지막 사진이 밤 22시 이후, 다음 날 묶음의 첫 사진이 새벽 3시 이전, 두 사진의 간격이 2시간 이내. 22시와 3시는 잇는 조건을 보는 기준일 뿐 묶음 안의 사진을 자르는 기준이 아니다. 자정에 맞닿은 두 묶음만 잇고 그날의 다른 묶음은 합치지 않는다. 묶음의 시작 날짜는 첫날, 끝 날짜는 다음 날이다 | 4.2.7 상세 3·예외, 기획 확인 |
| 4. 시각 없는 사진 붙이기 | 아래 표 | 4.2.7 상세 4 |
| 5. 1차 조건 | 정리 전 장수로 6장 이상이고 올린 멤버가 2명 이상이면 통과로 표시한다 | 4.2.7 상세 5 |

시각 없는 사진 붙이기(그날 사진 묶음이 하나뿐이면 판단 없이 그 묶음에 붙인다):

| 순서 | 기준 |
| --- | --- |
| ① | 같은 업로드 묶음 ID에 시각 있는 사진이 있으면 그 사진이 가장 많이 속한 묶음. 같으면 ②로 |
| ② | 그 사진을 올린 멤버가 그날 **한 묶음에만** 사진을 올렸으면 그 묶음 |
| ③ | 그날 사진이 가장 많은 묶음. 사진 수가 같으면 촬영 시각이 가장 이른 묶음 |

### 최종 판정은 연사 정리 뒤

6장 기준은 연사를 정리한 뒤의 장수다(4.2.7 상세 5, 4.2.8 로직 4). 이 계산은 정리 전 장수의 1차 판정까지만 하고,
최종 판정은 아래 「카드 사진 선정」(#68)이 한다.

## 처음 기준 숫자

명세서가 "처음 기준이며 써 보면서 조정한다"고 한 값이다(4.2.7 로직 6). 코드는 한곳(`RecommendationSettings`)에 모은다.

| 값 | 기본 |
| --- | --- |
| 하루를 나누는 빈 시간 | 4시간 |
| 나눈 양쪽 최소 장수 | 3장 |
| 자정 잇기 시작 시각 / 끝 시각 / 간격 | 22:00 / 03:00 / 2시간 |
| 추천 최소 장수 / 올린 멤버 | 6장 / 2명 |
| 연사로 보는 촬영 시각 차이 | 3초 이내(4.2.8 로직 1 "예: 3초") |
| 연사로 보는 이미지 비교값 차이 | 64비트 값에서 5비트 이하(제안, 써 보며 조정) |
| 카드에 담는 최대 장수 | 10장(4.2.8) |

## 해석한 부분 (제안)

명세서가 정하지 않았거나 모호해서 개발이 정한 것이다. 테스트로 고정하고, 달라지면 이 표와 테스트를 함께 바꾼다.

| 항목 | 해석 |
| --- | --- |
| 자정 잇기는 한 번만 | 한 묶음은 한 번만 이어서 최대 이틀을 넘지 않는다 |
| 자정 잇기의 간격 | 간격이 정확히 2시간이면 잇는다(「2시간 이내」) |
| 공백 4시간 | 정확히 4시간이면 나눈다(「4시간 이상」) |
| 사진 장수 세기 | 나눌 때의 양쪽 장수는 시각 있는 사진만 센다. 시각 없는 사진은 나눈 뒤에 붙는다 |
| 시각 없는 사진 붙이기 ①이 같을 때 | ②와 ③은 같은 수로 겨룬 묶음들 안에서만 고른다 |
| 시각 없는 사진 붙이기 ② | 올린 멤버가 여럿이면 각 멤버가 "한 묶음에만 올린" 묶음을 모아, 하나로 정해질 때만 쓰고 아니면 ③으로 간다 |
| 시각 없는 사진 붙이기 ③의 장수 | 붙이기 전 시각 있는 사진 장수. 붙이는 순서에 결과가 달라지지 않게 한다 |
| 묶음 안 사진 순서 | 첫날 시각 순 → 첫날 시각 없는 사진 → 다음 날 시각 순 → 다음 날 시각 없는 사진(4.2.3 로직 1). 시각 없는 사진은 사진 ID 순(먼저 올린 사진이 앞) |

## 재료 사진 조회 (4.2.7 상세 1, 이슈 #67)

묶기 계산에 넘길 사진을 번치 단위로 고른다. 번들 도메인(`bundle_photos`)은 **읽기만** 하고 번들 도메인 파일은 수정하지
않는다. 마이그레이션은 만들지 않는다.

### 재료가 되는 사진

| 조건 | 근거 |
| --- | --- |
| 그 번치의 사진이다 | 4.2.9 로직 5 (추천 번들 목록은 번치 단위) |
| 처리가 끝난(READY) 사진이다. 처리 중(PENDING)이거나 실패한(FAILED) 사진은 카드에 보일 수 없으므로 넣지 않는다(개발이 정한 부분, 사진함 목록과 같은 기준) | 이슈 #67, [사진함 목록 계약](photo-list.md) |
| 촬영 날짜가 있다. 사용자가 날짜를 정한 사진도 포함한다 | 4.2.7 상세 1, 3.1.5, 3.4.1 로직 5 |
| 번들 사진(`bundle_photos.photo_id`)이 참조하지 않는다. 작성 중인 번들(초안)과 발행된 번들에 쓰인 사진을 같은 방식으로 뺀다 | 4.2.7 로직 1, 4.1.3 로직 6 |

초안을 삭제하면 그 초안의 번들 사진 행이 함께 지워져 사진은 다시 재료가 된다(5.3.2 로직 4). 발행된 번들에서 사진함의
사진이 지워져 `photo_id`가 비어도(`ON DELETE SET NULL`) 다른 사진에는 영향이 없다.

### 출력

사진마다 `PhotoSample` 한 개: 사진 ID, 촬영 날짜, 촬영 시각(없을 수 있음), 올린 멤버 전체, 업로드 묶음 ID 전체. 함께 올린
사진은 한 개로 세고 올린 멤버와 업로드 묶음 ID를 모두 담는다(4.2.7 로직 2). 이미지 비교값은 업로드 때 저장하기로 한
값이며(아래 「이미지 비교값 위치」), 그 저장 컬럼이 생기기 전에는 이 조회가 채우지 않는다.

### 이 조회가 하지 않는 것

추천을 적용해 만든 초안의 후보 삭제와, 그 초안을 만든 뒤 남은 사진이 새 사진이 올라올 때까지 다시 추천되지 않게 하는
억제 규칙(#73), 후보 저장(#70).

## 카드 사진 선정 (4.2.8, 이슈 #68)

묶음 하나의 사진에서 카드에 담을 사진을 최대 10장 고른다. 4.2.7과 같은 순수 계산이며, 호출하는 쪽이 한 묶음의 사진
(`PhotoSample`)을 넘긴다. 이미지 비교값은 선택 값이다. 값은 업로드 때 서버가 계산해 저장하기로 했다(아래 「이미지 비교값
위치」).

### 출력

연사 정리 뒤 남은 장수, 올린 멤버, 최종 추천 여부, 카드 사진 ID(표시 순서대로, 최대 10장). 추천하지 않으면 카드 사진은 비어 있다.

### 규칙

| 단계 | 규칙 | 근거 |
| --- | --- | --- |
| 1. 연사 정리 | 촬영 시각 차이가 3초 이내이고 이미지가 거의 같은 사진은 한 연사로 보고 대표 1장만 남긴다. **올린 멤버가 같은 사진끼리만** 연사로 본다. 촬영 시각이나 이미지 비교값이 없는 사진은 줄이지 않는다 | 4.2.8 상세 1·로직 1, 같은 멤버 기준은 기획 확인 |
| 2. 최종 판정 | 연사 정리 뒤 **남은 사진** 기준으로 6장 이상이고 올린 멤버가 2명 이상일 때만 추천한다. 아니면 추천하지 않는다(카드는 항상 6~10장) | 4.2.8 로직 4·예외, 4.2.7 상세 5, 남은 사진 기준은 기획 확인 |
| 3. 10장 이하 | 따로 고르지 않고 모두 담는다 | 4.2.8 상세 2 |
| 4. 10장 초과 ① | 올린 멤버마다 최소 1장씩 고른다. **사진을 적게 올린 멤버부터** 고른다 | 4.2.8 상세 3-①, 로직 2 |
| 5. 10장 초과 ② | 남은 자리는 묶음의 촬영 시간대가 고르게 보이도록 고른다. 같은 멤버의 사진을 더 고를 때도 한 시간대에 몰리지 않게 한다. 시각 없는 사진도 고를 수 있다 | 4.2.8 상세 3-②, 로직 2 |
| 6. 함께 올린 사진 | 한 번만 고르고, 함께 올린 멤버 중 **그 묶음에 사진을 가장 적게 올린 멤버**의 몫으로 센다. 올린 장수가 같으면 **그 사진을 먼저 올린 멤버**의 몫이다. 몫이 정해진 사진은 다른 멤버가 자기 몫으로 고르지 못한다. 사진을 적게 올린 멤버가 빠지지 않게 하려는 것이다 | 4.2.8 로직 3, 기획 확인(몫이 한 명으로 고정된다는 점은 기획 답변에서 이끌어 낸 해석) |
| 7. 정렬 | 촬영 시각 순, 시각 없는 사진은 같은 날짜 뒤에 업로드 순. 자정을 넘긴 묶음은 첫날 시각 순 → 첫날 시각 없는 사진 → 다음 날 시각 순 → 다음 날 시각 없는 사진. 1번 사진이 대표 사진이다 | 4.2.3 로직 1, 4.2.8 로직 5 |
| 8. 고르지 않은 사진 | 사진함에 그대로 남는다. 이 계산은 사진을 지우거나 바꾸지 않는다 | 4.2.8 로직 6 |

### 이미지 비교값 위치 (결정)

연사 판별에 쓰는 이미지 비교값을 언제 어디서 만들지 정한다(4.2.8 로직 1은 "경량 이미지 비교 방식"까지만 정함).

| 항목 | 결정 |
| --- | --- |
| 위치 | **업로드 때 서버가 계산해 `photos`에 저장한다.** 후보를 계산할 때 이미지 저장소에서 사진을 읽는 방식은 쓰지 않는다 |
| 이유 | 서버가 업로드 때 이미 이미지 바이트를 갖고 있어 추가 네트워크가 필요 없다. 재계산은 사진이 바뀔 때마다 여러 날짜에 일어나므로, 계산 때 외부 이미지 저장소를 읽으면 지연과 사용량을 예측하기 어렵다 |
| 값 | 64비트 값 하나. 이미지를 줄여 밝기 모양을 요약한 값이며 서로 다른 비트 수로 비교한다. 새 의존성 없이 JDK 이미지 API로 계산할 수 있는지는 구현 때 확인한다. 해시 방식과 임계값(5비트)은 실제 연사 사진으로 시험해 정한다 |
| 계산 실패 | 비교값을 구하지 못해도 업로드는 성공시키고 값은 비워 둔다 |
| 값이 없는 사진 | 연사 정리에서 줄이지 않는다(계산에 이미 반영됨) |
| 기존 사진 | 백필은 필수가 아니다. 값이 없으면 그 사진은 연사 정리만 안 되고 다른 동작은 같다. 필요해지면 나중에 채운다 |
| 구현 범위 | 이 문서는 결정만 기록한다. 컬럼 추가(새 마이그레이션), 업로드에서 계산·저장, 재료 조회에 값 채우기는 별도 작업이며, 마이그레이션 번호는 팀원의 V17이 `dev`에 들어온 뒤 정한다. 구현할 이슈가 정해지면 이 문서에 적는다 |

명세서가 정하지 않아 개발이 정했다. 테스트로 고정하고, 달라지면 이 표와 테스트를 함께 바꾼다.

| 항목 | 해석 | 근거 |
| --- | --- | --- |
| 연사 중 남길 사진 | 연사 안에서 가운데 순서의 사진(촬영 시각 순으로 놓고 가운데, 짝수면 앞쪽 가운데) | 4.2.8 로직 1 "대표 사진 선정 기준은 개발 단계에서 정의" |

## 제목 생성 (4.2.2, 이슈 #69)

추천 번들 하나의 제목을 상황별 문장 목록에서 뽑는다. DB와 시계에 의존하지 않는 순수 계산이고, 난수 생성기는 밖에서
넣는다. 뽑은 제목을 후보에 저장하고 고정하는 일은 후보 테이블을 만드는 이슈 #70이 한다. 문장 목록은 「추천 번들 제목
문장 목록」(Notion, 2026-11-05 수정본, 89개)이고, 목록의 전체 문장이 이 계산의 데이터다.

### 입력

| 값 | 설명 | 근거 |
| --- | --- | --- |
| 묶음의 시작 날짜, 끝 날짜 | 끝 날짜는 자정을 넘겨 이은 묶음만 있다. 특별한 날과 요일은 **시작 날짜**로 판단한다 | 4.2.7 예외(자정 잇기 묶음은 첫날 묶음) |
| 촬영 시각들 | 시각이 있는 사진의 촬영 시각. 가운데 시각으로 시간대를 정한다 | 4.2.2 로직 3-① 기본 |
| 올린 멤버 닉네임 | 사진을 많이 올린 순서. 빈칸에 넣는다 | 4.2.2 로직 3-④, 문장 목록 빈칸 표기 |
| 번치 멤버 수, 번치에서 가장 이른 사진 날짜 | 전원 참여, 번치 첫 묶음 판단 | 4.2.2 로직 3-① |
| 앞 묶음의 끝 날짜 | 없으면 비어 있다 | 4.2.2 로직 3-① |
| 같은 목록에 보이는 제목, 최근 쓴 문장 ID(최근 것부터) | 제외에 쓴다 | 4.2.2 로직 3-② |

입력 값을 모으는 일은 #70이 한다. 앞 묶음과 번치 첫 묶음은 초안·발행 번들에 쓰인 사진을 포함한 모든 날짜 사진을 기준으로
한다(번들에 쓰인 사진이 빠지면 "오랜만"이 잘못 나온다).

### 결과

제목과 뽑은 문장의 ID. 문장에서 나오지 않은 제목(이후 AI 제목)을 위해 문장 ID는 비어 있을 수 있다. 4.2.2 로직 3-⑧의
AI 제목은 확정 전이라 만들지 않는다.

### 규칙

| 단계 | 규칙 | 근거 |
| --- | --- | --- |
| 1. 상황 판단 | 아래 순서에서 처음 해당하는 것: 특별한 날 → 번치의 첫 묶음 → 전원 참여 → 앞 묶음에서 30일 이상 → 자정 넘김 → 기본 | 4.2.2 로직 3-① |
| 2. 문장 모으기 | 그 상황의 사용 중(active) 문장. 특별한 날은 그날의 세부 상황, 기본은 세부 상황 문장과 일반 문장을 합친다(예: 토요일 저녁이면 「토요일 저녁」과 「주말 저녁」) | 4.2.2 로직 3-①, 문장 목록 쓰는 법 3 |
| 3. 제외 | 같은 목록에 이미 보이는 제목과 최근 10개 문장은 뺀다 | 4.2.2 로직 3-② |
| 4. 뽑기 | 남은 문장 중 무작위 1개 | 4.2.2 로직 3-② |
| 5. 빈칸 채우기 | `{요일}` 「토요일」, `{A}`·`{B}` 닉네임(사진 많은 순), `{N}` 나머지 인원 수. 빈칸 뒤에 조사를 붙이지 않는다 | 문장 목록 빈칸 표기 |
| 6. 길이 | 채운 문장이 15자(공백 포함)를 넘으면 그 문장은 버리고 다시 뽑는다 | 4.2.2 로직 3-⑥, 문장 목록 |
| 7. 소진 | 남은 문장이 없으면 빈칸 문장 → 최근 제외 해제 → 기본 묶음 순으로 보완한다 | 4.2.2 예외, 문장 목록 쓰는 법 4 |

상황 판단의 조건:

| 상황 | 조건 |
| --- | --- |
| 특별한 날 | 시작 날짜가 특별한 날(아래 「특별한 날 데이터」) |
| 번치의 첫 묶음 | 시작 날짜가 번치에서 가장 이른 사진 날짜 |
| 전원 참여 | 번치 멤버가 3명 이상이고 묶음에 올린 멤버가 번치 멤버 수 이상 |
| 오랜만 | 앞 묶음의 끝 날짜와 시작 날짜의 차이가 30일 이상 |

| 기본 | 위에 해당하지 않음. 요일 + 시간대(새벽 0~5시 / 오전 5~12시 / 오후 12~17시 / 저녁 17~24시), 시각 있는 사진이 없으면 요일만(시간대 없이 「촬영 시각 없음」 문장과, 월요일이면 「월요일」 문장) |

### 문장 데이터

문장마다 안정적인 ID, 상황, 세부 상황, 문장(빈칸 포함), 사용 여부(active)를 가진다. 문장을 읽는 곳은
`TitleSentenceSource` 하나이고, 지금은 코드의 데이터로 구현한다. 문장을 DB에서 관리하는 일(관리 도구, 배포 없는 수정)은
별도 이슈이며, 그때 읽는 구현만 바꾸고 제목 생성은 바뀌지 않는다.

| 항목 | 규칙 |
| --- | --- |
| ID | `상황.세부상황.번호`(예: `special.seollal.1`). 한 번 쓴 번호는 다시 쓰지 않고 순서를 바꾸지 않는다 |
| 문장을 빼고 싶을 때 | 지우지 않고 active를 끈다(최근 사용 이력의 연속성) |
| 검증(테스트) | ID와 문장 중복 없음, 빈칸을 채운 최대 길이가 15자 이내, 줄바꿈과 앞뒤 공백 없음, 금지 표현 없음 |

금지 표현 검사는 문장 목록 문서의 「쓰지 않는 문장」(활동·장소·날씨·직업·놀림·술·사진 수·날짜)에서 든 예를 바탕으로 한
안전망이며, 모든 금지 표현을 잡지는 못한다.

| 빈칸 문장 비율 | 정해질 때까지 0(소진·중복 때 보완용으로만 쓴다). 설정 값으로 둔다 | 문장 목록 쓰는 법 4 "비율은 기획에서 정함" |
| 글자 수 | 보이는 글자(문자 하나) 단위로 센다(이모지 포함) | 4.3.3과 같은 방식 |
| 세부 상황의 합치기 | 월요일은 「월요일」+평일 시간대, 금요일 저녁은 「금요일 저녁」+「평일 저녁」, 토요일 저녁은 「토요일 저녁」+「주말 저녁」, 일요일 저녁은 「일요일 저녁」+「주말 저녁」 | 문장 목록 쓰는 법 3 |
| 같은 날 여러 번들 | #70이 먼저 만든 번들의 제목을 다음 번들의 「같은 목록에 보이는 제목」으로 넘긴다 | 4.2.2 예외 |
| 닉네임이 긴 경우 | 닉네임은 공백 포함 1~12자이고 이모지는 쓸 수 없다(PRD, 인증 Spec 1.4.3). 문장 목록은 닉네임을 2글자로 세므로, 닉네임이 길면 빈칸 문장은 15자를 넘어 뽑히지 않고 다른 문장을 고른다. 예: `{A}·{B} 폼 미쳤다`는 두 닉네임의 글자 수 합이 8자까지, `{A} 외 {N}명 할렐야루`는 닉네임이 5자까지 | PRD 1.4, 문장 목록 「문장 쓰는 규칙」 |

## 후보 저장 (4.2.9 로직 2, 이슈 #70)

추천 번들 하나(후보)가 어떤 사진으로 이루어지고 카드에 무엇이 보이는지를 저장한다. 마이그레이션은 V18이다.

### 테이블

| 테이블 | 담는 것 | 근거 |
| --- | --- | --- |
| `bundle_candidates` | 번치, 시작 날짜, 끝 날짜(자정을 넘긴 묶음만, 다음 날), 제목, 제목이 나온 문장 ID(`title_sentence_key`), 마지막 사진 추가 시각, 생성·수정 시각 | 4.2.9 로직 2 |
| `candidate_photos` | 묶음에 속한 **전체 사진**(카드에 담기지 않은 사진, 연사 정리로 빠진 사진 포함)과, 카드에 담은 사진(최대 10장)의 표시 순서(`position` 1~10). 카드에 담은 사진만 `position`이 있고 나머지는 비어 있다 | 4.2.9 로직 2, 4.2.8 |
| `recommendation_dirty_dates` | 5분을 기다리는 동안 바뀐 날짜(번치, 날짜, 마지막 변경 시각). 다시 계산한 뒤 지운다 | 4.2.9 로직 2 |

### 규칙

| 규칙 | 내용 | 근거 |
| --- | --- | --- |
| 상태 없음 | 사라진 번들(30일 경과, 추천 조건 미충족, 분리·병합, 추천을 적용한 초안 생성)은 기록을 남기지 않고 행을 지운다. 상태·만료 컬럼은 없다. 사진은 사진함에 그대로 남는다 | 4.2.9 로직 4, 결정 |
| 다시 나타남 | 사라진 번들의 사진이 다시 조건을 채우면 새 후보와 새 제목이 된다. 30일 뒤 재노출에서 기존 제목을 유지하는 것(4.2.9 로직 5, 4.2.2 로직 3 ⑤)은 구현하지 않는다 | 결정 |
| 삭제 연쇄 | 번치를 지우면 후보·후보 사진·바뀐 날짜가 함께, 사진을 지우면 그 사진의 후보 사진 행만 지워진다(DB `ON DELETE CASCADE`) | 4.2.9 로직 1, 3.6.1 로직 5 |
| 사진 순서 | 카드에 담은 사진인지는 `position`이 있는지로 안다(별도 컬럼 없음). `position`은 1~10이다. 한 후보에 같은 사진은 한 번만 | 4.2.8 |
| 날짜 | `end_date`는 `start_date`보다 뒤다(자정을 넘긴 묶음의 다음 날) | 4.2.7 |
| 제목 | 한 번 저장한 제목은 바꾸지 않는다. 비어 있지 않고 줄바꿈이 없으며 DB에서는 60자까지 받는다(15자 한도는 제목 생성이 지킨다). `title_sentence_key`는 문장에서 나오지 않은 제목(AI 제목 등, 4.2.2 ⑧)을 위해 비울 수 있다 | 4.2.2 ⑤ |
| 마지막 사진 추가 시각 | 새 사진이 들어올 때만 올리고 내려가지 않는다 | 4.2.9 로직 3 |
| 두지 않는 것 | 장소 컬럼, 참여 멤버 컬럼(멤버는 후보 사진의 업로더로 조회 때 구한다), 상태 컬럼 | 4.2.2 ⑥, 4.2.9 로직 3 |

## 기존 후보와 비교 (4.2.9 로직 1, 이슈 #70)

사진이 바뀌면 해당 날짜의 사진을 다시 묶고(#67), 저장된 후보와 비교해 유지 여부를 판단한다. 데이터베이스와 시계에 의존하지
않는 순수 계산이다(`CandidateMatcher`).

### 입력과 출력

| 구분 | 내용 |
| --- | --- |
| 입력 | 후보 번호별 **전체 사진**(카드에 담기지 않은 사진, 연사 정리로 빠진 사진 포함), 다시 묶은 **모든 묶음**(추천 대상이 아닌 것 포함), 묶음별 최종 추천 판정(연사 정리 뒤 6장·멤버 2명, 4.2.8) |
| 출력 | 유지할 후보와 지금의 묶음, 새 후보로 만들 묶음(받은 순서), 지울 후보 |

### 규칙

| 경우 | 판단 | 근거 |
| --- | --- | --- |
| 유지 | 후보와 사진을 하나라도 공유하는 묶음이 **정확히 하나**이고, 그 묶음이 다른 후보의 사진을 공유하지 않으며, 지금도 추천 조건을 충족한다. 사진이 늘거나 줄어도 유지한다. 제목은 그대로 두고 최대 10장을 다시 선정한다 | 4.2.9 로직 1 [기존 추천 번들 유지] |
| 분리 | 후보의 사진이 묶음 둘 이상에 나뉘면 후보를 지우고, 추천 조건을 충족한 각 묶음을 새 후보(새 제목)로 만든다 | [사진 묶음 분리] |
| 병합 | 한 묶음이 후보 둘 이상의 사진을 가지면 그 후보를 모두 지우고, 묶음이 추천 조건을 충족하면 새 후보 하나(새 제목)로 만든다 | [사진 묶음 병합] |
| 추천 조건 미충족 | 묶음이 조건을 채우지 못하면 후보를 지우고 새 후보는 만들지 않는다. 연사 정리 뒤 6장 미만, 멤버 1명 이하 | [추천 조건 미충족], 4.2.8 |
| 사진이 남지 않음 | 어떤 묶음에도 사진이 없는 후보(사진 삭제, 초안에 쓰임, 날짜 변경)는 지운다 | 4.2.9 로직 1, 4.1.3 로직 6 |
| 새 묶음 | 후보와 겹치지 않는 묶음이 추천 조건을 충족하면 새 후보로 만든다 | 4.2.9 로직 1 |

### 개발이 정한 부분 (제안)

| 부분 | 정한 것 | 근거 |
| --- | --- | --- |
| 병합의 범위 | 후보끼리의 병합만 병합으로 센다. 추천 대상이 아닌 묶음은 저장하지 않아서 그 묶음과 합쳐졌는지 알 수 없고, 후보는 유지한다 | [사진 묶음 병합]이 "서로 다른 추천 번들"이라고 적음 |
| 분리된 조각 중 일부만 조건을 충족 | 충족한 조각만 새 후보가 되고 나머지는 후보가 되지 않는다 | [사진 묶음 분리]: 조건을 충족하는 경우에만 생성 |
| 분리와 병합이 함께 일어남 | 얽힌 후보를 모두 지우고, 조건을 충족한 묶음을 모두 새 후보로 만든다 | 두 항목을 함께 적용 |

## 재계산 (4.2.9 로직 1~3, 이슈 #70)

`RecommendationService.recalculate(번치, 바뀐 날짜들)`가 후보를 다시 계산해 저장·갱신·삭제한다. 사진이 바뀐 것을 받아서 5분
뒤에 부르는 일은 이 계산을 부르는 쪽(작업 큐)의 몫이다.

### 순서

| 순서 | 하는 일 | 근거 |
| --- | --- | --- |
| 1 | 번치를 잠근다(사진 업로드·삭제와 같은 잠금). 번치가 없거나 바뀐 날짜가 없으면 아무것도 하지 않는다 | 4.2.9 로직 2 |
| 2 | 번치의 재료 사진 전체(최대 1,000장)를 묶음으로 나누고(4.2.7), 묶음마다 카드 사진 선정과 최종 추천 판정(4.2.8)을 한다 | 4.2.9 로직 1 |
| 3 | 바뀐 날짜와 그 전날·다음 날에 걸친 후보와 묶음만 대상으로 한다 | 4.2.9 로직 2 |
| 4 | 저장된 후보와 비교해 유지·분리·병합·미충족을 판정한다([기존 후보와 비교](#기존-후보와-비교-429-로직-1-이슈-70)) | 4.2.9 로직 1 |
| 5 | 사라질 후보를 지운다. 유지할 후보는 제목을 그대로 두고 날짜·사진·선정 순서를 새로 저장한다. 새 후보는 제목을 만들어 저장한다 | 4.2.9 로직 1·2·3 |

### 규칙

| 규칙 | 내용 | 근거 |
| --- | --- | --- |
| 계산 범위 | 바뀐 날짜 D에 대해 D-1, D, D+1에 하루라도 걸치는 후보와 묶음만 바꾼다. 범위 밖의 후보는 손대지 않는다 | 4.2.9 로직 2 |
| 마지막 사진 추가 시각 | 새 후보는 묶음 사진 중 가장 늦게 **사진함에 추가된**(`photos.created_at`) 시각이다. 유지되는 후보는 지금 값보다 새로울 때만 올리고 내려가지 않는다. 사진만 지워지면 그대로다. 날짜를 옮겨 들어온 사진이나 초안에서 돌아온 사진은 오래전에 추가된 사진이라 시각을 올리지 않는다 | 4.2.9 로직 1·3 |
| 제목 | 새 후보에만 만든다. 유지되는 후보의 제목은 바꾸지 않는다. 새 후보가 여럿이면 날짜순으로 하나씩 만들고, 앞서 만든 제목과 문장을 다음 후보의 「보이는 제목」과 「최근 문장」에 더한다 | 4.2.2 로직 3 ② ⑤ |
| 후보 사진 | 묶음의 전체 사진을 저장하고 카드에 담은 사진만 순서(1~)를 가진다 | 4.2.9 로직 2 |
| 같은 번치 동시 계산 | 번치 잠금 때문에 같은 번치의 두 계산이 함께 돌지 않고 차례로 돈다. 뒤의 계산은 앞의 결과를 보고 판단한다 | 이슈 #70 |

### 제목 입력을 구하는 곳

명세서가 정한 것과 개발이 해석해서 정한 것을 나눠 적는다.

| 입력 | 명세서가 정한 것 | 개발이 정한 것 (제안) |
| --- | --- | --- |
| 닉네임 | 빈칸에는 그 사진 묶음에 사진을 올린 멤버를 넣는다(4.2.2 로직 3 ④) | 올린 장수 많은 순, 같은 장수면 멤버 번호 순으로 둔다. 함께 올린 사진은 각 멤버가 올린 것으로 센다. 닉네임이 없거나 공백인 멤버는 뺀다 |
| 번치 멤버 수 | 3명 이상의 멤버가 있는 번치(4.2.2 로직 3 ①) | 활성 멤버만 센다 |
| 번치의 가장 이른 사진 날짜 | 사진함에서 가장 이른 날짜의 사진 묶음이 번치의 첫 사진 묶음이다(4.2.2 로직 3 ①) | 날짜가 있는 READY 사진 전체에서 구한다. 초안·발행 번들에 쓰인 사진도 사진함에 남는 사진이라 포함한다(5.3.2 로직 3, 4.2.9 로직 4) |
| 바로 앞 묶음 끝 날짜 | 바로 앞 사진 묶음에서 30일 이상 지났는지 본다(4.2.2 로직 3 ①) | 묶음을 저장하지 않아서 「묶음에 속하지 않고 묶음보다 앞선 사진 중 가장 늦은 날짜」로 대신한다. 묶음의 첫날에 묶음의 첫 촬영 시각보다 앞서 찍은 사진은 그날로 본다(같은 날 앞선 모임은 오랜만이 아님). 시각 없는 사진은 앞뒤를 가릴 수 없어서 같은 날 것은 세지 않는다 |
| 보이는 제목 | 같은 목록에 이미 보이는 제목은 뺀다(4.2.2 로직 3 ②) | 이번 계산 뒤에도 남는 후보들의 제목과 이번에 만든 제목을 「보이는 제목」으로 본다. 사라질 후보의 제목은 보이지 않으므로 뺀다 |
| 최근 문장 | 같은 번치에서 최근에 쓴 문장(예: 최근 추천 10개)은 뺀다(4.2.2 로직 3 ②) | 사라진 번들은 기록하지 않으므로 지금 있는 후보들의 문장 키를 만든 때 최신순으로 쓴다(이번에 지워지는 후보 것 포함). 이번에 만든 문장을 맨 앞에 둔다 |

## 재계산을 부르는 때 (4.2.9 로직 1·2, 이슈 #70)

사진이 바뀌면 바뀐 날짜를 기록하고, 번치의 마지막 변경에서 5분이 지나면 기록된 날짜를 한 번에 다시 계산한다.

### 순서

| 순서 | 하는 일 | 근거 |
| --- | --- | --- |
| 1 | 사진 변경 이벤트(`PhotoChangedEvent`)를 사진 변경과 **같은 트랜잭션**에서 받아 (번치, 촬영 날짜, 지금 시각)을 `recommendation_dirty_dates`에 남긴다. 같은 날짜가 또 바뀌면 시각만 새로 쓴다. 변경이 되돌려지면 기록도 사라진다. 촬영 날짜가 없는 사진은 남기지 않는다 | 4.2.9 로직 1, 4.2.7 |
| 2 | 30초마다 「기록 중 가장 늦은 시각이 5분 이상 지난 번치」를 오래 기다린 순으로 찾는다 | 4.2.9 로직 2 |
| 3 | 번치마다 따로 트랜잭션을 열어 번치를 잠근 뒤 **다시 한 번 조용한지 확인**한다. 잠금을 기다리는 사이 새 변경이 커밋됐으면(기록 시각이 기준보다 새로움) 건드리지 않고 그 변경의 5분을 기다린다 | 4.2.9 로직 2 |
| 4 | 조용하면 기록된 날짜 전부로 재계산을 한 번 부르고 기록을 지운다 | 4.2.9 로직 2 |

### 규칙

## 테스트 기준

- 하루 나누기: 4시간 공백에서 나눔, 3시간 59분은 안 나눔, 한쪽이 2장이면 안 나눔, 양쪽 3장이면 나눔, 오전 8장 + 저녁
  1장은 한 묶음, 꾸준히 찍으면 한 묶음, 가장 긴 공백부터 나눔, 시각 있는 사진이 없으면 하루가 한 묶음.
- 멤버로 나누기: 공백이 2시간이어도 앞(멤버 A·B)과 뒤(멤버 C·D)의 멤버가 다르면 나눔, 한 명이라도 겹치면 안 나눔,
  멤버가 달라도 한쪽이 3장 미만이면 안 나눔, 양쪽에 걸쳐 함께 올린 사진이 있으면 안 나눔, 공백이 짧아도 멤버가
  완전히 다르면 나눔, 4시간 공백과 멤버 분리가 섞이면 가장 긴 공백부터 나눔, 시각 없는 사진은 멤버 비교에 쓰지 않음.
- 자정 잇기: 23:10~23:50 + 00:20~01:30은 한 묶음(시작 전날, 끝 다음 날), 20:00부터 05:00까지 끊김 없이 찍으면 한 묶음,
  간격 2시간은 잇고 2시간 1분은 안 잇고, 간격을 늘려도 전날 마지막 사진이 22시 전이거나 다음 날 첫 사진이 3시 뒤면
  안 잇고, 이틀치 전체를 합치지 않으며, 한 묶음은 한 번만 잇는다.
- 시각 없는 사진 붙이기: 묶음이 하나면 그대로, ①②③과 동률 처리, 다른 날의 같은 업로드 묶음은 무시.
- 1차 조건: 5장 미만, 올린 멤버 1명, 6장·2명 경계.
- 함께 올린 사진은 1장으로 세고 올린 멤버를 모두 센다. 날짜가 다른 사진은 다른 묶음. 묶음 안 사진 순서. 빈 입력.
- 재료 사진 조회: 날짜 있는 READY 사진만 나옴, 날짜를 모르는 사진·처리 중·실패한 사진·다른 번치의 사진은 안 나옴,
  초안에 쓰인 사진과 발행된 번들에 쓰인 사진은 안 나옴, 초안을 삭제하면 다시 나옴, 사진이 지워져 비어 있는 번들 사진
