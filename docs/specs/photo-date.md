# 사진 촬영 날짜 변경 계약

이 문서는 이슈 #37의 사진 촬영 날짜 변경 API 계약을 고정한다. 기준은 기능명세서 3.4.1(날짜 바꾸기), 3.4.2(끌어서
날짜 옮기기와 되돌리기), 3.3.1(고른 사진이 그사이 지워진 경우), 3.5.2(사진 상세 ⋯), 5.6.2(역할별 권한)이고, 추천 번들에
알리는 규칙은 4.2.7, 4.2.9를 따른다. 삭제는 [사진 삭제 계약](photo-delete.md), 목록과 상세는
[사진함 목록 조회 계약](photo-list.md)과 [날짜 미확인 목록·사진 상세 계약](photo-detail.md)을 따른다.
**와이어프레임과 기능명세서가 다르면 기능명세서를 따른다.**

값은 확정(명세서 근거 표시), 제안(명세서가 정하지 않아 개발이 기본안으로 구현), 확정 대기로 나눠 적는다.

## 요청

`POST /api/v1/bunches/{bunchId}/photos/date`

```json
{ "photoIds": [5021, 5018], "capturedDate": "2026-10-03" }
```

날짜 없음으로 되돌릴 때(3.4.2 「되돌리기」)는 `capturedDate` 대신 `clearDate`를 보낸다.

```json
{ "photoIds": [5021], "clearDate": true }
```

| 항목 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `bunchId` (경로) | Long | O | 사진이 속한 번치 |
| `photoIds` | Long[] | O | 1~50개, 중복·1 미만 불가(3.3.1 로직 1) |
| `capturedDate` | 날짜(`yyyy-MM-dd`) | `clearDate`와 둘 중 하나 | 고른 사진 모두에 적용할 날짜. 오늘(`Asia/Seoul`) 이후면 400 |
| `clearDate` | Boolean | `capturedDate`와 둘 중 하나 | `true`면 날짜 없음으로 되돌린다 |

- 인증이 필요하다. 가입을 완료한 그 번치의 ACTIVE 멤버만 호출할 수 있다.
- `capturedDate`와 `clearDate: true` 중 **정확히 하나**만 있어야 한다. 둘 다 있거나 둘 다 없으면 400이다. 비우는 일이
  필드를 빼먹은 요청으로 일어나지 않게 하려는 제안이다.
- 사진 상세(3.5.2)의 「날짜 바꾸기」도 사진 1장을 담아 같은 API를 쓴다.
- 「저장」은 날짜를 고르기 전까지 비활성이고 날짜는 하나만 고른다(3.4.1 상세 4). 그래서 시트의 저장은 항상
  `capturedDate`다.

## 권한

| 호출자 | 사진 | 결과 |
| --- | --- | --- |
| 올린 멤버 | 내가 올린 사진 | 변경됨 |
| 올린 멤버 | 함께 올린 사진(내가 올린 멤버 중 한 명) | 변경됨. 사진 자체의 날짜가 바뀌어 올린 모든 멤버에게 같은 날짜로 보인다(3.4.1 로직 2) |
| 관리자 | 다른 멤버가 올린 사진 | 변경됨(5.6.2 「타멤버 사진 삭제・날짜 변경」) |
| 일반 멤버 | 다른 멤버만 올린 사진이 하나라도 섞임 | 403, 요청 전체가 거절됨. 앱은 토스트 「내가 올린 사진만 날짜를 바꿀 수 있어요.」를 띄운다 |

- 관리자는 메인 관리자와 공동 관리자다(5.6.2). 코드에는 아직 공동 관리자 역할이 없어 `OWNER`만 관리자로 본다. 판단은
  `PhotoService.isAdministrator` 한 곳에 있어 역할이 추가될 때 이 함수만 바꾼다.
- 촬영 날짜가 있는 사진도 바꿀 수 있다(3.4.1 로직 1).
- 관리자가 확인 창을 띄우는 경우(다른 멤버 사진이 섞임, 함께 올린 사진 포함)는 앱 동작이다. 서버는 확인 여부를 받지
  않고 권한만 확인한다.
- 권한은 요청 시점의 역할로 판단한다(5.6.3 로직 3).

## 결과

| 요청 | 사진의 변화 |
| --- | --- |
| `capturedDate` | `capturedDate`가 그 날짜가 되고 `dateSource`는 `USER`가 된다. **촬영 시각은 그대로**다(3.4.1 로직 3). 시각이 없던 사진은 시각이 없는 채로 남는다 |
| `clearDate: true` | 날짜와 시각이 비고 `dateSource`는 `UNKNOWN`이 된다. 사진은 「촬영 날짜를 확인할 사진」에 다시 나온다 |

- 날짜를 바꾼 사진은 사진함 목록의 그 날짜 섹션으로 옮겨지고, 날짜 미확인 목록에서는 빠진다. 이동은 목록 조회의 결과이고
  서버가 따로 처리하지 않는다.
- 같은 날짜로 바꿔도 성공한다. 같은 요청을 다시 보내도 같은 결과다.
- 이미 있는 날짜 섹션으로만 옮길 수 있다는 규칙(3.4.2 로직 2)은 앱이 지킨다. 서버는 어떤 날짜든 받는다.

### 「되돌리기」(3.4.2)

서버는 원래 촬영 날짜를 따로 보관하지 않는다. 앱이 목록에서 받은 이전 값을 다시 보낸다.

| 끌기 전 | 되돌릴 때 앱이 보내는 것 | 결과 |
| --- | --- | --- |
| 날짜 없음 | `clearDate: true` | 날짜 없음으로 복원 |
| 촬영 날짜 있음 | 이전 `capturedDate` | 이전 날짜와 시각으로 복원. 출처가 `EXIF`가 아니라 `USER`로 남는다 |
| 지정한 날짜 | 이전 `capturedDate` | 이전 날짜로 복원 |

- `clearDate: true`는 **`USER`이고 시각이 없는 사진**에만 쓸 수 있다. 하나라도 아니면 요청 전체를 400으로 거절한다.
  앱 오류로 촬영 정보(EXIF)와 시각이 지워지지 않게 하는 제안이다. 날짜 없던 사진을 끌었다가 되돌리는 흐름은 모두
  통과한다.
- 되돌린 뒤 사진의 자리는 정렬 규칙대로 정해진다(날짜 없는 사진은 업로드 최신순, 날짜 있는 사진은 이전 날짜의 촬영 시각
  순). 그래서 원래 자리로 돌아간다.

### 끌어서 놓은 사진의 자리 (3.4.2 로직 4, 기획 확정)

끌어서 옮기기는 날짜를 바꾸는 기능이라 섹션 안 순서를 따로 저장하지 않는다. 사진함은 멤버가 함께 보는 공간이라 순서는
촬영 시각 하나로 통일한다.

- 섹션 안 순서는 항상 사진함 목록의 정렬 규칙이다. 늦은 촬영 시각이 앞이고, 시각이 없는 사진은 그 섹션 맨 뒤에 업로드
  순(먼저 올린 사진이 앞, 4.2.3과 같은 규칙)으로 둔다.
- 시각이 있던 사진은 날짜만 바뀌고 시각이 유지되어 그 촬영 시각 자리로 들어간다. 시각이 없던 사진은 맨 뒤 업로드 순
  자리로 들어간다.
- 앱은 손을 뗀 순간 그 날짜 섹션의 같은 규칙에 따른 자리에 사진을 바로 넣어, 새로고침 때 자리가 튀지 않게 한다(끄는
  동안의 자리 미리보기는 그대로). 앱이 정렬에 쓰는 `capturedTime`과 `photoId`는 목록 응답에 있다.

## 전부 성공 또는 전부 실패

- 한 번의 요청은 하나의 트랜잭션이다. 하나라도 권한이 없으면 아무것도 바꾸지 않는다(3.4.1 로직 4).
- 번치 → 사진 ID 오름차순으로 잠근다. 삭제와 같은 순서라 날짜 변경과 삭제가 동시에 와도 한쪽이 먼저 끝난 뒤 다른 쪽이
  처리된다.
- **고른 사진 중 일부가 그사이 지워졌으면 아무것도 바꾸지 않는다**(3.3.1, 날짜 바꾸기 시트의 「저장」 포함). 앱이 그
  사진을 선택에서 빼고 토스트 「선택한 사진 중 N장이 사진함에서 사라져 선택이 해제됐어요.」를 띄울 수 있도록, 사라진
  사진 ID를 `409 PHOTO_004`의 `detail.missingPhotoIds`에 담는다([사진 삭제 계약](photo-delete.md)과 같은 형식).
- 확인 순서: 입력 형식과 날짜(400) → 번치·소속(404, 403) → 다른 번치·`READY` 아님(400) → 사라진 사진(409) → 권한(403) →
  비우기 대상 확인(400).

## 응답

```json
{ "success": true, "data": { "updatedCount": 2 } }
```

| 필드 | 설명 |
| --- | --- |
| `updatedCount` | 날짜가 바뀐 사진 장수. 앱의 토스트 「사진 날짜가 변경되었어요.」는 한 장이든 여러 장이든 같은 문구다 |

## 오류

| 상태 | 코드 | 경우 |
| --- | --- | --- |
| 400 | `COMMON_001` | 빈 목록, 51개 이상, 중복·1 미만 ID, 날짜와 `clearDate`가 둘 다 있거나 없음, 오늘 이후 날짜, 다른 번치 또는 `READY`가 아닌 사진 포함, 비울 수 없는 사진 포함 |
| 400 | `COMMON_002` | 형식이 잘못된 본문(날짜 형식 포함) |
| 401 | `AUTH_001` | 인증 없음 |
| 403 | `AUTH_015` | 가입 미완료 |
| 403 | `AUTH_002` | 번치의 활성 멤버가 아님, 일반 멤버가 다른 멤버만 올린 사진을 포함 |
| 404 | `RESOURCE_001` | 번치 없음 |
| 409 | `PHOTO_004` | 고른 사진 중 일부가 그사이 지워짐. 아무것도 바꾸지 않음 |

## 추천 번들에 알리기

날짜를 바꾸면 이전 날짜의 추천에서 빠지고 새 날짜의 추천에 들어간다(4.2.9 상세 1). 같은 트랜잭션에서
`PhotoChangedEvent`(`photoAdded=false`)를 발행한다. 새 사진이 들어온 것이 아니기 때문이다.

| 요청 | 발행하는 신호 |
| --- | --- |
| `capturedDate` | 바뀌기 전의 날짜마다 1회(날짜가 없던 사진은 제외), 새 날짜 1회. 같은 날짜는 한 번만 |
| `clearDate` | 바뀌기 전의 날짜마다 1회. 날짜 없는 사진은 추천에 들어가지 않는다(4.2.7 상세 1) |

재계산 범위(그 날짜와 전날·다음 날)와 시점(마지막 변경 5분 뒤 한 번)은 구독하는 쪽이 정한다(4.2.9 상세 2). 지금
구독하는 곳은 없다.

## 이 이슈에서 하지 않는 것

- 날짜를 한 번에 조정한 사진을 같은 묶음으로 보려면(4.2.7 로직 3) 조정 때 묶음 ID를 저장해야 한다. 스키마 변경이
  필요해서 추천 번들 구현(#26)과 정한 뒤 별도로 한다. 이 이슈는 마이그레이션이 없다.
- 삭제가 같은 신호를 보내는 것(4.2.9 상세 1)은 삭제 이슈의 후속이다.
- 끌어서 놓은 자리의 섹션 안 순서 저장(3.4.2 로직 4)은 하지 않는다(기획 확정, 위 「끌어서 놓은 사진의 자리」).

## 확정 대기

| 항목 | 기본안 | 확인 대상 |
| --- | --- | --- |
| 요청 모양(`POST .../photos/date`, `capturedDate` 또는 `clearDate`), 응답 `updatedCount` | 위 계약 | 앱 |
| 「되돌리기」의 날짜 없음 복원을 `clearDate: true`로 하는 것, `USER`이고 시각 없는 사진만 허용 | 위 계약 | 앱 |
| 되돌린 뒤 출처가 `EXIF`에서 `USER`로 남는 것 | 허용. 날짜·시각은 그대로 | 기획 |
| 날짜를 옮긴 사진이 추천 번들의 「마지막 사진 추가 시각」을 갱신하는지(4.2.9) | 갱신하지 않음(`photoAdded=false`). 명세서가 「새로운 사진이 추가된 경우에만」이라고 했다 | 추천 번들 담당(#26) |
| 날짜를 조정한 묶음 ID 저장(4.2.7 로직 3) | 이 이슈에서는 하지 않음 | 추천 번들 담당(#26) |
| 오래된 날짜의 하한 | 없음(명세서는 오늘 이후만 막는다) | 기획 |
| 공동 관리자 | 명세서 5.6.2로 확정. 역할이 생기면 `isAdministrator`만 바꾼다 | 번치·멤버 담당 |

## 테스트 기준

- 자리: 날짜를 옮긴 사진은 목록에서 그 날짜의 촬영 시각 자리에 있고, 시각이 없는 사진은 맨 뒤에 업로드 순으로 있다.
- 변경: 올린 멤버가 자기 사진의 날짜를 바꾸면 `capturedDate`가 바뀌고 `dateSource`가 `USER`, 시각은 그대로. 날짜 없던
  사진은 시각 없이 날짜만 생긴다. 여러 장을 한 번에 바꾼다.
- 목록 반영: 날짜를 지정한 사진은 날짜 미확인 목록에서 빠지고 사진함 목록의 그 날짜에 나온다. 비우면 반대로 된다.
- 함께 올린 사진: 올린 멤버 누구가 바꿔도 사진 한 장의 날짜가 바뀌고 모두에게 같은 날짜로 보인다.
- 권한: 일반 멤버는 다른 멤버만 올린 사진이 섞이면 아무것도 바뀌지 않고 403, 함께 올린 사진은 내가 올린 멤버면 허용,
  관리자는 모두 허용.
- 날짜: 오늘은 되고 내일은 400, 날짜와 `clearDate`가 둘 다 있거나 없으면 400, 형식이 잘못된 날짜는 400.
- 비우기: `USER`이고 시각이 없는 사진은 비워지고, 촬영 정보(EXIF) 사진이나 시각이 있는 사진이 섞이면 아무것도 안 바뀌고 400.
- 전부 성공 또는 전부 실패, 지워진 사진 409(`missingPhotoIds`)와 아무것도 안 바뀜, 다른 번치·`READY` 아님 400.
- 입력·인증: 빈 목록, 51개, 중복, 1 미만, 비멤버, 나간 멤버, 가입 미완료, 없는 번치, 토큰 없음.
- 동시 요청(실제 PostgreSQL): 같은 사진을 동시에 바꾸는 요청, 날짜 변경과 삭제가 동시에 와도 결과가 일관됨.
- 추천 번들 신호: 이전 날짜와 새 날짜에 `photoAdded=false`로 발행되고, 같은 날짜는 한 번, 날짜 없던 사진의 이전 날짜는
  없음, 거절된 요청은 발행하지 않음.
